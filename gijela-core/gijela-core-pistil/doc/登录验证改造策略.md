# 登录验证改造策略（gijela-core-pistil）

> 目标：基于当前 `gijela-core-pistil` 与 `gijela-core-security-common` 现有实现，完成一套可落地、可回滚、可审计的登录验证改造方案。  
> 范围：**不做设备指纹认证**，但增加“会话列表 + 定向踢出”能力，聚焦双 Token、可撤销、XSS 风险收敛与运维能力。

---

## 1. 背景与现状

当前工程已具备：
- 双 Token 接口形态（`/api/v1/auth/login`、`/api/v1/auth/refresh`、`/api/v1/auth/logout`）
- `tokenVersion` 失效链路（登出、权限变更可触发版本递增）
- JWT 过滤认证与 Redis 权限缓存

当前关键缺口：
- Refresh Token 仅验签，未做服务端状态校验与撤销
- Access Token 缺少 `jti` 黑名单即时吊销能力
- 前端 `localStorage` 存 token，存在 XSS 窃取风险
- 认证过滤器允许 query token，增加泄露面（日志/Referer）

---

## 2. 改造目标

### 2.1 安全目标（P0）
1. Refresh Token 必须服务端可控（Redis 持久化 + 可撤销）。
2. Access Token 支持即时吊销（`jti` 黑名单）。
3. 保留并强化 `tokenVersion` 全局失效能力。
4. 降低 XSS 风险：Refresh 不可被前端脚本读取。

### 2.2 体验目标（P0）
1. 保持现有登录/刷新接口不破坏前端主流程。
2. 支持无感刷新（前端拦截器自动续期）。

### 2.3 运维目标（P1）
1. 审计登录/刷新/登出/吊销动作。
2. 提供 Redis Key 可观测与排障指引。
3. 提供管理员可见的“用户登录会话列表”，支持按会话定向踢出。
4. 支持单账号最大在线会话数限制，超限后拒绝新登录，必须先手动删除旧会话。

---

## 3. 架构策略（无设备指纹版）

### 3.1 Token 设计
- Access Token：短期（建议 15~30 分钟），JWT，包含 `typ=access`、`jti`、`tokenVersion`。
- Refresh Token：长期（建议 7 天），JWT，包含 `typ=refresh`、`jti`。

### 3.2 Redis 键设计
- `security:session:{sessionId}`  
  - value：`userId`、`username`、`loginAt`、`lastActiveAt`、`clientLabel`、`refreshJtiHash`  
  - ttl：与 refresh 过期一致
- `security:user:sessions:{userId}`  
  - value：`sessionId` 集合（Redis Set）
  - ttl：建议与最长 refresh 生命周期一致（或由定时任务清理空洞会话）
- `security:blacklist:{accessJti}`  
  - value：`1`
  - ttl：access 剩余有效期
- `security:user:{username}:version`（沿用现有）

> 说明：这里的 `sessionId` 是“登录会话ID”，不是设备指纹，不参与设备可信判定，仅用于运维可视化与定向踢出。

### 3.3 鉴权链路
1. 解析 Access Token（验签、过期）
2. 校验 `typ=access`
3. 校验黑名单（`jti`）
4. （可开关）校验 `sid` 在线会话存在性（实时踢出）
5. 校验 `tokenVersion`
6. 加载权限并放行

> 配置开关：`security.jwt.enableAccessSessionCheck`
> - `true`：每次请求校验 `sid`（支持实时踢出，Redis 开销更高）
> - `false`：不在 access 鉴权阶段校验 `sid`（仅 refresh 时校验，会话踢出延迟生效）

### 3.4 登录并发控制
- 配置项：`security.jwt.maxSessionsPerUser`
- 含义：单账号允许同时在线的最大会话数，默认 `1`，设置为 `<= 0` 表示不限制。
- 行为：
  1. 登录时先统计当前账号有效会话数；
  2. 若已达到上限，则直接拒绝新登录；
  3. 用户必须先在“会话管理”中手动踢出旧会话，才能重新登录。

### 3.5 刷新链路
1. 解析 Refresh Token（验签、过期）
2. 校验 `typ=refresh`
3. 从 Redis 校验 `security:session:{sessionId}` 中的 `refreshJtiHash` 与 token 中 `jti` 一致
4. 生成新 Access Token
5. 可选轮换 Refresh Token（默认开启）

### 3.6 会话列表与踢出链路
1. 登录成功后创建 `sessionId`，写入 `security:session:{sessionId}`，并加入 `security:user:sessions:{userId}`。
2. 管理员查询会话列表时，按用户ID读取 `security:user:sessions:{userId}`，批量回查会话详情。
3. 管理员踢出单会话时：
  - 删除 `security:session:{sessionId}`
  - 从 `security:user:sessions:{userId}` 移除该 `sessionId`
  - 可选：将当前 access `jti` 加黑名单（若接口带当前 access）
4. 管理员踢出全部会话时：
  - 清空该用户全部 `sessionId` 对应会话
  - 递增 `tokenVersion`，确保旧 access 全失效

---

## 4. XSS 风险收敛策略

### 4.1 存储策略
- Refresh Token：改为 `HttpOnly + Secure + SameSite` Cookie。
- Access Token：仅保存在前端内存，不落 `localStorage`。

### 4.2 传输策略
- 默认只接受 `Authorization: Bearer <token>`。
- 关闭 query token（`token` / `access_token`）兜底能力。

### 4.3 响应头策略（后端）
统一增加安全头（网关或应用层）：
- `Content-Security-Policy`
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: no-referrer`
- HTTPS 场景下加 `Strict-Transport-Security`

## 5. 代码改造清单（按模块）

## 5.1 `gijela-core-security-common`

1. `JwtUtil`：
- 生成 access/refresh 时加入 `jti`
- 提供 `getJti(...)` 辅助方法

2. `JwtProperties`：新增配置
- `refreshKeyPrefix`（默认 `security:refresh:`）
- `blacklistKeyPrefix`（默认 `security:blacklist:`）
- `refreshRotateEnabled`（默认 `true`）
- `maxSessionsPerUser`（默认 `1`，`<=0` 表示不限制）

3. `JwtAuthenticationFilter`：
- access 认证前增加黑名单校验
- 直接移除 query token 读取（仅保留 `Authorization` 头）

## 5.2 `gijela-core-pistil`

1. 新增 `RefreshTokenService` + `RefreshTokenServiceImpl`：
- `createSession(userId, username, refreshJti, expireAt, clientLabel)`
- `validateSession(sessionId, refreshJti)`
- `revokeSession(sessionId)`
- `revokeAllSessions(userId)`
- `listSessions(userId)`

2. `AuthServiceImpl`：
- `login`：签发后创建登录会话，返回 `sessionId`
- `login`：登录前校验当前账号有效会话数，超限则拒绝登录
- `refresh`：必须先校验会话状态再签发
- `logout`：撤销当前会话 + access `jti` 入黑名单
- 新增管理员踢出能力（单会话踢出、全会话踢出）

3. 审计日志：
- 增加登录/刷新/登出/吊销/管理员踢出事件记录（成功/失败）

4. 新增管理员接口（建议）：
- `GET /api/v1/auth/sessions?userId=...`：查询用户会话列表
- `POST /api/v1/auth/sessions/page`：分页查询会话（支持 `userId`/`username`）
- `POST /api/v1/auth/sessions/{sessionId}/kickout`：踢出单会话
- `POST /api/v1/auth/sessions/kickout-all?userId=...`：踢出全部会话

## 5.3 前端 `gijela-bloom-pistil`

1. token 存储改造：
- 移除 `localStorage.token` 作为长期存储
- access 仅内存态

2. 刷新机制：
- 拦截 401 自动调用刷新
- 刷新成功后重放请求

3. Cookie 策略：
- 刷新接口启用 `withCredentials`

## 6. 验证与发布策略（开发阶段）

当前处于开发阶段，不保留兼容策略，直接按目标方案实施与验证。

### 6.1 灰度策略
1. 环境开关控制（`refreshRotateEnabled`）。
2. 先在 dev/staging 完整验证，再发布生产。
3. 发布后首周保留强化日志，观察刷新失败率、401 比例。

### 6.2 回滚策略
- 任一阶段异常可回滚为：
  - 保留 `tokenVersion`，关闭黑名单检查
  - 关闭 refresh 轮换
  - 临时恢复旧 token 读取方式

---

## 7. 验收标准（必须满足）

1. 登录后存在 `security:session:{sessionId}` 且 TTL 正确。
2. `security:user:sessions:{userId}` 可查询到该 `sessionId`。
3. 删除该会话后，刷新立即失败。
4. 登出后当前会话不可用，旧 access 命中黑名单不可用。
5. 管理员可按会话定向踢出，且不影响同用户其他会话。
6. 权限变更/踢出全部会话后，旧 access 被 `tokenVersion` 拦截。
7. 前端不再把 access/refresh 持久化到 `localStorage`。
8. 当账号在线会话数达到上限时，新登录被明确拒绝，并返回可读错误提示。

## 9. 非目标声明

本策略不包含：
- 设备指纹认证、设备可信评分、设备风控模型
- 2FA（短信/邮箱/OTP）
- 风控引擎（异地登录、行为评分）

上述能力可在当前策略稳定后作为下一阶段增强项。

---

## 10. 一句话结论

在不引入设备指纹认证的前提下，采用“**Access 短效 + 会话化 Refresh 可撤销 + `jti` 黑名单 + `tokenVersion` 全局失效 + Cookie 化 refresh + 管理员会话踢出**”即可在现有 gijela 代码结构内实现一套可上线的登录验证安全方案。

## 11. 开发阶段任务拆解（可直接开工）

### 11.1 后端任务
1. `security-common`：
  - `JwtUtil` 增加 `jti` 生成与解析
  - `JwtProperties` 增加 `refreshKeyPrefix` / `blacklistKeyPrefix` / `refreshRotateEnabled`
  - `JwtAuthenticationFilter` 增加黑名单校验并移除 query token 读取
2. `pistil`：
  - 新增 `RefreshTokenService`（会话化存储）
  - `AuthServiceImpl` 重构 `login/refresh/logout`
  - 新增会话列表与管理员踢出接口
3. 审计：
  - 记录登录、刷新、登出、踢出结果与原因

### 11.2 前端任务
1. 停止 `localStorage.token` 方案，改为 access 内存态。
2. 刷新接口走 Cookie（`withCredentials=true`）。
3. 新增“在线会话列表”与“踢出”操作页（管理员权限控制）。

### 11.3 联调验收清单（最小闭环）
1. 登录成功，返回 access + 建立 session。
2. access 过期后可自动刷新。
3. 单会话踢出后，该会话刷新失败；同用户其他会话不受影响。
4. 全部踢出后，旧 access 全失效。
5. XSS 验证：浏览器脚本无法读取 refresh token。
