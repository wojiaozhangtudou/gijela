# 双 Token 别只会“续期”：gijela 管理后台从登录可用到登录可治理（含实时踢人）

> 适合读者：正在做后台管理系统、需要“可控登录态”的后端/全栈工程师。  
> 技术栈：Spring Boot + Spring Security + Redis + Vue3 + Axios。  
> 场景关键词：双 Token、实时踢人、会话管理、无感刷新、XSS 收敛、设备号/IP 追踪。

---

## 摘要

很多项目上了 JWT 后，只解决了“登录可用”，却没解决“登录可控”。

你可能也遇到过这类线上场景：

- 管理员刚踢人，对方还能继续操作；
- 用户点了退出，结果会话还占着在线名额；
- 出现异常登录，却看不到设备号和来源 IP；
- 安全改造一做就影响体验，业务方不愿上线。

典型问题是：
- 管理员踢掉会话后，对方还能继续用；
- token 泄露后撤销困难；
- 前端把 token 放 localStorage，XSS 风险大；
- 安全和体验经常互相拉扯。

本文基于 `gijela` 项目的真实改造，介绍一套**会话化双 Token**方案：
- `accessToken` 短效 + `refreshToken` 长效；
- Redis 承载会话状态，支持单会话踢出与全部踢出；
- 支持实时踢人（可配置开关）；
- 前端无感刷新，用户体验不受影响。

一句话：这不是“多发一个 token”，而是把登录系统升级为“可治理系统”。

## 1. 为什么单 Token 不够

“单 JWT”在很多系统里都能跑，但有四个硬伤：

1. **撤销困难**：token 未过期前，几乎天然可用；  
2. **踢人不实时**：管理员操作后，客户端往往还能调用接口；  
3. **粒度不够**：想踢“某一个会话”很难；  
4. **风险窗口大**：如果 token 存储方式不当（如 localStorage），泄露后破坏面大。

所以要从“无状态 token”升级为“**有状态会话 + token**”。

## 2. 目标：不仅登录成功，还要登录可治理

本项目的改造目标不是“多发一个 token”，而是实现以下能力：

- 支持无感续期（体验）
- 支持按会话踢出（运维）
- 支持实时失效（安全）
- 支持全局失效（应急）
- 支持审计追溯（治理）

## 3. 整体设计：会话化双 Token

### 3.1 Token 职责分离

- `accessToken`：短期（当前 30 分钟），用于业务接口访问；
- `refreshToken`：长期（当前 7 天），仅用于换新 access。

### 3.2 Redis 状态模型

- `security:refresh:session:{sid}`：会话主体（userId/username/loginAt/lastActiveAt/refreshJtiHash/deviceNo/loginIp/clientLabel）
- `security:user:sessions:{userId}`：用户会话索引
- `security:blacklist:{jti}`：access 黑名单
- `security:user:{username}:version`：tokenVersion

### 3.3 前端存储策略

- access：仅内存态，不落 localStorage；
- refresh：HttpOnly Cookie（JS 不可读）。

---

## 4. 核心链路设计

### 4.1 登录链路

1. 校验用户名/密码；
2. 创建会话 `sid`；
3. 签发 access + refresh；
4. refresh 写入 HttpOnly Cookie。

### 4.2 刷新链路

1. 校验 refresh 签名和类型；
2. 校验 `sid` 会话存在、`refreshJtiHash` 匹配；
3. 签发新 access（可轮换 refresh）；
4. 返回新登录态。

### 4.3 注销/踢出链路

- 注销：撤销当前会话 + access `jti` 拉黑 + tokenVersion 递增；
- 单踢：删除 `security:refresh:session:{sid}`；
- 全踢：删除用户所有会话并递增 tokenVersion。

> 注意：前端退出必须调用后端 `/auth/logout`，只清前端本地 token 会导致会话残留，占用在线名额。

---

## 5. 实时踢人是怎么做到的

关键点：**请求鉴权阶段在线校验 `sid`**。

即每次 access 鉴权除了验签，还会检查 Redis 里对应会话键是否存在：

- 存在：继续放行；
- 不存在：视为会话失效，直接未认证。

这样管理员一旦踢出会话，用户**下一次请求就失效**，而不是等 token 自然过期。

---

## 6. 性能与安全取舍：为什么要查 Redis

常见疑问：双 Token 不就是 access 本地验签、过期再 refresh 吗？

没错，那是“经典无状态模式”。本项目**两种都支持**，通过配置切换；当前默认是“增强安全模式”：

- 经典模式：性能优先，实时可控能力弱；
- 增强模式：可控优先，需一定 Redis 成本。

本质是以少量在线查询换取“会话治理能力”。在后台管理系统里，这个交换通常值得。

配置矩阵可以这样理解：

- `security.jwt.enableAccessSessionCheck=true`：增强安全模式（每次鉴权查会话在线态，支持实时踢人）
- `security.jwt.enableAccessSessionCheck=false`：经典无状态模式（access 仅本地验签，踢人通常延迟到 access 过期）

---

## 7. 一键切换：实时踢人开关

为了让系统在“性能优先”和“安全优先”之间可切换，新增了配置开关：

- `security.jwt.enableAccessSessionCheck`
  - `true`：每次 access 请求检查会话在线状态（支持实时踢人）
  - `false`：不做该检查（踢人延迟生效，通常到 access 过期）

这让双 Token 策略具备了**场景化可调能力**。

也就是说：你现在的实现不是“二选一重构”，而是“同一套代码 + 配置开关”同时覆盖两种运行模式。

---

## 8. 再进一步：单账号在线数限制

本项目还增加了一个很实用的治理能力：**单账号最大在线会话数控制**。

- 配置项：`security.jwt.maxSessionsPerUser`
- 默认值：`1`
- 特性：
  - 超过上限后，新的登录请求直接拒绝；
  - 不会自动顶掉旧会话；
  - 必须先手动删除旧设备/旧会话，才能继续登录。

这类策略很适合后台管理系统，因为它强调的是“账号归属明确”和“会话可追溯”。

## 9. 前端配套改造（决定体验）

后端再完善，前端处理不好也会“看起来很烂”。本项目前端做了这些关键点：

1. Axios 响应拦截器统一续期；
2. 并发刷新互斥，避免 refresh 风暴；
3. access 失效后自动跳转登录；
4. 会话管理页支持：
   - 分页查询
   - 用户名筛选
   - 按 userId 精确筛选
   - 单会话踢出 / 全部踢出
5. 个人中心“登录设备管理”已落地为弹窗，不跳转页面，可直接查看并管理当前用户会话。

## 10. 设备号与登录 IP：可追溯能力

为了解决“谁在登录、从哪登录”的可观测问题，本项目新增了会话维度的追踪字段：

- `deviceNo`：设备编号（当前由前端生成并持久化）
- `loginIp`：登录 IP（后端按 `X-Forwarded-For/X-Real-IP/RemoteAddr` 解析）
- `clientLabel`：客户端信息（UA/平台）

这样在会话列表和个人设备管理弹窗里，就能做到：

1. 快速定位异常来源（IP/设备）
2. 精准踢出可疑会话
3. 支撑运维审计与安全排查

## 11. 菜单与权限：会话管理页落地

为了让能力可运营，新增了菜单和按钮权限：

## 12. 踩坑与修复记录

### 12.1 “踢了还能用，刷新页面才过期”

原因：只撤销 refresh，没有在 access 鉴权时校验 sid。  
修复：增加 `sid` 在线校验（可开关）。

### 12.2 刷新浏览器后顶部 tab 重复

原因：`/sys/users` 和 `/system/users` 别名路径被当作两个标签。  
修复：tabs store 增加路径规范化与恢复去重。

### 12.3 会话列表只能按 userId 查

修复：新增分页接口，支持 userId 可选 + username 模糊过滤。

### 12.4 “点退出后还占在线名额，重新登录被拦”

原因：前端早期仅清理本地状态，没有调用后端注销接口。  
修复：前端退出统一调用 `/auth/logout`，后端同步撤销会话并清理 refresh cookie。

### 12.5 “设备信息缺失，无法判断异常登录来源”

原因：会话模型早期只记录 userId/时间，不含设备号和 IP。  
修复：会话模型补充 `deviceNo/loginIp/clientLabel`，并在列表与个人设备管理弹窗展示。
