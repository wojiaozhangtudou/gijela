# 完美的 Token 登录方案设计（架构版）

> 本文聚焦于**方案设计**，不涉及具体代码实现，适合架构师和技术决策者阅读。

---

## 一、设计目标

一个“完美”的 Token 登录方案需要在以下维度达到平衡：

| 维度 | 目标 | 优先级 |
|------|------|--------|
| **安全性** | 防CSRF、防XSS、防重放、防Token盗用 | P0 |
| **用户体验** | 无感刷新、多端同步、长期免登录 | P0 |
| **可运维性** | 可踢人、可审计、可监控、可回滚 | P1 |
| **性能** | 低延迟、高吞吐、可水平扩展 | P1 |
| **兼容性** | Web/App/小程序全端支持 | P2 |

## 二、核心架构：双Token + 分级存储

### 2.1 方案全景图

```
┌─────────────────────────────────────────────────────────────────┐
│                           客户端层                               │
├─────────────┬─────────────┬─────────────┬─────────────────────┤
│   Web端     │   App端     │   小程序    │      第三方         │
│ (内存+Cookie)│ (内存+Keychain)│ (内存+Storage)│     (Bearer)       │
└──────┬──────┴──────┬──────┴──────┬──────┴──────────┬──────────┘
       │             │             │                  │
       ▼             ▼             ▼                  ▼
┌─────────────────────────────────────────────────────────────────┐
│                         API网关层                                │
│              限流 / 黑白名单 / 设备指纹检测                       │
└─────────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────────┐
│                        认证服务层                                │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐            │
│  │ 登录/登出   │  │ Token刷新   │  │  Token撤销  │            │
│  └─────────────┘  └─────────────┘  └─────────────┘            │
└─────────────────────────────────────────────────────────────────┘
       │                           │
       ▼                           ▼
┌──────────────┐          ┌──────────────┐
│   Redis集群   │          │   业务数据库  │
│ Refresh Token│          │   用户信息    │
│   黑名单      │          │   权限数据    │
│   设备指纹    │          └──────────────┘
└──────────────┘
```

### 2.2 两种Token的职责划分

| Token类型 | 存储位置 | 有效期 | 是否可撤销 | 核心职责 |
|-----------|---------|--------|-----------|---------|
| **Access Token** | 客户端内存 | 15分钟 | 黑名单方式 | 业务接口鉴权，无状态验证 |
| **Refresh Token** | 服务端(Redis) | 7-30天 | 是 | 获取新Access Token，可撤销 |

**设计理念：**
- Access Token 负责“性能”：短效、无状态、验签即可、不查存储
- Refresh Token 负责“控制”：长效、可撤销、需要时查存储

## 三、Token 数据结构设计

### 3.1 Access Token 内容（最小化原则）

| 字段 | 说明 | 必要性 |
|------|------|--------|
| 用户ID | 唯一标识用户 | 必须 |
| 角色/权限版本 | 用于权限变更检测 | 必须 |
| 设备指纹哈希 | 防止跨设备盗用 | 推荐 |
| Token唯一ID | 用于黑名单 | 可选 |
| 签发时间/过期时间 | 时效控制 | 必须 |

**设计原则：** 只存“验权必需”字段，不存敏感信息（手机号、地址等）

### 3.2 Refresh Token 存储结构（Redis）

| 存储Key | 存储Value | 用途 |
|---------|-----------|------|
| `refresh:{userId}:{deviceId}` | 设备信息、指纹、最后使用时间 | 验证Refresh Token有效性 |
| `user:{userId}:devices` | 设备ID集合 | 管理用户登录设备 |
| `user:{userId}:token_version` | 版本号（整数） | 改密码后使所有Token失效 |
| `blacklist:{accessTokenJti}` | 过期时间戳 | 主动撤销Access Token |

## 四、核心流程设计

### 4.1 登录流程

```
用户 ──▶ 提交凭证 ──▶ 验证身份 ──┬──▶ 2FA验证(如需)
                                 │
                                 ▼
                          生成Access Token
                                 │
                                 ▼
                          生成Refresh Token
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
              存储到Redis                 返回客户端
           (设备信息/指纹)           (Access放内存/Refresh放安全存储)
```

**关键设计点：**
- 每个设备独立Refresh Token，支持多设备管理
- 限制每用户最多5个活跃设备
- 记录登录IP、设备名、时间用于审计

### 4.2 请求鉴权流程

```
请求 ──▶ 携带Access Token ──▶ 验证签名 ──┬── 失败 ──▶ 返回401
                                        │
                                        ▼ 成功
                                 检查黑名单 ──┬── 在黑名单 ──▶ 返回401
                                        │
                                        ▼ 不在
                                 检查版本号 ──┬── 不匹配 ──▶ 返回401(需重新登录)
                                        │
                                        ▼ 匹配
                                 检查设备指纹 ──┬── 不匹配 ──▶ 告警+返回401
                                        │
                                        ▼ 匹配
                                    放行业务请求
```

**性能优化：** 90%的请求只经过验签步骤，无需查Redis

### 4.3 Token刷新流程

```
Access Token过期 ──▶ 客户端携带Refresh Token ──▶ 验证Refresh Token签名
                                                        │
                                                        ▼
                                              Redis中是否存在？
                                                        │
                                            ┌───────────┴───────────┐
                                            ▼                       ▼
                                           存在                     不存在
                                            │                       │
                                            ▼                       ▼
                                     验证版本号匹配              返回重新登录
                                            │
                                            ▼
                                     生成新Access Token
                                            │
                              ┌─────────────┴─────────────┐
                              ▼                           ▼
                        可选：滚动刷新             返回新Access Token
                        (Refresh Token换发)
```

**滚动刷新策略：** 当Refresh Token生命周期过半时，换发新的Refresh Token，降低长期不换发带来的风险

### 4.4 撤销/踢人流程

| 场景 | 操作方式 | 生效时间 |
|------|---------|---------|
| 用户主动登出 | 删除Refresh Token + Access Token加入黑名单 | 立即 |
| 管理员踢人 | 删除Refresh Token + 递增版本号 | Access Token立即失效 |
| 用户修改密码 | 递增版本号 + 删除所有Refresh Token | 所有Token立即失效 |
| 检测到异常 | 标记设备可疑 + 撤销Refresh Token | 下次刷新时失效 |

## 五、安全设计

### 5.1 威胁模型与对策

| 威胁 | 攻击方式 | 防御措施 |
|------|---------|---------|
| **CSRF** | 恶意网站利用Cookie自动携带 | Access Token不放Cookie，放在Header |
| **XSS** | 脚本读取localStorage中的Token | Refresh Token放httpOnly Cookie；Access Token放内存 |
| **Token窃取** | 中间人/客户端恶意软件 | 短效Token(15分钟)+设备指纹绑定 |
| **重放攻击** | 截获Token重复使用 | 短有效期+请求签名(可选) |
| **暴力破解** | 穷举Token签名 | 强密钥+限流+账号锁定 |
| **内部人员** | 运维人员查库窃取 | Refresh Token存哈希值 |

### 5.2 分级存储策略

| 端类型 | Access Token存储 | Refresh Token存储 | 理由 |
|--------|-----------------|-------------------|------|
| **Web端** | 内存(变量) | httpOnly Cookie | 内存防XSS，Cookie防XSS且支持自动携带 |
| **移动端原生** | 内存 | Keychain/Keystore | 利用操作系统安全存储 |
| **小程序** | 内存 | 小程序Storage | 受限于平台能力，需加强其他防护 |
| **SPA/PWA** | 内存 | httpOnly Cookie | 同Web端 |

### 5.3 设备指纹设计

**采集信息（不侵犯隐私）：**
- User-Agent（浏览器标识）
- Accept-Language（语言偏好）
- IP段（前24位）
- 时区偏移量
- 屏幕分辨率（可选）

**应用场景：**
- Token签发时绑定指纹
- 每次请求验证指纹是否匹配
- 不匹配时触发告警，但不立即拦截（避免误伤）

### 5.4 异常检测机制

| 异常类型 | 检测方式 | 处置动作 |
|---------|---------|---------|
| 短时间内多地登录 | 记录最近IP，检测地理位置跳变 | 告警 + 要求短信验证 |
| 频繁刷新Token | Redis计数器，5分钟内超过10次 | 暂时锁定账号15分钟 |
| 异常设备数量 | 单用户超过5个设备 | 拒绝新设备登录 |
| Refresh Token重放 | 检测到同一jti使用两次 | 撤销该用户所有Token |

## 六、性能与扩展性设计

### 6.1 性能目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| Access Token验证延迟 | < 2ms | 纯CPU验签，无IO |
| Token刷新延迟 | < 10ms | 含一次Redis读 |
| 登录延迟 | < 50ms | 含DB查询+Redis写入 |
| 系统吞吐量 | 10万 QPS | 水平扩展可达 |

### 6.2 缓存策略

| 数据类型 | 缓存位置 | TTL | 说明 |
|---------|---------|-----|------|
| 用户版本号 | Redis | 永久 | 改密码时更新 |
| 用户权限 | Redis + 本地缓存 | 5分钟 | 减少DB压力 |
| Refresh Token | Redis | 跟随Token有效期 | - |
| 黑名单 | Redis | 跟随Token剩余有效期 | - |

### 6.3 水平扩展方案

```
                    ┌─────────┐
                    │ 负载均衡 │
                    └────┬────┘
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
      ┌────────┐   ┌────────┐   ┌────────┐
      │ 认证A  │   │ 认证B  │   │ 认证C  │   (无状态，可随意扩缩)
      └───┬────┘   └───┬────┘   └───┬────┘
          └─────────────┼─────────────┘
                        ▼
                  ┌──────────┐
                  │Redis集群 │ (所有认证服务共享)
                  │ 主从+哨兵 │
                  └──────────┘
```

**关键点：**
- 认证服务无状态，可任意水平扩展
- 只有Refresh Token验证需要访问Redis
- Access Token验证完全无状态

### 6.4 降级与容灾

| 故障场景 | 降级策略 | 用户影响 |
|---------|---------|---------|
| Redis部分节点故障 | 自动故障转移 | 无感知 |
| Redis全集群故障 | 只接受已签发的Access Token，拒绝刷新 | 最多15分钟内无法刷新 |
| 数据库故障 | 使用缓存中的用户信息 | 权限变更可能延迟生效 |

## 八、兼容性设计

### 8.1 多端适配策略

| 端类型 | Refresh Token传输 | Access Token刷新方式 | 特殊处理 |
|--------|------------------|---------------------|---------|
| Web | httpOnly Cookie | 自动，拦截器处理 | 支持无感刷新 |
| iOS App | 响应体 + Keychain | 主动调用刷新接口 | 后台刷新 |
| Android App | 响应体 + Keystore | 主动调用刷新接口 | 后台刷新 |
| 小程序 | 响应体 + Storage | 主动调用刷新接口 | 需处理并发刷新 |
| 第三方 | Bearer Token | 标准OAuth2 | 按标准协议 |

### 8.2 版本演进兼容

```yaml
API版本管理:
  v1: 初始版本
  v2: 增加设备指纹
  v3: 增加滚动刷新
  v4: 增加可疑设备标记

兼容策略:
  - 新旧Token版本可共存
  - 旧版客户端收到新版Token能正常解析
  - 关键字段增量添加，不删减
```

## 九、方案对比与选型建议

### 9.1 与常见方案对比

| 特性 | 纯Session | 纯JWT | 本方案 |
|------|----------|-------|--------|
| 实时踢人 | ✅ | ❌ | ✅ |
| 无状态验证 | ❌ | ✅ | ✅（90%请求） |
| 跨端支持 | ❌ | ✅ | ✅ |
| 设备管理 | ❌ | ❌ | ✅ |
| 防CSRF | 需额外配置 | ✅ | ✅ |
| 防XSS | ✅ | ❌ | ✅ |
| 实现复杂度 | 低 | 中 | 中高 |

### 9.2 适用场景

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 企业内部后台 | Session | 简单，需要踢人 |
| C端App | **本方案** | 多端+安全+体验平衡 |
| 开放API平台 | 纯JWT | 无状态，第三方友好 |
| 高安全金融应用 | 本方案+增强 | 加短信/生物验证 |
| 简单博客/论坛 | Session或纯JWT | 过度设计没必要 |

## 十一、总结

### 设计哲学

1. **分层防御**：不依赖单一安全措施，层层设防
2. **性能优先**：90%的请求保持无状态，只有需要控制时才查存储
3. **可撤销是底线**：无论设计多复杂，必须能主动控制会话
4. **体验不妥协**：用户7-30天免登录，刷新过程无感知

### 核心取舍

| 做对了什么 | 接受了什么代价 |
|-----------|---------------|
| 双Token分离职责 | 实现复杂度增加 |
| 分级存储 | 需要适配不同端 |
| 设备指纹 | 可能误伤，需要灰度 |
| 版本号机制 | 每次请求多一次版本比较（内存操作） |

### 一句话总结

> **用Access Token换性能，用Refresh Token换控制，用分级存储换安全，三者结合才是工程上的“完美”。**
