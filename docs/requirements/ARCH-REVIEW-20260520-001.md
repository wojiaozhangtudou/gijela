# ARCH-REVIEW-20260520-001：chat-flow 评审文档整合与 Phase 2 开发口径评审

### 一、可落地性结论
- 结论：有条件可落地。
- 依据：
  - Phase 1 已实现并归档，运行链路（会话、消息、Completion、运行历史）已闭环。
  - 现有评审文档（20260515/18/19-001~004）可覆盖“规划→开工→落地”全周期，但存在信息分散、口径冲突、状态过时问题。
  - 若先完成文档口径统一，再进入 Phase 2，可显著降低实现偏差与返工。

### 二、关键问题与调整建议
1. 问题：评审结论分散，执行口径不唯一。
   - 位置：
     - ARCH-REVIEW-20260515-001 / 五、chat-flow 企业级功能点清单（P0 全量）
     - ARCH-REVIEW-20260519-002 / 四、阶段计划（Phase 1/2/3）
   - 风险：研发对“全量 P0 一次上线”与“分阶段推进”理解不一致，导致排期和验收标准冲突。
   - 建议：以“已实现事实 + 后续迭代”重写统一基线：
     - 已完成：Phase 1（会话闭环 + 运行历史 + 模式语义）
     - 待开发：Phase 2（系统变量注入、chatflow 类型增强、流式能力按子阶段拆解）
   - 优先级：P0

2. 问题：安全口径前后不一致（模型密钥存储）。
   - 位置：
     - ARCH-REVIEW-20260518-001 / 二-6（本期不在模型表存真实 API Key）
     - ARCH-REVIEW-20260519-001 / 二.5（`cf_llm_model.api_key` 描述为运行时使用）
   - 风险：可能出现明文密钥落库，违反最小暴露原则与审计要求。
   - 建议：统一为“密钥不入业务表，仅走环境变量/配置中心”，并在模型表字段说明中标注“禁用明文密钥持久化”。
   - 优先级：P0

3. 问题：接口契约仍有历史表述残留，影响联调一致性。
   - 位置：
     - ARCH-REVIEW-20260519-003 / 二-1（要求补 API 合同）
     - ARCH-REVIEW-20260519-004 / 二-2（分页排序细节待补）
   - 风险：前后端分页、排序、默认值不一致，导致“可用但不可验收”。
   - 建议：在单一“Phase 2 开发合同”中固定：
     - 分页默认值与上限（如 `pageSize<=100`）
     - 排序默认规则（会话按 `updated_at desc`，消息按 `created_at asc`）
     - 错误码映射（超时/参数/未发布工作流）
   - 优先级：P0

4. 问题：文档导航页存在重复/过时状态。
   - 位置：index.md / 当前状态、最新评审、当前缺陷跟踪。
   - 风险：管理面信息失真，后续任务分派基于错误状态。
   - 建议：
     - 当前状态仅保留一套“Phase 1 已归档”结论；
     - 最新评审保留“最新整合评审 + 当前有效开工评审”；
     - 缺陷状态以 BUG-LIST 为唯一真源。
   - 优先级：P0

5. 问题：Phase 2 目标过大，缺少最小可验收子里程碑。
   - 位置：ARCH-REVIEW-20260519-002 / 四（Phase 2、Phase 3）。
   - 风险：系统变量、结构化历史、SSE 流式同时推进，回归面过大。
   - 建议：Phase 2 拆为 2A/2B：
     - 2A：系统变量注入 + `chatflow` 类型 + 非流式稳定回归
     - 2B：SSE 流式输出 + 前端流式渲染
   - 优先级：P1

### 三、最小落地路径（MVP）
- 第一步：完成文档整合基线（本评审文档 + index 导航统一），冻结 Phase 2 范围。
- 第二步：先做 Phase 2A（`sys.*` 注入、契约固定、稳定性验证通过），不引入 SSE。
- 第三步：在 2A 稳定后推进 2B（流式输出），并单独提测与压测。

### 六、Phase 2 开发入口（任务拆分）

#### 2A：系统变量注入与契约收敛（先做）
1. 后端引擎：`RunContext` 注入 `sys.query`、`sys.chat_history`、`sys.conversation_id`。
2. 后端契约：固定分页/排序/错误码默认值（`pageSize<=100`；会话 `updated_at desc`；消息 `created_at asc`）。
3. 类型区分：`appType=chatflow` 生效，Start 节点展示系统变量（只读）。
4. 数据策略：开发阶段执行数据清空，不保留 Phase 1 `question/history` 旧链路兼容。
5. 验收门槛：
  - 单测通过：系统变量注入、错误码映射。
  - 集成通过：创建会话 → 发消息 → 运行成功 → 历史可回放。
  - 回归通过：现有 workflow（非 chatflow）链路无行为变化。

#### 2B：流式输出（2A 稳定后）
1. 后端接口：新增 chat-flow SSE 对话输出接口（保持与非流式 Completion 并存）。
2. 前端工作台：消息窗口支持 token 级增量渲染与中断处理。
3. 稳定性：补充超时、断流、重连与降级文案策略。
4. 验收门槛：
  - 功能：流式输出完整、结束态可落库。
  - 性能：长文本响应稳定，无明显 UI 卡顿。
  - 回归：非流式模式可继续作为兜底路径。

#### 上线顺序建议
- 先发布 2A（契约稳定版），观察一轮线上运行数据。
- 再发布 2B（体验增强版），按灰度策略放量。
