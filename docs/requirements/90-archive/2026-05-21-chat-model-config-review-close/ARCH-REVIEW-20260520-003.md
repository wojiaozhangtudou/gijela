# ARCH-REVIEW-20260520-003：chat 模块 LLM / Embedding 模型配置数据库化评审

### 一、可落地性结论
- 结论：可落地。
- 依据：
  - 当前 `open-ai` / `embedding` 配置由 `ChatModuleProperties` + `application.yml` 直接驱动，链路清晰，改造范围可控。
  - 现有前端已有知识库管理页面，可作为“模型配置管理”的交互原型，但不能直接复用当前页面语义。
   - 本次方案明确为“数据库单源配置 + 前端维护”，支持多家厂商的 OpenAI-compatible 大模型接入；并将“新建会话选大模型/输名称、知识入库选向量模型”纳入同一配置入口，不保留 YAML 运行兜底，也不引入配置缓存刷新、版本、启停、审计、回滚等扩展能力。

### 二、关键问题与调整建议
1. 问题：运行时配置仍依赖静态 YAML，无法在线维护。
   - 位置：
     - `gijela-core/gijela-core-chat/src/main/resources/application.yml`
     - `gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/config/ChatModuleProperties.java`
     - `gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/config/ChatModuleConfig.java`
   - 风险：改模型、改地址、调超时时只能发版；多环境切换和紧急止血成本高。
   - 建议：`open-ai` / `embedding` 改为完全从数据库读取，并通过前端页面维护；支持多家厂商的 OpenAI-compatible 配置项；YAML 中仅保留与数据库连接相关的基础环境配置。
   - 优先级：P0

2. 问题：密钥与模型参数未分层，存在明文配置外泄风险。
   - 位置：`application.yml` 中 `open-ai.api-key`、`embedding.api-key`
   - 风险：密钥一旦进入代码仓库或默认配置，存在泄露、误提交、旧配置内容被暴露的风险。
   - 建议：
       - 数据库中采用明文存储 API Key，前端不回显明文；
     - 前端只显示“已配置 / 未配置”，不回显明文；
     - 日志与接口响应禁止输出密钥全文；
     - 旧的 YAML 明文默认值必须移除。
   - 优先级：P0

3. 问题：数据库是唯一来源时，数据库不可用会直接影响模型调用与配置读取。
   - 位置：`ChatModuleConfig.openAiCompatibleProperties()`、`KnowledgeSearchGateway` 的 embedding 调用链路
   - 风险：数据库异常时，LLM 与 embedding 配置不可读取，会直接影响聊天服务能力。
   - 建议：在需求中明确该风险属于可接受范围；数据库稳定性作为前置约束，前端仅负责维护，不做额外降级链路。
   - 优先级：P0

4. 问题：数据库配置表字段范围需要收敛，避免无效扩展。
   - 位置：目标数据模型设计
   - 风险：模型配置字段设计过宽会增加前后端复杂度，偏离“仅维护 LLM/Embedding 参数”的目标。
   - 建议：新增配置表仅包含：
       - 配置类型：`open-ai` / `embedding`
       - 厂商标识：如 `qwen` / `deepseek` / `openai` / `azure-openai`
     - `base_url`、`api_key_ciphertext`、`model`
     - 超时字段
     - `updated_time`
   - 优先级：P1

5. 问题：前端维护页面缺少权限边界与交互规范。
   - 位置：前端管理页面设计
   - 风险：普通用户可见、可改敏感配置，容易引发生产事故。
   - 建议：新增独立后台页，至少支持：
     - 列表查看当前配置状态；
     - 编辑 `base_url` / `model` / `timeout`；
     - 密钥仅支持“重新设置 / 清空”，不回显；
     - 保存前校验 URL 与超时范围；
     - 仅授权角色可访问。
   - 优先级：P1

6. 问题：现有知识库页面可参考，但不适合直接承载模型配置。
   - 位置：`gijela-bloom/gijela-bloom-chat/src/views/KnowledgePage.vue`
   - 风险：知识库操作与模型配置属于不同职责，混在一起会破坏页面语义和权限模型。
   - 建议：复用其“卡片 + 表单 + 结果反馈”的视觉风格，单独新增“模型配置管理”页面和接口。
   - 优先级：P2

7. 问题：新建会话与知识入库都需要显式选择模型，但当前入口没有统一承载。
    - 位置：
       - `gijela-bloom/gijela-bloom-chat/src/views/ChatPage.vue`（`createNewSession()`）
       - `gijela-bloom/gijela-bloom-chat/src/views/KnowledgePage.vue`（`submitKnowledge()` / `submitKnowledgeFile()`）
       - `gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/controller/ChatController.java`
       - `gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/domain/dto/KnowledgeIndexRequest.java`
    - 风险：
       - 新会话不带模型，后续消息只能继续沿用默认模型，无法按会话绑定；
       - 知识入库不带向量模型，文本向量化会依赖隐式默认值，和“配置可维护”目标不一致。
    - 建议：
      - 新建会话时在前端弹窗中同时收集“会话名称 + 对话大模型”；
       - 后端新增会话创建接口或会话初始化字段，持久化 `sessionName` 与 `modelRoute`；
       - 知识入库时在前端选择“向量模型”，并把所选模型传递到入库请求中；
       - 后端入库接口接收向量模型标识后，再执行向量化。
    - 优先级：P0

### 三、最小落地路径（MVP）
- 第一步：定义数据库配置表与读写接口，先只覆盖 `open-ai` 和 `embedding` 两类配置。
- 第二步：前端新建会话弹窗补齐“名称 + 对话大模型选择”，知识入库表单补齐“向量模型选择”。
- 第三步：后端会话创建与知识入库接口同步接收模型标识，并按入参执行。
- 第四步：前端新增配置管理页，支持查看和编辑。

### 四、待拍板决策
1. API Key 采用数据库明文存储，不做加密列。
2. 新建会话要求“名称必填 + 对话大模型必选”。
3. 知识入库支持向量模型切换按钮，默认可预填推荐项。

### 六、本轮开发反馈（2026-05-20）
1. 类型：架构缺口
    - 严重级别：Major
    - 位置：
       - `gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/service/impl/DefaultGraphExtractionService.java`
       - `gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/service/impl/DefaultAttachmentSummaryService.java`
    - 影响：当前已完成“聊天主链路 + 知识入库 embedding”按数据库配置动态读取；但图谱抽取、附件摘要仍使用静态 `OpenAiCompatibleClient` 注入，尚未切换到数据库配置源。
    - 建议：补充统一运行时模型解析器，将上述链路也切换为 `chat_model_config` 读取。
    - 临时方案：图谱/附件链路暂沿用现有 YAML 配置，聊天与知识链路已可用数据库配置。

2. 类型：实现风险
   - 严重级别：Minor
   - 位置：`gijela-bloom/gijela-bloom-chat/src/views/ModelConfigPage.vue`
   - 影响：当前页面未加独立权限拦截，具备路由访问能力的用户可进入配置页。
   - 建议：在权限模型明确后补充路由守卫与后端鉴权。
   - 临时方案：通过网关或上层权限配置暂时限制访问范围。
