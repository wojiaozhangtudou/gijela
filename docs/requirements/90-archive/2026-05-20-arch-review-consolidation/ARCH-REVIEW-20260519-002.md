# ARCH-REVIEW-20260519-002：工作流接入模型对话（仅 chat-flow 业务域）

> 规划日期：2026-05-19  
> 状态：已复审（Phase 1 可开工）  
> 涉及模块：`gijela-core-chat-flow`、`gijela-bloom-chat-flow`

---

## 一、可落地性结论

- **结论：有条件可落地**
- **依据：**
        - `gijela-core-chat-flow` 已具备工作流执行、版本管理、运行日志与模型管理能力，是天然主干。
        - 业务边界已确认：`gijela-core-chat` 与 `chat-flow` **无业务关系**，不做能力复用、不做运行时互调。
        - 会话管理、消息存储、对话入口、SSE 输出均在 chat-flow 内独立建设。
        - Phase 1 可先完成 chat-flow 内闭环（非流式）；Phase 2/3 再补齐系统变量与流式体验。

---

## 二、现状分析（chat-flow 独立业务域）

### 2.1 生产主模块（`gijela-core-chat-flow`）现状

```
POST /api/v1/chat-flow/workflows/{workflowId}/runs
         ↓
 WorkflowRunService.startRun()  (同步)
         ↓
 WorkflowEngine.executeB1()
         ↓
 WorkflowEngineResult { finalResult: { answer: "..." } }
```

### 2.2 建设缺口（必须在 chat-flow 内补齐）

| 缺口 | 描述 |
|------|------|
| 会话模型 | chat-flow 当前缺少“会话 + 消息”领域模型与表结构 |
| 对话入口 | chat-flow 当前只有 workflow run 接口，缺少对话友好入口 |
| 历史能力 | workflow 当前无法直接消费结构化会话历史 |
| 流式输出 | chat-flow 当前只有同步结果，缺 SSE 对话输出 |
| 降级机制 | 执行失败时缺统一对话级兜底返回 |
| 域边界治理 | 需明确 chat-flow 全量自建，不从 `gijela-core-chat` 复用业务对象与链路 |

---

## 三、推荐架构方案

### 3.1 模块通信方式选择

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **A. 生产入口放在 chat（再转发 chat-flow）** | 复用旧代码快 | 违反“无业务关系”边界，职责错位 | ❌ 不采用 |
| **B. 生产入口直接放在 chat-flow** | 边界清晰，部署简单，后续演进一致 | 需移植会话与消息能力 | ✅ **推荐** |
| **C. chat-flow + MQ 异步总线** | 扩展性好 | 实现复杂，不利于当前 RT 对话 | ❌ 当前阶段不采用 |

**结论：生产链路、调试链路、数据链路均由 chat-flow 独立承载；不引入 `gijela-core-chat`。**

---

### 3.2 Session 绑定设计

在 `chat-flow` 模块新增会话域表（独立业务数据模型）：

```sql
CREATE TABLE cf_chatflow_session (
        id BIGINT PRIMARY KEY AUTO_INCREMENT,
        session_id VARCHAR(64) NOT NULL UNIQUE,
        title VARCHAR(128) NULL,
        workflow_id VARCHAR(64) NOT NULL,
        workflow_inputs JSON NULL,
        status VARCHAR(32) NOT NULL DEFAULT 'active',
        created_at DATETIME NOT NULL,
        updated_at DATETIME NOT NULL,
        deleted TINYINT NOT NULL DEFAULT 0
);

CREATE TABLE cf_chatflow_message (
        id BIGINT PRIMARY KEY AUTO_INCREMENT,
        session_id VARCHAR(64) NOT NULL,
        role VARCHAR(16) NOT NULL,
        content LONGTEXT NOT NULL,
        extra_json JSON NULL,
        created_at DATETIME NOT NULL,
        deleted TINYINT NOT NULL DEFAULT 0,
        INDEX idx_session_created (session_id, created_at)
);
```

- `cf_chatflow_session.workflow_id` 必填：每个会话绑定一个工作流（后续可扩展切换策略）。
- `workflow_inputs` 仅存“固定业务参数”，不存本轮用户 query。

### 3.3 数据流设计（生产入口在 chat-flow）

**Phase 1（chat-flow 内闭环，非流式）：**

```
用户发消息
    ↓
POST /api/v1/chat-flow/chat/completions { sessionId, content }
    ↓
ChatflowConversationService
        ↓
读取 cf_chatflow_session + 最近 N 轮 cf_chatflow_message
        ↓
组装 WorkflowRunRequest.inputs：
  question = content
  history  = "[{role,content},...]"  // Phase 1 先字符串
  + workflow_inputs
        ↓
调用内部 WorkflowRunService.startRun()
        ↓
WorkflowEngineResult.finalResult["answer"]
        ↓
落库 user/assistant 消息 → 返回 completion 响应
```

**Phase 2（系统变量自动注入）：**

```
RunContext 自动携带系统变量：
  sys.query           = content
  sys.chat_history    = List<{role, content}>   ← 结构化，非字符串
  sys.conversation_id = sessionId
  sys.user            = userId

Start 节点不再需要手动声明 question / history mapping，
LLM 节点直接通过 {{sys.query}}、{{sys.chat_history}} 引用。
```

---

### 3.4 工作流类型区分

Phase 2 引入 `chatflow` 类型，与现有 `workflow` 区分：

| 类型 | 说明 | 触发方式 | 历史感知 |
|------|------|----------|----------|
| `workflow` | 无状态，一次性执行 | API / 定时 | ❌ |
| `chatflow` | 有状态，多轮对话 | `chat-flow/chat/completions` | ✅ 平台自动注入 |

> 编辑器中 `chatflow` 类型工作流的 Start 节点自动展示系统变量区，用户只需配置业务扩展参数。

---

### 3.5 输入输出契约

**Phase 1 约定（用户手动配置）：**

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `question` | `string` | **是** | Start 节点 inputs 中必须声明 |
| `history` | `string` | 否 | JSON 字符串，prompt 中用 `{{history}}` 引用 |

**Phase 2 约定（平台自动注入）：**

| 系统变量 | 类型 | 说明 |
|----------|------|------|
| `sys.query` | `string` | 本轮用户消息，无需声明 |
| `sys.chat_history` | `array` | 结构化历史，无需声明 |
| `sys.conversation_id` | `string` | 会话 ID |

**输出约定（全阶段统一）：**

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `answer` | `string` | `finalResult["answer"]`，chat 取此字段作为回复 |

---

### 3.6 Session 创建 / 编辑 UI

- **Phase 1**：在 chat-flow 前端新增会话管理页（创建/编辑/删除 Session），绑定已发布工作流，可配置固定入参。
- **Phase 2**：创建会话时区分 `workflow` / `chatflow`；`chatflow` 自动隐藏 `question`/`history` 配置项（平台注入）。

## 四、阶段计划

### Phase 1：MVP — chat-flow 内闭环 + 非流式调用
> **目标**：不依赖 `gijela-core-chat`，在 chat-flow 内形成完整会话对话闭环。

| 步骤 | 内容 | 模块 |
|------|------|------|
| P1-1 | 新增 `cf_chatflow_session`、`cf_chatflow_message` 两张表与 mapper/domain/service | chat-flow |
| P1-2 | 新增 chat-flow 对话接口：`/api/v1/chat-flow/chat/completions` | chat-flow |
| P1-3 | 新增 `ChatflowConversationService`，内部调用 `WorkflowRunService.startRun` | chat-flow |
| P1-4 | 新增 Session CRUD 接口（仅 chat-flow） | chat-flow |
| P1-5 | chat-flow 前端新增会话工作台（Session 列表 + 消息窗口） | bloom-chat-flow |
| P1-6 | 端到端验证：在 chat-flow 页面发消息，收到工作流 `answer` 输出 | 测试 |

**验收标准：**
- chat-flow 会话可直接驱动工作流并返回回复。
- 与 `gijela-core-chat` 保持零业务依赖。
- 工作流执行失败有统一降级文案与错误码。

---

### Phase 2：系统变量自动注入 + Chatflow 类型区分
> **目标**：对齐业界体验，用户编排对话工作流时无需手动配置 question/history mapping。

| 步骤 | 内容 | 模块 |
|------|------|------|
| P2-1 | `chat-flow` 引擎扩展 `RunContext`，增加 `sys.*` 系统变量注入机制 | chat-flow |
| P2-2 | 工作流 `appType` 新增 `chatflow`，执行时自动将 `sys.query`、`sys.chat_history` 注入 RunContext | chat-flow |
| P2-3 | 编辑器 Start 节点区分系统变量区（只读展示）和业务参数区（用户配置） | bloom-chat-flow |
| P2-4 | LLM 节点输入 mapping 支持 `source=system`（引用 `sys.*` 变量） | chat-flow |
| P2-5 | `chat_history` 改为结构化传参（List），chat-flow 对话接口直接传结构化历史 | chat-flow |
| P2-6 | 回归测试：Phase 1 链路兼容，新建 chatflow 类型工作流验证系统变量注入 | 测试 |

**验收标准：**
- 新建 `chatflow` 工作流时，Start 节点自动展示 `sys.query`、`sys.chat_history` 等只读系统变量。
- LLM 节点 prompt 中可直接引用 `{{sys.query}}`，无需手动配置 mapping。
- Phase 1 已上线的 `workflow` 类型链路不受影响。

---

### Phase 3：流式输出 + 能力扩展节点
> **目标**：提升对话实时感，扩展工作流编排能力（RAG、工具调用、对话变量）。

| 步骤 | 内容 | 模块 |
|------|------|------|
| P3-1 | chat-flow LLM 节点支持流式调用（SSE 逐 token 推送） | chat-flow |
| P3-2 | chat-flow 新增 `/chat/stream` 或 `/chatflow-runs/stream` 接口，直接 SSE 输出 | chat-flow |
| P3-3 | chat-flow 前端消息窗口适配 SSE（打字机效果） | bloom-chat-flow |
| P3-5 | 工作流新增 **对话变量节点**（ConversationVariable），跨轮次持久化状态 | chat-flow |
| P3-6 | 工作流新增 **知识库检索节点**（RAG Node），接入现有 knowledge 能力 | chat-flow |
| P3-7 | 工作流新增 **工具调用节点**（Tool/MCP Node），接入现有 skill/MCP 能力 | chat-flow |

**验收标准：**
- chatflow 模式对话有逐 token 流式输出效果。
- 对话变量能跨轮次读写。
- RAG 节点能检索知识库并将结果注入 LLM prompt。

## 五、关键问题与调整建议

1. **问题：模块通信超时与降级**
        - 风险：即使改为 chat-flow 内调用，LLM 节点本身仍可能超时。
        - 建议：对 `WorkflowRunService.startRun` 设置统一超时与错误码映射；失败时返回降级文案并记录 error 日志；P3 流式后体验改善。
   - 优先级：P0

2. **问题：工作流版本策略**
   - 风险：Session 绑定后工作流升级，session 是否跟随新版本？
   - 建议：**跟随最新 published_version**，每次执行时动态查 `cf_workflow.published_version`；若需锁版本，由用户在 session 设置中手动指定。
   - 优先级：P1（需拍板）

3. **问题：未发布工作流不可用**
        - 建议：Session 绑定时只允许选 `status=active` 的工作流；工作流被禁用后该 session 标记不可用并提示重新绑定。
   - 优先级：P0

4. **问题：Phase 1 历史为字符串 → Phase 2 为结构化对象，契约升级**
   - 建议：Phase 2 升级时在执行引擎侧做兼容，`source=workflow` 且 key=`history` 时自动将字符串解析为结构化对象，平滑迁移。
   - 优先级：P1

5. **问题：如何保证与 `gijela-core-chat` 零业务耦合**
        - 建议：禁止在 chat-flow 中引用 chat 模块类、表、接口；新能力全部在 chat-flow 重建；通过代码评审与依赖扫描做门禁。
   - 优先级：P0

## 七、默认实现决策（已定）

1. **工作流版本策略**：Session 执行时动态跟随最新 `published_version`（Phase 1 不提供手动锁版本）。
2. **历史透传深度**：Phase 1 固定最近 10 轮历史。
3. **工作流停用策略**：工作流停用后，Session 自动标记不可用并提示重新绑定（不降级到默认模型）。
4. **Phase 2 启动策略**：Phase 1 达到验收标准后启动，不并行推进。
5. **多输出字段策略**：Phase 1 仅消费 `answer`，其余字段仅透传保留，不做前端展示。
6. **Session 中途切换工作流**：允许切换，仅影响新消息，不重置历史。

### 9.1 API 合同（后端/前端统一口径）

#### A. 发送消息

`POST /api/v1/chat-flow/chat/completions`

请求体：

```json
{
        "sessionId": "cfs_202605190001",
        "content": "请总结今天会议内容",
        "requestId": "req_202605190001"
}
```

字段约束：

| 字段 | 类型 | 必填 | 约束 |
|------|------|------|------|
| `sessionId` | string | 是 | 长度 8-64，仅字母/数字/下划线/中划线 |
| `content` | string | 是 | 去首尾空白后长度 1-8000 |
| `requestId` | string | 否 | 幂等键，建议 1-64 |

成功响应：

```json
{
        "code": 0,
        "message": "ok",
        "data": {
                "sessionId": "cfs_202605190001",
                "messageId": "cmsg_202605190002",
                "answer": "这是会议总结...",
                "workflowId": "wf_xxx",
                "runId": "run_xxx",
                "createdAt": "2026-05-19T10:30:00"
        }
}
```

#### B. 会话 CRUD

- `GET /api/v1/chat-flow/chat/sessions?pageNum=1&pageSize=20&keyword=`
- `POST /api/v1/chat-flow/chat/sessions`
- `PUT /api/v1/chat-flow/chat/sessions/{sessionId}`
- `DELETE /api/v1/chat-flow/chat/sessions/{sessionId}`（软删）
- `GET /api/v1/chat-flow/chat/sessions/{sessionId}/messages?pageNum=1&pageSize=50`

会话创建请求体示例：

```json
{
        "title": "运营日报助手",
        "workflowId": "wf_abc123",
        "workflowInputs": {
                "tenant": "default",
                "scene": "daily-report"
        }
}
```

#### C. 错误码（Phase 1 必备）

| 错误码 | 场景 | 前端提示 |
|--------|------|----------|
| `CHATFLOW_SESSION_NOT_FOUND` | 会话不存在/已删除 | 会话不存在，请刷新后重试 |
| `CHATFLOW_WORKFLOW_NOT_ACTIVE` | 绑定工作流未发布/已停用 | 当前会话绑定的工作流不可用，请重新绑定 |
| `CHATFLOW_RUN_TIMEOUT` | 执行超时 | 请求超时，请稍后重试 |
| `CHATFLOW_RUN_FAILED` | 引擎执行失败 | 执行失败，请稍后重试 |
| `CHATFLOW_PARAM_INVALID` | 入参非法 | 请求参数不合法 |

### 9.2 DDL 与索引（含回滚）

建表补充约束：

```sql
ALTER TABLE cf_chatflow_session
        ADD UNIQUE KEY uk_session_id (session_id),
        ADD KEY idx_workflow_status (workflow_id, status, deleted),
        ADD KEY idx_updated_at (updated_at);

ALTER TABLE cf_chatflow_message
        ADD KEY idx_session_created (session_id, created_at),
        ADD KEY idx_session_role_created (session_id, role, created_at);
```

JSON 约束策略：

- `workflow_inputs`、`extra_json` 写入前在服务层做 JSON schema 基础校验（对象类型 + 最大长度）。
- 超限或非法 JSON 统一返回 `CHATFLOW_PARAM_INVALID`。

回滚脚本：

```sql
DROP TABLE IF EXISTS cf_chatflow_message;
DROP TABLE IF EXISTS cf_chatflow_session;
```

### 9.3 超时/重试/降级统一口径

| 项 | 口径 |
|----|------|
| 执行超时 | 60s（与 `chat-flow.engine.timeout-ms` 对齐） |
| 自动重试 | Phase 1 不开启自动重试 |
| 降级响应 | 返回 `CHATFLOW_RUN_TIMEOUT` / `CHATFLOW_RUN_FAILED` + 统一文案 |
| 日志要求 | 记录 `sessionId`、`workflowId`、`runId`、`requestId` |

统一降级文案：

- 超时：`本次请求处理超时，请稍后重试。`
- 失败：`工作流执行失败，请稍后重试。`
