# ARCH-REVIEW-20260518-001：chat-flow 大模型维护（CRUD）能力评审

### 一、可落地性结论
- 结论：有条件可落地
- 依据：
  - 现状中，LLM 节点已存在 `model` 配置位，前端节点配置面板也已有“模型”字段，说明调用链路已具备“按模型名执行”的最小基础。
  - 后端 `LlmNodeExecutor` 当前会优先读取节点配置中的 `model`，否则回退到 `chat-flow.llm.model` 全局配置，具备向“模型注册表”演进的兼容空间。
  - 但目前缺少“模型主数据”层：没有模型表、没有 CRUD 接口、没有启停状态、没有权限菜单、没有运行时解析与缓存策略，不能直接上生产。

### 二、关键问题与调整建议
1. 问题：目标与范围尚未收敛
   - 位置：需求描述 / 范围定义
   - 风险：若“模型维护”同时承担供应商、密钥、路由、计费、租户隔离，会从简单 CRUD 膨胀为“模型网关中心”。
   - 建议：本期收敛为“chat-flow 可选模型注册表”，仅管理：模型编码、展示名称、供应商、目标模型名、状态、默认温度/最大令牌、备注，不承载真实密钥。
   - 优先级：P0

2. 问题：架构边界未明确
   - 位置：模块职责
   - 风险：若把模型维护直接塞进前端静态枚举或 `application-chat-flow.yml`，会形成“配置文件 + 页面并行配置源”，后续难维护。
   - 建议：
     - 后端：在 `gijela-core-chat-flow` 增加模型管理子链路（controller/service/mapper/domain）。
     - 前端：在 `gijela-bloom-chat-flow` 增加“模型维护”页面，并在流程编辑器中改为下拉选择。
     - 不修改 `gijela-core-llm-sdk-*` 公共 SDK，只在 chat-flow 侧做运行时解析。
   - 优先级：P0

3. 问题：协议与数据契约未定义
   - 位置：数据模型 / 请求响应契约
   - 风险：若节点里继续只存自由文本 `model`，后续模型改名、停用、灰度发布都会失控。
   - 建议：
     - 新增模型主数据表，建议字段：
       - `id`
       - `model_key`（业务稳定键，唯一）
       - `display_name`
       - `provider`
       - `target_model`
       - `enabled`
       - `default_temperature`
       - `default_max_tokens`
       - `remark`
       - `created_at/updated_at`
     - 节点配置从 `config.model` 演进为：
       - `config.modelKey`（主用）
       - `config.model`（兼容旧数据，可保留一段时间）
     - 编辑器下拉接口只返回启用模型；管理页列表接口返回全量模型。
   - 优先级：P0

4. 问题：运行时解析与兼容策略缺失
   - 位置：执行链路
   - 风险：直接切到 `modelKey` 会导致历史流程无法运行。
   - 建议：
     - `LlmNodeExecutor` 解析顺序：
       1. `config.modelKey` → 查模型注册表拿 `target_model`
       2. 若无，再回退 `config.model`
       3. 再无则回退 `chat-flow.llm.model`
     - 模型被禁用时：校验阶段直接报错，运行阶段拒绝执行并给出可读提示。
   - 优先级：P0

5. 问题：性能与容量设计未补齐
   - 位置：性能与容量
   - 风险：每个节点执行都查库解析模型，会带来额外数据库压力。
   - 建议：
     - 启用模型列表与 `modelKey -> target_model` 映射做本地缓存；
     - 管理页变更后清缓存或刷新版本号；
     - MVP 阶段可先本地内存缓存，后续再接 Redis。
   - 优先级：P1

6. 问题：安全与合规边界不清
   - 位置：安全与合规
   - 风险：若把供应商密钥直接落在模型 CRUD 表中，会引入明文密钥、审计缺失、环境串用风险。
   - 建议：
     - 本期不在模型表中存真实 API Key；
     - 密钥仍由环境变量/配置中心注入；
     - 模型维护只管理“可选模型元数据”；
     - 新增后台菜单权限与操作审计。
   - 优先级：P0

7. 问题：可测试性与上线门槛未定义
   - 位置：测试与发布
   - 风险：模型 CRUD 上线后若编辑器、校验器、执行器三处不一致，会出现“能选不能跑”或“能跑不能保存”。
   - 建议：最少补齐以下验证：
     - CRUD 单测；
     - 启用/停用状态校验；
     - 编辑器下拉加载；
     - 历史流程兼容回归；
     - 执行链路解析 `modelKey` 回归。
   - 优先级：P1

### 三、最小落地路径（MVP）
- 第一步：后端建立 `LLM 模型注册表` 与 CRUD 接口，仅管理模型元数据，不管理密钥。
- 第二步：前端新增“模型维护”页，并把 LLM 节点中的“模型”改成下拉选择启用模型。
- 第三步：执行器支持 `modelKey -> target_model` 解析，并保留对旧 `config.model` 的兼容回退。

### 四、待拍板决策
1. 模型维护是 `chat-flow` 私有能力，还是未来全仓统一“模型中心”？
2. 节点配置是否立即切换为 `modelKey`，还是保留 `model`/`modelKey` 双写一段时间？
3. 模型表是否允许维护供应商、基础 URL 等扩展字段，还是仅维护目标模型名？
4. 是否需要“默认模型”能力，以及默认模型由系统级还是应用级决定？
5. 是否需要租户/环境隔离（开发、测试、生产模型集合不同）？
