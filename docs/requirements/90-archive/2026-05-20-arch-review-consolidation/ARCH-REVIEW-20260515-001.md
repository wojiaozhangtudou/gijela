# ARCH-REVIEW-20260515-001：chat-flow 前后端新模块规划（Dify 类编排服务）

### 一、可落地性结论
- 结论：可落地（可交由开发实现）
- 依据：
  - 当前仓库已具备 `gijela-core-chat` 与 `gijela-bloom-chat`，可继续承担“调试工作台”定位，复用模型调用、知识检索、附件、MCP 等基础能力。
  - `gijela-core-chat-flow` / `gijela-bloom-chat-flow` 应明确作为“企业级流程编排应用”独立模块建设，与调试工作台解耦。
  - 需求范围已明确为“全功能 P0 一次性上线”，并补充了接口、数据表、错误码、Schema、测试矩阵与上线清单，具备工程实施输入。
  - 可按“流程定义 + 执行调试 + 发布运行”分层并行开发，并通过 B1~B5 批次推进控制交付风险。

### 二、关键问题与调整建议
1. 问题：`chat-flow` 与现有 `chat` 模块存在功能重叠（已确认可接受）
   - 位置：模块规划 / 1. 模块命名与职责
   - 风险：若不区分“调试链路”和“企业链路”的权限、入口、数据隔离，会造成发布能力误用到调试环境，或调试数据污染企业运行数据。
   - 建议：明确边界：
     - `gijela-core-chat`：定位为调试工作台后端，保留会话、消息、附件、知识、模型调用、联调验证基础能力
     - `gijela-core-chat-flow`：定位为企业级编排应用后端，仅负责流程定义、节点编排、执行编排、运行记录、发布管理
     - `gijela-bloom-chat`：定位为调试工作台前端
     - `gijela-bloom-chat-flow`：定位为企业级编排应用前端，仅负责流程编辑器、运行调试页、流程管理页
     - 允许能力重叠，但必须满足：菜单分组独立、权限点独立、运行数据独立（调试与生产隔离）。
   - 优先级：P0

2. 问题：缺少统一流程 DSL（前端画布结构与后端执行结构尚未定义）
   - 位置：协议与数据契约 / 2. 流程定义模型
   - 风险：若前端直接把 Vue Flow 图数据当后端执行数据，后续节点扩展、版本迁移、执行回放会非常难维护。
   - 建议：先定义独立 `WorkflowDefinition` 协议，至少包含：
     - 基础信息：`id`、`code`、`name`、`status`、`version`
     - 节点：`id`、`type`、`position`、`config`、`inputs`、`outputs`
     - 连线：`id`、`sourceNodeId`、`targetNodeId`、`condition`
     - 运行配置：超时、重试、并发、变量作用域
     - 发布信息：草稿版 / 发布版 / 回滚信息
   - 优先级：P0

3. 问题：功能点容易一次性铺太大
   - 位置：目标与范围 / 3. 首期功能范围
   - 风险：把 Dify 全量能力一次性拉齐，会同时引入节点系统、变量系统、发布系统、运行系统、监控系统，延期概率高。
   - 建议：首期只做以下功能点：
     - 流程列表：新建、复制、删除、草稿保存
     - 流程编辑器：拖拽节点、连线、节点配置、保存草稿
  - 节点类型：开始、结束、LLM、知识检索、KAG 图数据查询、条件分支、HTTP 调用
     - 调试运行：单次试跑、节点级输入输出、错误展示
     - 发布运行：发布版本、按版本执行、运行记录查询
     - 权限菜单：流程查看 / 编辑 / 发布 / 调试 四类权限
    - 实施方式：全功能纳入 P0，同期按 B1~B5 批次交付
   - 优先级：P0
  - 决策更新（2026-05-15）：按业务要求改为“全功能 P0 一次性上线”，原分期后置项取消。

4. 问题：执行模型未定，难以评估性能与稳定性
   - 位置：性能与容量 / 4. 执行引擎方案
   - 风险：如果同步执行、异步执行、流式输出、节点重试没有统一模型，后端会频繁返工。
   - 建议：先拍板执行语义：
     - 首期采用“单次请求触发 + 服务端顺序执行 + 节点级运行日志落库”
     - LLM 节点支持流式输出，但流程级先不做全链路流式编排
     - 运行记录拆为：流程运行主表 + 节点运行明细表
     - 重试仅支持节点级固定次数重试，不做全图恢复
   - 优先级：P0

5. 问题：缺少可观测性约束，后续调试成本会很高
   - 位置：稳定性 / 5. 运行日志与回放
   - 风险：编排系统没有节点级日志、耗时、输入输出快照，线上无法定位问题。
   - 建议：首期必须内置：
     - 节点状态：pending / running / success / failed / skipped
     - 节点耗时、错误信息、输入输出摘要
     - 发布版本号与运行实例绑定
     - 调试运行与正式运行分开存储
  - 优先级：P0

6. 问题：测试与上线门槛未定义
   - 位置：可测试性与上线门槛 / 7. 验收策略
   - 风险：没有标准验收用例，前后端对“可用”定义不一致。
   - 建议：首期验收至少覆盖：
     - 画布保存 / 回显一致
     - 非法流程校验（孤立节点、缺失开始节点、分支未闭合）
     - 单条成功执行链路
     - 节点失败中断与错误提示
     - 发布版本后按版本执行
     - 权限隔离与菜单可见性
  - 优先级：P0

### 三、最小落地路径（执行顺序）
- 第一步：确定模块边界与 DSL
  - 输出 `chat-flow` 模块职责说明、流程 JSON 协议、节点类型清单。
- 第二步：完成基础编辑器与草稿保存
  - 前端完成流程列表、画布编辑、右侧节点配置；后端完成流程定义保存/查询接口。
- 第三步：完成调试执行与运行记录
  - 支持开始/LLM/知识检索/KAG 图数据查询/条件/结束节点，落库节点运行明细，前端可查看节点级结果。
- 第四步：补发布与权限
  - 支持草稿发布、版本执行、流程管理菜单与权限点。

### 四、待拍板决策
1. 已确认：模块拆分确定为 `gijela-core-chat` / `gijela-bloom-chat`（调试工作台） 与 `gijela-core-chat-flow` / `gijela-bloom-chat-flow`（企业级编排应用），功能重叠为有意设计。
2. 已确认：首期画布选型采用 `Vue Flow`，暂不采用 `AntV X6` / `LogicFlow`。
3. 已确认：首期节点范围按全量上线，包含开始、结束、LLM、知识检索、KAG 图数据查询、条件、HTTP、tool、skill、mcp-tool、agent、code、loop、answer、variable-aggregator、template-transform、variable-assigner。
4. 已确认：子流程、循环、并行网关、多人协同、模板能力同步纳入 P0。
5. 已确认：运行引擎采用“顺序执行 + 节点级日志落库 + 发布版执行”。
6. 当前无阻塞性待拍板项，可直接进入开发实施。

### 七、P0 接口清单（后端草案）

#### 1）流程定义管理
- `GET /api/v1/chat-flow/workflows`
  - 分页查询流程（按名称、状态、创建人过滤）
- `POST /api/v1/chat-flow/workflows`
  - 新建流程（默认草稿）
- `GET /api/v1/chat-flow/workflows/{workflowId}`
  - 查询流程详情（含最新草稿定义）
- `PUT /api/v1/chat-flow/workflows/{workflowId}`
  - 更新流程基础信息（名称、描述、标签）
- `DELETE /api/v1/chat-flow/workflows/{workflowId}`
  - 删除流程（软删除）

#### 2）流程画布与草稿
- `PUT /api/v1/chat-flow/workflows/{workflowId}/draft`

  - 读取草稿定义

- `POST /api/v1/chat-flow/workflows/{workflowId}/debug-runs`

- `POST /api/v1/chat-flow/workflows/{workflowId}/publish`
  - 发布草稿生成新版本

  - 按发布版本执行
- `GET /api/v1/chat-flow/workflows/{workflowId}/runs`
  - 查询正式运行历史
- `GET /api/v1/chat-flow/runs/{runId}`
  - 查询正式运行详情（节点级明细）

- 所有接口统一走 `ApiResponse`

### 十一、Dify 节点能力对齐策略（chat-flow 路线图）

#### 1）应用形态差异（必须先定）
- `Workflow`：面向自动化任务流，必须有 `start` 与 `end`。
- `Chatflow`：面向多轮对话流，支持 `answer` 节点，`end` 节点可选或不暴露。
- 结论：`chat-flow` 需在流程元数据增加 `appType`（`workflow` / `chatflow`），节点可用性按 `appType` 控制。

#### 2）节点分级接入（避免一次性铺满）

##### P0（一次性接入）
- 基础与流程控制：`start`、`end`、`if-else`
- 核心 AI：`llm`、`knowledge-retrieval`、`kag-graph-query`
- 数据处理：`http-request`
- 基础与流程控制：`answer`、`variable-aggregator`、`loop`
- 数据与逻辑处理：`template-transform`、`variable-assigner`、`code`
- 外部集成：`tool`、`skill`、`mcp-tool`
- 高级能力：`agent`

### 十二、P0 节点契约清单（输入/输出/配置）

#### 0）统一执行上下文约定（所有节点通用）
- `runContext`
  - `runId`: string
  - `workflowId`: string
  - `workflowVersion`: number
  - `appType`: `workflow` | `chatflow`
  - `variables`: object（运行时变量池）
  - `metadata`: object（requestId、operator、traceId）
- 节点通用返回结构：
  - `status`: `success` | `failed` | `skipped`
  - `outputs`: object
  - `error`: `{ code: string, message: string } | null`
  - `metrics`: `{ durationMs: number, tokenUsage?: object }`

#### 1）`start` 节点（起点）
- 作用：接收外部触发输入，初始化变量。
- `configSchema`：
  - `inputDefs`: `[{ name, type, required, defaultValue? }]`
- `inputSchema`：无上游输入（由触发入口注入）
- `outputSchema`：
  - `inputs`: object（标准化后的入口参数）

#### 2）`end` 节点（终点，仅 workflow 强制）
- 作用：声明最终输出变量。
- `configSchema`：
  - `returnMappings`: `[{ key, fromExpr }]`
- `inputSchema`：任意上游变量
- `outputSchema`：
  - `finalResult`: object（对外返回）

#### 3）`llm` 节点（大模型）
- 作用：执行文本生成、总结、分类等任务。
- `configSchema`：
  - `model`: string
  - `systemPrompt`: string
  - `userPromptTemplate`: string
  - `temperature`: number
  - `maxTokens`: number
  - `stream`: boolean（P0 节点内可流式，流程级先非流式编排）
  - `outputMode`: `text` | `json`
- `inputSchema`：
  - `promptVars`: object（用于模板渲染）
- `outputSchema`：
  - `text`: string
  - `json`: object（当 `outputMode=json`）
  - `usage`: `{ promptTokens, completionTokens, totalTokens }`

#### 4）`knowledge-retrieval` 节点（知识检索）
- 作用：从知识库检索上下文片段。
- `configSchema`：
  - `datasetIds`: string[]
  - `topK`: number
  - `scoreThreshold`: number
  - `searchMode`: `semantic` | `hybrid`
- `inputSchema`：
  - `query`: string
- `outputSchema`：
  - `documents`: `[{ id, title, score, content, metadata }]`
  - `contextText`: string（拼接后上下文）

#### 4.1）`kag-graph-query` 节点（KAG 图数据查询）
- 作用：面向图谱进行实体、关系、路径查询，提供结构化图上下文。
- `configSchema`：
  - `graphSpace`: string
  - `queryMode`: `entity` | `relation` | `path`
  - `topK`: number
  - `maxHops`: number
  - `filters`: object
- `inputSchema`：
  - `query`: string
  - `seedEntities?`: string[]
- `outputSchema`：
  - `entities`: `[{ id, name, type, properties }]`
  - `relations`: `[{ source, target, type, properties }]`
  - `paths`: `[{ nodes, edges, score }]`
  - `summary`: string

#### 5）`if-else` 节点（条件分支）
- 作用：根据表达式路由到不同分支。
- `configSchema`：
  - `conditions`: `[{ branchKey, expression }]`
  - `defaultBranch`: string
- `inputSchema`：
  - `variables`: object
- `outputSchema`：
  - `branch`: string
  - `passed`: boolean

#### 6）`http-request` 节点（外部请求）
- 作用：调用外部 API。
- `configSchema`：
  - `method`: `GET` | `POST` | `PUT` | `DELETE`
  - `urlTemplate`: string
  - `headersTemplate`: object
  - `queryTemplate`: object
  - `bodyTemplate`: object|string
  - `timeoutMs`: number
- `inputSchema`：
  - `requestVars`: object
- `outputSchema`：
  - `statusCode`: number
  - `headers`: object
  - `body`: object|string

### 十三、节点校验规则（P0 必须）
1. 图结构校验
   - 必须且仅有一个 `start`。
   - `workflow` 必须至少一个 `end`；`chatflow` 可无 `end`。
  - 禁止孤立节点；若启用 `loop`，需满足循环终止约束。
2. 节点配置校验
   - 每个节点必须通过 `configSchema` 必填项校验。
   - 表达式字段（如 `if-else.expression`）在保存前做语法校验。
3. 发布校验
  - 未通过结构/配置校验的流程禁止发布。

### 二十一、WorkflowDefinition JSON Schema v1（正式稿）

#### 1）结构定义（概览）
```json
{
  "appType": "workflow",
  "nodes": [],
  "edges": [],
  "runtimeConfig": {
    "timeoutMs": 60000,
    "maxRetry": 0,
    "concurrency": 1
  },
  "meta": {
    "name": "流程名称",
    "description": "说明",
    "tags": ["demo"]
  }
}
```

#### 2）字段约束
- `appType`：必填，`workflow` | `chatflow`
- `nodes`：必填，数组长度 >= 1
- `edges`：必填，数组长度 >= 0
- `runtimeConfig.timeoutMs`：可选，默认 60000，范围 [1000, 300000]
- `runtimeConfig.maxRetry`：可选，默认 0，范围 [0, 5]
- `runtimeConfig.concurrency`：可选，默认 1，范围 [1, 10]

#### 3）Node 定义
```json
{
  "id": "n_llm_1",
  "type": "llm",
  "position": { "x": 380, "y": 180 },
  "config": {},
  "inputs": {},
  "outputs": {}
}
```

字段约束：
- `id`：必填，唯一，正则 `^[a-zA-Z][a-zA-Z0-9_-]{2,63}$`
- `type`：必填，枚举：
  - `start`
  - `end`
  - `llm`
  - `knowledge-retrieval`
  - `kag-graph-query`
  - `if-else`
  - `http-request`
  - `answer`
  - `variable-aggregator`
  - `template-transform`
  - `variable-assigner`
  - `tool`
  - `skill`
  - `mcp-tool`
  - `agent`
  - `code`
  - `loop`
- `position`：必填，`x`/`y` 为 number
- `config`：必填，object（按节点类型校验）

#### 4）Edge 定义
```json
{
  "id": "e_start_llm",
  "sourceNodeId": "n_start_1",
  "targetNodeId": "n_llm_1",
  "condition": null
}
```

字段约束：
- `id`：必填，唯一
- `sourceNodeId`：必填，必须存在于 `nodes.id`
- `targetNodeId`：必填，必须存在于 `nodes.id`
- `condition`：可选（用于分支边）

#### 5）图级校验规则
1. 必须且仅有一个 `start`
2. 当 `appType=workflow` 时，至少一个 `end`
3. 节点 ID、边 ID 全局唯一
4. 禁止孤立节点（除 `start` 外每个节点至少有一条入边）
5. 若存在循环（`loop`），必须声明 `maxIterations`（建议范围 1~100，默认 10）且具备可判定终止条件
