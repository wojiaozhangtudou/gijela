| 字段 | 说明 |
|------|------|
| `run_id` | 关联执行记录 |

### 2.5 `cf_llm_model` — LLM 模型注册表

| 字段 | 说明 |
|------|------|

| `provider` | 供应商（如 `openai`、`aliyun`） |
| `base_url` | API 基础 URL |

## 四、执行引擎架构

### 4.1 核心组件

```
WorkflowRunService
  └── startDebugRun()   → async (taskExecutor) → WorkflowRunServiceImpl.executeAsync()
  └── startRun()        → sync               → WorkflowRunServiceImpl.executeSync()
        ↓
  WorkflowEngine.execute(definition, inputs, onNodeRecord)
        ↓
  [图遍历：start → 逐条 edge → end]
        ↓
  NodeExecutorRegistry.getExecutor(nodeType)
        ↓
  NodeExecutor.execute(node, runContext)
        ↓  (callback)
  onNodeRecord.accept(NodeExecutionRecord)  → 实时写入 cf_workflow_run_node
```

### 4.2 WorkflowEngine 执行流程

1. 从 `definition.nodes` 中找到 `type=start` 的节点作为入口。
2. 循环：通过 `definition.edges`（`sourceNodeId → targetNodeId`）查找当前节点的下一个节点。
3. 对每个节点：
   - 构建 `inputs`：根据 `node.data.inputs` 中的 `mapping`，从 `RunContext` 中解析来源（`workflow` / `previous` / `constant`）。
   - 调用对应 `NodeExecutor.execute()`。
   - 将执行结果写入 `RunContext`，触发 `onNodeRecord` 回调实时落盘。
4. 遇到 `type=end` 节点时终止，返回 `WorkflowEngineResult`。

### 4.3 LlmNodeExecutor 执行逻辑

1. 从节点 config 读取 `modelKey`（优先）或 `model`（兼容旧数据）。
2. 通过 `LlmModelMapper` 按 `model_key` 查询 `cf_llm_model`（`enabled=1` 且未删除）。
3. 读取 `system_prompt`、`user_prompt_template`、`temperature`、`max_tokens`。
4. 用 `inputs` map 替换 prompt 中的 `{{varName}}` 模板占位符（正则 `\{\{\s*([a-zA-Z0-9_.-]+)\s*\}\}`）。
5. 调用 LLM SDK，返回 `NodeExecuteResult`（含 `answer` 字段）。

### 4.4 RunContext 输入来源映射

| mapping.source | 取值方式 |
|----------------|----------|
| `workflow` | 从工作流启动时传入的 `inputs` map |
| `previous` | 从上一个节点的 `output_snapshot`（`answer` 字段）取值 |
| `constant` | 直接使用 mapping 中的 `value` 字段 |

## 五、异步执行模型

```
HTTP POST /debug-runs
    ↓
创建 cf_workflow_run (status=running)
    ↓ 立即返回 { runId }
    ↓
CompletableFuture.runAsync(engine::execute, taskExecutor)
    ↓
节点执行 → onNodeRecord 回调 → INSERT cf_workflow_run_node（实时）
    ↓
完成 → UPDATE cf_workflow_run (status=success/failed)

前端轮询: GET /debug-runs/{runId}（含最新节点记录列表）
```

## 六、工作流 definition JSON 结构

```json
{
  "nodes": [
    {
      "id": "start-1",
      "type": "start",
      "data": {
        "label": "开始",
        "inputs": [
          { "name": "question", "type": "string", "required": true }
        ]
      }
    },
    {
      "id": "llm-1",
      "type": "llm",
      "data": {
        "label": "LLM节点",
        "config": {
          "modelKey": "qwen-plus-online",
          "systemPrompt": "你是一个助手",
          "userPromptTemplate": "{{question}}",
          "temperature": 0.7,
          "maxTokens": 2048
        },
        "inputs": [
          {
            "name": "question",
            "mapping": { "source": "workflow", "key": "question" }
          }
        ]
      }
    },
    {
      "id": "end-1",
      "type": "end",
      "data": { "label": "结束" }
    }
  ],
  "edges": [
    { "id": "e1", "source": "start-1", "target": "llm-1" },
    { "id": "e2", "source": "llm-1",   "target": "end-1"  }
  ],
  "application": {
    "debugInputs": { "question": "你好" }
  }
}
```

> `application.debugInputs` 由前端维护，用于保存调试面板的入参草稿，不影响正式执行。

## 八、配置项说明（application.yml / application-dev.yml）

```yaml
server:
  port: 9010

chat-flow:
  engine:
    timeout-ms: 60000     # 单次执行最大超时（毫秒）
    max-retry: 0          # 当前版本不支持重试
    concurrency: 1        # 并发执行数量限制
```

LLM API Key、baseUrl 等敏感配置在 `cf_llm_model` 表中管理，通过模型注册表在运行时加载，**不建议**在 `application.yml` 中明文维护。

## 九、已知限制与后续优化点

| 编号 | 类别 | 描述 | 优先级 |
|------|------|------|--------|
| L-01 | 节点类型 | 当前仅支持 `start` / `llm` / `end` 三种节点类型，不支持分支、条件、循环 | P1 |
| L-02 | 并发 | `concurrency=1`，不支持并行节点分支 | P1 |
| L-03 | 重试 | `max-retry=0`，节点失败不会自动重试 | P2 |
| L-04 | 模型缓存 | `LlmNodeExecutor` 每次执行都查询 DB，高频调用建议加本地缓存 | P2 |
| L-05 | API Key 安全 | `cf_llm_model.api_key` 明文存储，需评估是否接入密钥管理服务 | P0 |
| L-06 | 输入校验 | `validate` 接口仅检查 `start`/`end` 节点存在性，未校验输入类型/必填项 | P2 |
| L-07 | 执行超时 | `timeout-ms` 配置存在但当前执行链路未强制中断，LLM 调用可能超时 | P1 |
