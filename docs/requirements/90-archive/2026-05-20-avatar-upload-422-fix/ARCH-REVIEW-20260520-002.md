# ARCH-REVIEW-20260520-002：gijela-core-pistil 用户头像上传 422 问题评审

### 一、可落地性结论
- 结论：可落地。
- 依据：
  - 问题链路明确：前端上传头像时提交 Base64，后端对 `avatarBase64` 长度限制为 `<=60000`，超过即触发 422（参数校验失败）。
  - 不涉及跨模块重构，优先在前端上传链路做“压缩+兜底”，可与现有 `/api/v1/users/avatar`、`ApiResponse`、`ErrorCode` 保持兼容。

### 二、关键问题与调整建议
1. 问题：上传原图直接转 Base64，容易超过后端长度限制。
   - 位置：二、条目1（请求体 `avatarBase64`）
   - 风险：频繁出现 422，用户无法完成头像更新。
   - 建议：前端上传时先压缩（缩边长 + JPEG 质量递减），压缩后再提交；仍超限时前端直接拦截提示。
   - 优先级：P0

2. 问题：失败提示语义不清晰，用户不知道是“文件过大”。
   - 位置：二、条目2（错误反馈）
   - 风险：重复重试导致体验差、问题难定位。
   - 建议：在前端加入超限明确提示“头像文件过大，请选择更小的图片后重试”。
   - 优先级：P1

3. 问题：头像大小策略未形成统一口径。
   - 位置：二、条目3（契约说明）
   - 风险：后端限制与前端行为不一致，后续联调反复。
   - 建议：在接口契约中固定头像长度上限（当前 60000）并要求前端上传前压缩。
   - 优先级：P2

### 三、最小落地路径（MVP）
- 第一步：前端 `Profile` 页面接入上传压缩逻辑并保持请求契约不变。
- 第二步：增加长度兜底与明确错误提示，阻断必然失败请求。
- 第三步：联调验证 `/api/v1/users/avatar` 上传、读取、页面回显完整闭环。

### 四、待拍板决策
1. 头像长度上限是否继续保持 `60000`，还是提升到更高阈值（如 200000）？
2. 后续是否统一改为“对象存储 URL”方案，避免 Base64 入库体积问题？
