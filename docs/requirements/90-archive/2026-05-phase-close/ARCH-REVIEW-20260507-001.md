# ARCH-REVIEW-20260507-001

## 需求基线（用于条目引用）
- 第1章 条目1.1：目标是“整体规划 LLM 日志输出”，覆盖同步、流式、工具调用、附件、提示词、会话。
- 第1章 条目1.2：日志要支持问题排查、性能观测、审计追溯。
- 第2章 条目2.1：默认不泄露敏感数据（用户隐私、密钥、令牌、附件原文）。
- 第2章 条目2.2：日志应支持检索、聚合、告警与留存策略。

## 一、可落地性结论
- 结论：有条件可落地。
- 依据：
  - 现有 chat 模块已具备统一入口（编排层 + 控制器 + 审计链路），可挂接结构化日志与 TraceId。
  - 关键前置是“日志分级模型、脱敏策略、采样与留存”需先冻结；否则容易出现日志噪音、成本失控、合规风险。

## 二、关键问题与调整建议
1. 问题：目标与范围未分层，运行日志与审计日志边界不清。
   - 位置：第1章 条目1.1/1.2
   - 风险：同一事件多处重复记录，排障时口径不一致。
   - 建议：按三层模型统一：
     - `access`（请求级）
     - `runtime`（编排与工具执行）
     - `audit`（可追责操作）
     并要求每层统一字段：`traceId`、`sessionId`、`turnId`、`tenantId`、`modelRoute`、`status`、`latencyMs`。
   - 优先级：P0

2. 问题：架构边界未定义“谁负责打点”。
   - 位置：第1章 条目1.1
   - 风险：控制器、Service、客户端重复埋点，维护成本高。
   - 建议：
     - 控制器只记 access。
     - `ChatOrchestratorService` 记 runtime 主事件（模型请求、工具阶段、流式生命周期）。
     - 各 Skill 仅记 skill 子事件，不直接写 access/audit。
     - 使用统一 `LlmLogEventPublisher` 出口，禁止散写 `logger.info` 业务 JSON。
   - 优先级：P0

3. 问题：协议与数据契约缺少标准事件模型。
   - 位置：第2章 条目2.2
   - 风险：后续接 ELK/Loki/ClickHouse 时字段不可聚合。
   - 建议：冻结事件契约（建议 JSON 行日志）：
     - 公共字段：`eventType`、`eventTime`、`traceId`、`spanId`、`sessionId`、`messageId`、`tenantId`、`appCode`。
     - 模型字段：`provider`、`model`、`promptTokens`、`completionTokens`、`totalTokens`、`firstTokenMs`、`finishReason`。
     - 工具字段：`toolName`、`toolCallId`、`toolStatus`、`toolLatencyMs`。
     - 错误字段：`errorCode`、`errorType`、`retryable`。
   - 优先级：P0

4. 问题：性能与容量策略缺失（尤其流式高频事件）。
   - 位置：第1章 条目1.2
   - 风险：QPS 上升后 IO 放大，影响主链路时延。
   - 建议：
     - 流式 token 级日志默认关闭，仅记录 `stream.start` / `stream.first_token` / `stream.done`。
     - `runtime.debug` 采用按会话或按 trace 采样开关（默认 1%）。
     - 大字段（prompt/content/tool result）只保留摘要：`sha256` + `length` + `preview(128)`。
   - 优先级：P0

5. 问题：稳定性策略未覆盖日志通道故障。
   - 位置：第2章 条目2.2
   - 风险：日志后端抖动反向拖慢业务线程。
   - 建议：
     - 业务线程异步投递日志（队列 + 批量 flush）。
     - 队列满时降级：丢弃 debug，保留 error/audit。
     - 明确重试上限和熔断窗口（例如 3 次失败后 60s 半开）。
   - 优先级：P1

6. 问题：安全与合规条目不够可执行。
   - 位置：第2章 条目2.1
   - 风险：泄露密钥、手机号、身份证、附件原文，产生合规事故。
   - 建议：
     - 落地脱敏规则库（正则 + 字段级白名单）。
     - 默认屏蔽：`Authorization`、`apiKey`、`cookie`、附件正文、完整 prompt 原文。
     - 审计日志与运行日志分索引，留存分级：error/audit 180 天，runtime 30 天。
   - 优先级：P0

7. 问题：可测试性与上线门槛未定义。
   - 位置：第1章 条目1.2
   - 风险：上线后难以验证“该有的日志都在、敏感字段已脱敏”。
   - 建议：设置上线闸门：
     - 契约测试：事件字段完整性与类型。
     - 脱敏测试：敏感样本回归（密钥/手机号/身份证）。
     - 压测：目标 QPS 下日志开关开启时 P95 增幅 < 5%。
     - 演练：日志后端不可用时业务成功率不低于基线 99%。
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：冻结日志事件字典与字段契约（`access/runtime/audit` + 必填字段 + 错误码映射）。
- 第二步：在编排主链路接入统一日志发布器，先打 8 个核心事件：`chat.request`、`model.request`、`model.response`、`stream.start`、`stream.first_token`、`stream.done`、`tool.invoke`、`chat.finish`。
- 第三步：接入脱敏与采样，再补告警规则（错误率、超时率、首 token 延迟）后灰度上线。

## 四、待拍板决策
1. 日志后端选型：ELK/Loki/ClickHouse（三选一）及是否双写。
2. Prompt/附件原文是否允许“受控留痕”（仅审计域、仅白名单租户）。
3. 流式日志采样粒度：按租户、按模型路由、按会话还是按 trace。
4. 统一 Trace 方案：沿用现有 requestId 还是全面切 OpenTelemetry TraceId。
