# ARCH-REVIEW-20260507-003

## 需求基线（用于条目引用）
- 第1章 条目1.1：日志存储固定 Elasticsearch（ES）。
- 第1章 条目1.2：必须有日志聚合看板。
- 第1章 条目1.3：明确要求“不依赖 Kibana”。
- 第2章 条目2.1：延续 access/runtime/audit 分层与脱敏要求。

## 一、可落地性结论
- 结论：可落地。
- 依据：
  - ES 仅作为存储与检索引擎，不绑定 Kibana 仍可通过后端聚合 API + 自研前端看板实现完整闭环。
  - 现有仓库已具备后端 Spring Boot 与前端 Vue3 管理端能力，适合落地“内建日志平台页”。

## 二、关键问题与调整建议
1. 问题：现有方案把可视化能力默认绑定 Kibana。
   - 位置：第1章 条目1.3
   - 风险：部署与权限体系受制于外部组件，产品化一致性弱。
   - 建议：采用“ES + 自研看板”架构：
     - 后端新增 `log-observability` 模块（或 chat 内子域）提供聚合查询接口。
     - 前端在管理台新增“LLM 日志看板”页面。
     - ES 只暴露给后端服务，不直接暴露给前端。
   - 优先级：P0

2. 问题：缺少统一查询契约，前端难复用。
   - 位置：第2章 条目2.1
   - 风险：每张图一个接口，维护成本高。
   - 建议：统一查询 API 契约：
     - `POST /api/v1/llm-logs/query/timeseries`
     - `POST /api/v1/llm-logs/query/topn`
     - `POST /api/v1/llm-logs/query/distribution`
     - `POST /api/v1/llm-logs/query/trace/{traceId}`
     请求统一支持：时间范围、租户、模型路由、状态、错误码、会话、分页。
   - 优先级：P0

3. 问题：看板角色差异未固化，容易做成“大杂烩”。
   - 位置：第1章 条目1.2
   - 风险：可读性差，排障效率低。
   - 建议：自研看板按三视图拆分：
     - `SRE 总览`：QPS、错误率、P95、首 token 延迟、ES 写入失败率。
     - `研发排障`：trace 时间线、tool 调用链、错误码分布、慢请求 TopN。
     - `审计视图`：按租户/操作人/模型路由检索，展示脱敏事件轨迹。
   - 优先级：P0

4. 问题：如果前端直接拼 ES DSL，会引入安全与维护风险。
   - 位置：第2章 条目2.1
   - 风险：DSL 注入、权限绕过、字段泄露。
   - 建议：
     - 前端仅传业务过滤条件；DSL 由后端模板化生成。
     - 后端加字段白名单与租户隔离拦截。
     - 所有“原文类字段”默认不返回，仅返回摘要字段。
   - 优先级：P0

5. 问题：不依赖 Kibana 后，告警通道需独立建设。
   - 位置：第1章 条目1.2
   - 风险：只能看图不能告警。
   - 建议：
     - 后端定时任务按 1/5/10 分钟窗口执行聚合规则。
     - 告警结果写入 `llm_alert_event`（MySQL）并推送企业微信/钉钉。
     - P0 告警：错误率、P95、首 token 延迟、工具失败率、ES 写入失败率。
   - 优先级：P1

6. 问题：容量与成本治理仍需 ES 侧策略，不因去 Kibana 而减少。
   - 位置：第2章 条目2.1
   - 风险：热分片膨胀导致查询超时。
   - 建议：保持 ILM + 模板治理：
     - runtime：30 天；audit：180 天。
     - rollover：1 天或 30GB 主分片。
     - 字段 `dynamic: false`，新增字段走评审。
   - 优先级：P1

7. 问题：可测试性与上线门槛未重定义（去 Kibana 后）。
   - 位置：第1章 条目1.3
   - 风险：上线后页面有图但数据不准。
   - 建议：增加验收门槛：
     - 同一查询条件下，自研 API 与 ES 基准查询误差 < 1%。
     - `traceId` 下钻可串起完整会话链路（>=99%）。
     - 脱敏抽检 100 条命中率 100%。
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：冻结“ES 字段字典 + 聚合 API 契约 + 权限模型”。
- 第二步：实现 4 个查询 API（时序/TopN/分布/Trace）并在管理台落首版总览页。
- 第三步：补研发排障页、审计页与告警中心，完成灰度上线。

## 四、待拍板决策
1. 自研看板放在现有管理台（推荐）还是独立前端应用。
2. 告警渠道优先级（企业微信、钉钉、邮件）与值班路由。
3. Trace 规范：沿用现有 requestId 还是切换 OTel TraceId。
4. 聚合 API 是否需要导出能力（CSV/离线报表）。
