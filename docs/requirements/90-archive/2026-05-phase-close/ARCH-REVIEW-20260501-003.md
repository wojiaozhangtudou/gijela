## 二、决策清单（全部已拍）

| # | 决策项 | 拍板结果 | 原因 |
|---|---|---|---|
| **D1** | SDK 模块命名 | `gijela-core-llm-sdk-skill` / `gijela-core-llm-sdk-mcp` | 与现有 `sdk-core` / `sdk-openai-compatible` / `sdk-observability` / `sdk-plugin` 对齐 |
| **D2** | Java 包前缀 | `com.gijela.morpheus.llm.sdk.skill` / `com.gijela.morpheus.llm.sdk.mcp` | 与 `com.gijela.morpheus.llm.sdk.core` 对齐 |
| **D3** | yml 配置前缀 | `gijela.llm.skill.*` / `gijela.llm.mcp.*` | **不再保留 `chat.skills.*` / `chat.mcp.*`**，干净的 SDK 命名空间 |
| **D4** | 业务专属 provider 归属 | `KnowledgeSearchSkillProvider` / `AttachmentContextSkillProvider` 留 chat | 它们依赖 chat 的 RAG 网关与 attachment mapper，纯业务实现 |
| **D5** | `@Scheduled` 同步兜底 | sdk-mcp 提供 `gijela.llm.mcp.sync-cron`，默认空 = 不开 | 给业务方留兜底口子，不强制 |
| **D6** | 拆分时机 | **现在拆**（在工程小、测试覆盖足时一次到位） | 越晚拆迁移面越大 |
| **D7** | sdk-skill / sdk-mcp 是否提供 Spring Boot AutoConfiguration | **是**，使用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` | Spring Boot 3 标准方式 |
| **D8** | sdk-mcp → sdk-skill 依赖方向 | sdk-mcp **单向依赖** sdk-skill | 桥接器 `McpToolSkillProvider` 自然归属 sdk-mcp |
| **D9** | 配置类合并/拆开 | **拆开**：`SkillSdkProperties` / `McpSdkProperties` 各自独立 | SDK 边界清晰 |
| **D10** | `TokenCipher` 归属 | 留 chat | sdk-mcp 只接收明文 bearerToken |
| **D11** | `McpToolBindingSource` 接口位置 | sdk-mcp 内 | chat 实现该接口（`MyBatisMcpServerService implements McpToolBindingSource`） |
| **D12** | 测试如何分配 | 谁实现谁测：sdk-skill 测自己；sdk-mcp 测自己；chat 留 mapper / controller / 业务 provider 测试 | 与生产代码同位 |
| **D13** | `ChatModuleProperties.Skills` / `.Mcp` 内嵌类 | **删除** | 配置全部下沉到 SDK |
| **D14** | `SkillRegistry` 默认内置 | **零内置**（连 time.now / echo 也不预注册） | 真正的 SDK，业务方按需 register |
| **D15** | 业务 provider 注册方式 | chat 在 `ChatModuleConfig` 显式 `register(...)`；本地包通过 sdk-skill 的 `LocalSkillPackageLoader` 自动加载 | 显式优于隐式 |
| **D16** | DB schema 是否调整 | **不动**。`chat_mcp_server` / `chat_skill_state` 是业务表 | SDK 不感知持久化 |

## 四、最小落地路径（4 阶段）

### 阶段 1 — 内部解耦（0.5 天）
**目标**：让搬迁前的代码在原地就先满足"SDK 化"约束，避免在搬迁过程中同时改逻辑。

1. `SkillRegistry` 构造函数签名从 `(McpGateway, ChatAttachmentMapper, ChatModuleProperties, AutowireCapableBeanFactory)` 改为 `(SkillSdkProperties, AutowireCapableBeanFactory)`；删除内置 4 个 `register`。
2. `SkillRegistry.register(SkillProvider)` 改为 public。
3. `ChatModuleConfig.skillRegistry()` Bean 改为：
   ```java
   SkillRegistry r = new SkillRegistry(skillSdkProperties, beanFactory);
   r.register(new TimeNowSkillProvider());
   r.register(new EchoSkillProvider());
   r.register(new KnowledgeSearchSkillProvider(mcpGateway));
   r.register(new AttachmentContextSkillProvider(chatAttachmentMapper));
   return r;
   ```
4. 在 chat 内**临时**新建 `SkillSdkProperties` / `McpSdkProperties`（同包），把 `ChatModuleProperties.Skills` / `.Mcp` 字段全部转移；`ChatModuleProperties` 中删除两个内嵌类。
5. yml 前缀**直接改**为 `gijela.llm.skill.*` / `gijela.llm.mcp.*`，更新 [application.yml](gijela-core/gijela-core-pistil/src/main/resources/application.yml) / [application-dev.yml](gijela-core/gijela-core-pistil/src/main/resources/application-dev.yml)。
6. `McpSkillSync` 不再依赖 `McpServerService`：
   - 新建 `McpToolBindingSource { List<McpToolBinding> loadActive(String tenant); }`
   - `McpServerService.loadActiveBindings` 方法删除（业务接口不持有该 SDK 方法）；改成 `MyBatisMcpServerService implements McpToolBindingSource`，把方法实现搬过去
   - `McpSkillSync` 构造改为 `(McpToolBindingSource, SkillRegistry, McpJsonRpcClient, McpSdkProperties)`
   - `MyBatisMcpServerService` 触发同步改为持有 `ObjectProvider<McpSkillSync>`（已是该模式，保留即可）
7. `MyBatisMcpServerService.create()` 成功后也调一次 `triggerSkillSync()`（之前漏的）。
8. 跑 `mvn -pl gijela-core-chat test`，确认 109 测试全绿。

**产出**：代码还在 chat，但已经满足 SDK 边界约束。

### 阶段 2 — 拆 sdk-skill（1 天）

1. 新建 maven 模块 `gijela-core-llm-sdk-skill`，加入 [gijela-core-llm/pom.xml](gijela-core/gijela-core-llm/pom.xml) 的 modules。
2. pom 仅依赖 `gijela-core-llm-sdk-core` + `spring-boot-autoconfigure`（optional）+ `slf4j-api`；测试加 junit5 + mockito。
3. 按 5.1 表搬迁文件到 `com.gijela.morpheus.llm.sdk.skill.*`；同时把 `SkillSdkProperties` 一起搬过去。
4. 新建 `SkillSdkAutoConfiguration`：
   - `@ConfigurationProperties(prefix = "gijela.llm.skill")` 暴露 `SkillSdkProperties`
   - `@ConditionalOnMissingBean SkillRegistry` 自动构建
   - `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 中声明该类
5. chat 模块 pom 加依赖；批量改 import；删除原 `adapter/skill/` 下被搬走的类与对应 test。
6. chat 中保留：`KnowledgeSearchSkillProvider` / `AttachmentContextSkillProvider`（改 import）+ `SkillStateService` 体系。
7. 跑 `mvn test`。

### 阶段 3 — 拆 sdk-mcp（1 天）

1. 新建 maven 模块 `gijela-core-llm-sdk-mcp`，加入 modules。
2. pom 依赖 `sdk-core` + `sdk-skill` + `okhttp` + `spring-boot-autoconfigure`(optional) + `slf4j-api`。
3. 按 5.2 表搬迁文件到 `com.gijela.morpheus.llm.sdk.mcp.*`；包括 `McpToolBindingSource` 接口、`McpToolBinding` / `McpToolSkillProvider` / `McpSkillSync` 三个桥接类。
4. 新建 `McpSdkProperties`（前缀 `gijela.llm.mcp`），字段：
   ```
   connectTimeoutSeconds / readTimeoutSeconds / callTimeoutSeconds
   allowStdio / stdioCommandWhitelist / stdioStartupTimeoutSeconds / stdioCallTimeoutSeconds
   maxToolsExposed / maxToolResponseChars / autoExposeToSkills
   syncCron (默认空)
   ```
   注意：**`cipherKey` 不放这里**（留 chat），sdk-mcp 接收明文 token。
5. 新建 `McpSdkAutoConfiguration`：
   - 注册 `McpJsonRpcClient` Bean
   - 注册 `McpSkillSync` Bean（仅在 `McpToolBindingSource` 存在时）
   - 注册 `ApplicationRunner` 启动钩子调 `initOnStartup()`
   - 若 `syncCron` 非空，注册 `@Scheduled` 兜底（用 `TaskScheduler`）
6. chat 模块加 sdk-mcp 依赖；改 import；删除原 `adapter/mcp/client/`、`adapter/mcp/skill/` 下被搬走的类；保留 `McpGateway` / `KnowledgeSearchGateway` / `TokenCipher` / `MyBatisMcpServerService`。
7. `MyBatisMcpServerService implements McpToolBindingSource` 落地。
8. 跑 `mvn test` + `mvn -pl gijela-core-pistil package` + 启动 jar 验证。

### 阶段 4 — 收尾（0.5 天）

1. 给两个新 SDK 各写一份 `README.md`（用法、配置项、扩展点示例），引用本评审号。
2. 更新 [docs/requirements/index.md](docs/requirements/index.md)。
3. 跑一遍前端 `pnpm build` 确认无前端影响。
4. 用 baidu-map MCP server 做一次端到端联调（test → refresh-tools → 在聊天中调用工具）。

**总计：~2.5 天**。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 阶段 1 改了 yml 前缀，本地未更新会启动失败 | 中 | 直接改 [application-dev.yml](gijela-core/gijela-core-pistil/src/main/resources/application-dev.yml) + [application.yml](gijela-core/gijela-core-pistil/src/main/resources/application.yml)，README 注明 |
| `LocalSkillPackageLoader` 默认路径 `skills` 是相对路径，工作目录变化时找不到 | 低 | 文档明确建议绝对路径 |
| sdk-mcp 的 `McpSkillSync` 启动钩子失败可能阻塞应用 | 中 | 已实现 `initOnStartup()` 内部 try-catch（109 个测试已覆盖） |
| `@ConditionalOnMissingBean(McpToolBindingSource.class)` 漏写导致没注册时 sync 异常 | 低 | sdk-mcp AutoConfig 加 `@ConditionalOnBean(McpToolBindingSource.class)` |
| chat 测试中 `MockBean` 名字大量重命名 | 中 | 阶段 1 已搬动配置，阶段 2/3 主要改 import，IDE 一键搞定 |
