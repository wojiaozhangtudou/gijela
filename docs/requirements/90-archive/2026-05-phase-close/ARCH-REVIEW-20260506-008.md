# ARCH-REVIEW-20260506-008

## 一、可落地性结论
- 结论：**可落地**。
- 依据：Day1 已冻结基础模型与接口，Day2 重点收敛“线上可控性”：版本冲突、审计 diff、回滚与灰度开关；均可在现有 `gijela-core-chat` 架构内增量实现。

## 二、关键问题与调整建议

1. 问题：版本冲突处理仍停留在“仅报错”，缺少前端可用的冲突载荷。
   - 位置：第2章 2.1（协议与数据契约）
   - 风险：用户只看到 409，不知道该覆盖还是放弃。
   - 建议：`PROMPT_VERSION_CONFLICT` 响应增加 `latestVersion/latestContent/latestUpdatedAt`，前端弹框支持“刷新后重试”。
   - 优先级：P0

2. 问题：审计日志虽有记录，但未结构化 diff。
   - 位置：第2章 2.2（安全与合规）
   - 风险：无法快速审查改动范围，追责成本高。
   - 建议：新增差异字段：`diffSummary`（行级增删改统计 + 前 20 行片段），并支持按 `tenantId/appCode/modelRoute` 查询。
   - 优先级：P0

3. 问题：缺少系统级提示词回滚接口。
   - 位置：第3章 3.1（稳定性）
   - 风险：错误发布后只能手工回填，恢复慢。
   - 建议：新增 `POST /api/v1/chat/prompts/system/rollback`，按 `targetPublishedVersion` 回滚并写审计。
   - 优先级：P0

4. 问题：没有灰度控制，发布即全量。
   - 位置：第4章 4.1（性能与容量）
   - 风险：提示词策略异常会影响全部会话。
   - 建议：增加灰度开关：
     - `chat.prompt.gray.enabled`
     - `chat.prompt.gray.ratio`
     - `chat.prompt.gray.tenants`
     命中灰度才使用新版本，否则回落旧发布版本。
   - 优先级：P0

5. 问题：编排层缺少可观测标签。
   - 位置：第5章 5.1（可测试性与上线门槛）
   - 风险：故障时无法判断命中版本与灰度分流结果。
   - 建议：在 `chat.complete/chat.stream` 审计中追加：
     - `promptPublishedVersion`
     - `sessionPromptVersion`
     - `effectivePromptHash`
     - `grayHit`
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：补齐冲突响应载荷 + 审计 diff 结构。
- 第二步：新增回滚接口并接入权限校验与审计。
- 第三步：灰度开关接入编排层，验证可观测字段后灰度上线。

## 四、待拍板决策
1. 灰度维度优先按租户还是按会话（建议：先租户）。
2. 回滚是否允许跨模型路由（建议：不允许，按 `modelRoute` 隔离）。
3. 审计 diff 是否保存全文快照（建议：保存，保留 30 天）。
