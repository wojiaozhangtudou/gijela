# ARCH-REVIEW-20260501-002 — MCP / Skill 从 chat 工程拆出独立 SDK 模块的可落地性评审

> 评审对象：将 `gijela-core-chat` 中的 MCP / Skill 实现拆分为独立的 SDK 模块
> - `gijela-core-llm-sdk-mcp`
> - `gijela-core-llm-sdk-skill`
>
> 让 `gijela-core-chat` 仅作为"业务编排 + 持久化 + 管理后台"。

---

## 一、可落地性结论

**结论**：✅ **有条件可落地**（需先做"业务 provider 解耦"和"配置拆分"两个前置步骤，才能做物理拆分；否则会拆出循环依赖或一堆灰色可见性 hack）。

**依据**：
1. 大多数 sdk 候选类已经是"业务无感知"的：`McpJsonRpcClient` / `transports/*` / `McpEndpointConfig` / `SkillRegistry` / `SkillProvider` / `SkillManifest` / `LocalSkillPackageLoader` / `SchemaBuilder` 全部不依赖 chat 的 entity / mapper / controller。
2. 真正的耦合点只有两处，均可通过"接口反转 + 构造注入"轻松解开：
   - `SkillRegistry` 构造参数里硬塞了 `McpGateway` + `ChatAttachmentMapper`（为内置的 `KnowledgeSearchSkillProvider` / `AttachmentContextSkillProvider` 服务）；
   - `McpToolSkillProvider` 同时依赖 `SkillProvider`（skill）和 `McpEndpointConfig` / `McpJsonRpcClient`（mcp），形成"两个 SDK 谁依赖谁"的桥接抉择。
3. 数据库表 `chat_mcp_server` / `chat_skill_state` 与 `Mapper` 是业务侧资产，**不入 SDK**，留在 chat。
4. 现存 109 项单测分布合理，拆分后不会出现"测试无法迁移"的死结。

---

## 二、关键问题与调整建议

### 问题 1：`SkillRegistry` 构造期硬注入业务 provider，违反"SDK 不感知业务"
- **位置**：[SkillRegistry.java](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/adapter/skill/SkillRegistry.java) 构造函数。
- **风险**：直接把 `SkillRegistry` 移到 `sdk-skill` 会反向依赖 `McpGateway` / `ChatAttachmentMapper`，sdk-skill → chat 形成循环。
- **建议**：
  - 第一步（拆分前必做）：`SkillRegistry` 构造只保留通用入参（`ChatModuleProperties` 改成 `SkillRegistryProperties`、`AutowireCapableBeanFactory`），**不再 register 任何业务 provider**；只内置 `time.now` / `echo` 两个零依赖示例 provider。
  - chat 侧改为在 `ChatModuleConfig` 里手动 `skillRegistry.register(new KnowledgeSearchSkillProvider(...))`、`register(new AttachmentContextSkillProvider(...))`。
  - 新增一个 `SkillRegistry.register(SkillProvider)` 公共方法（当前只有私有 `register`）。
- **优先级**：**P0**（拆分先决条件）。

### 问题 2：桥接器 `McpToolSkillProvider` 同时依赖两个 SDK，归属不清
- **位置**：[McpToolSkillProvider.java](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/adapter/mcp/skill/McpToolSkillProvider.java) + [McpSkillSync.java](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/adapter/mcp/skill/McpSkillSync.java)。
- **风险**：放错地方 → SDK 间循环依赖；或者业务方每次都要自己写桥接代码。
- **建议**：参考业界（spring-ai-mcp、langchain4j-mcp）做法，**让 sdk-mcp 单向依赖 sdk-skill**：
  - `gijela-core-llm-sdk-skill`：纯接口 + Registry，不感知 MCP；
  - `gijela-core-llm-sdk-mcp`：依赖 sdk-skill，提供 `McpToolSkillProvider` / `McpToolBinding` 两个桥接类；
  - `McpSkillSync` 同样放 sdk-mcp，但需要把"持久化数据源"抽象成接口 `McpToolBindingSource { List<McpToolBinding> loadActive(String tenant); }`，sdk-mcp 自身不知道 MyBatis。
  - chat 侧实现 `McpToolBindingSource`（即原 `MyBatisMcpServerService.loadActiveBindings`），注入给 `McpSkillSync`。
- **优先级**：**P0**。

### 问题 3：`ChatModuleProperties` 里混了 mcp / skills / openai / conversation 多组配置
- **位置**：[ChatModuleProperties.java](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/config/ChatModuleProperties.java)。
- **风险**：sdk 拆出后，`ChatModuleProperties` 又被两个 sdk 反向依赖。
- **建议**：
  - sdk-skill 单独建 `SkillSdkProperties`（`scanEnabled` / `localPath` / `hotReload*`）。
  - sdk-mcp 单独建 `McpSdkProperties`（transport 超时、stdio 白名单、`maxToolsExposed`、`maxToolResponseChars`、`autoExposeToSkills`、`cipherKey`）。
  - chat 的 `ChatModuleProperties` 里把对应内嵌类删掉，改为引用上面两个；前缀保持 `chat.skills.*` / `chat.mcp.*` 不变，避免 yml 兼容性破坏。
- **优先级**：**P0**。

### 问题 4：`McpServerService` 接口耦合了 sdk 类型 `McpToolBinding`
- **位置**：[McpServerService.java](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/service/McpServerService.java) 中 `loadActiveBindings()`。
- **风险**：业务接口里出现 SDK 类型，不算严重，但要确认依赖方向：chat 依赖 sdk-mcp（OK，方向正确）。
- **建议**：保留现状 + 改名为实现 `McpToolBindingSource`（问题 2 抽象）；同时业务管理接口（list/detail/create/update/delete/test/refreshTools）保留在 chat。
- **优先级**：P1。

### 问题 5：`TokenCipher` 既被 chat 用又会被 sdk-mcp 用
- **位置**：[TokenCipher.java](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/util/TokenCipher.java)。
- **风险**：sdk-mcp 不应感知"加密的 token 怎么解密"，否则 chat 和 sdk 都得管 cipherKey。
- **建议**：sdk-mcp 只接收**已解密的明文 token**（`McpEndpointConfig.bearerToken` 即明文）。`TokenCipher` 留 chat，由 `MyBatisMcpServerService.toEndpointConfig()` 解密后传入。当前实现已经是这个模式，**无需调整**。
- **优先级**：P2（确认即可）。

### 问题 6：`KnowledgeSearchSkillProvider` / `AttachmentContextSkillProvider` 的归属
- **位置**：[adapter/skill/](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/adapter/skill/)。
- **风险**：放进 sdk-skill 会反向依赖 chat 的 `ChatAttachmentMapper` / `KnowledgeSearchGateway`；放进 chat 又要依赖 sdk-skill 的 `SkillProvider` 接口（这是合理方向）。
- **建议**：**留 chat**。它们是业务专属技能，由 chat 在启动时主动 `skillRegistry.register(...)`。
- **优先级**：P0（与问题 1 同步执行）。

### 问题 7：`MyBatisMcpServerService` 通过 `ObjectProvider<McpSkillSync>` 注入触发同步
- **位置**：[MyBatisMcpServerService.java](gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/service/impl/MyBatisMcpServerService.java)。
- **风险**：拆分后这条链路依然成立（chat 业务侧 → 调用 sdk-mcp 的 McpSkillSync），方向正确。
- **建议**：拆分时保持现状即可，但要把 `triggerSkillSync()` 内联到 `update/delete/toggle/refreshTools/create` 五处保持一致（目前 `create` 没触发，可能新增 server 后必须重启）。
- **优先级**：P1（顺手补一处）。

### 问题 8：测试归属与 Mockito 依赖
- **位置**：所有 `*Test.java`。
- **风险**：sdk 模块若不引入 mockito 测试依赖，部分测试无法迁移。
- **建议**：两个新 sdk 模块都加 `<scope>test</scope>` 的 junit-jupiter + mockito-core。 涉及业务 mapper 的测试（如 `MyBatisMcpServerService` 的 loadActiveBindings 路径）留 chat。
- **优先级**：P1。

### 3.3 依赖图（目标）

```
gijela-core-llm-sdk-skill   （零业务依赖；可选 spring-boot-autoconfigure）
        ▲
        │
gijela-core-llm-sdk-mcp     （依赖 sdk-skill 仅为桥接 SkillProvider）
        ▲
        │
gijela-core-chat            （依赖以上两个 sdk + chat 自有 mapper/entity/controller）
```

**禁止反向依赖**：sdk-skill 不依赖 sdk-mcp；任何 sdk 都不依赖 chat。

## 四、最小落地路径（MVP 实施顺序）

### 第一阶段（不动模块，先解耦内部依赖；半天）
1. `SkillRegistry`：把 `register(SkillProvider)` 改为 public；构造函数移除内置 4 个 register。
2. `ChatModuleConfig`：在 `skillRegistry()` Bean 内手动 register 业务 4 provider。
3. 跑 `mvn -pl gijela-core-chat test`，确认 109 测试全绿。

### 第二阶段（拆 sdk-skill；1 天）
4. 新建 maven 模块 `gijela-core-llm-sdk-skill`，加入 `gijela-core-llm/pom.xml` 的 modules。
5. 移动文件到 `com.gijela.morpheus.llm.sdk.skill.*`，新建 `SkillSdkProperties`。
6. chat 模块 pom 加依赖；批量改 import；删除原 `adapter/skill/` 下被搬走的类。
7. 业务 provider（KnowledgeSearch / AttachmentContext）保留 chat、改 import。
8. 跑全量测试。

### 第三阶段（拆 sdk-mcp；1 天）
9. 新建 `gijela-core-llm-sdk-mcp`，引入 sdk-skill 依赖。
10. 引入接口反转：新建 `McpToolBindingSource`，`McpSkillSync` 改成依赖它；chat 的 `MyBatisMcpServerService implements McpToolBindingSource`。
11. 移动 client / transport / skill 桥接类；新建 `McpSdkProperties`。
12. chat 改 import + 删除原 `adapter/mcp/client/` 与 `adapter/mcp/skill/`。
13. 跑全量测试 + `mvn -pl gijela-core-pistil package` 启动 jar 验证 yml 兼容。

### 第四阶段（顺手补 + 收尾；半天）
14. `MyBatisMcpServerService.create()` 成功后也调一次 `triggerSkillSync()`（问题 7）。
15. 写一份 sdk 模块 README.md（用法、依赖、配置项），引用本评审号。
16. 更新 `docs/requirements/index.md`。

**总计**：约 **3 天**（含联调），不动 DB schema、不动前端。

## 五、待拍板决策

1. **D1 — sdk 命名**：是 `gijela-core-llm-sdk-skill` / `gijela-core-llm-sdk-mcp` 还是更短的 `gijela-llm-skill` / `gijela-llm-mcp`？倾向沿用现有 `gijela-core-llm-sdk-*` 命名，与 `sdk-core` / `sdk-openai-compatible` 对齐。
2. **D2 — 包前缀**：是 `com.gijela.morpheus.llm.sdk.skill` 还是 `com.gijela.morpheus.skill`？倾向前者，与 `com.gijela.morpheus.llm.sdk.core` 对齐。
3. **D3 — yml 前缀**：sdk-skill 用 `chat.skills.*`（兼容现有）还是 `gijela.llm.skill.*`（更通用）？倾向**保留 `chat.skills.*` + `chat.mcp.*`**，避免破坏现网配置；后续多业务接入时再加 `@ConfigurationProperties` 别名。
4. **D4 — 是否同步把 `KnowledgeSearchSkillProvider` 拆出去**？不建议。它依赖 `KnowledgeSearchGateway`（chat 的 RAG 网关），是业务实现，留 chat。
5. **D5 — McpSkillSync 是否提供 `@Scheduled` 兜底**？建议加一个 yml 开关 `chat.mcp.sync-cron`（默认空 = 不调度），sdk-mcp 内置但不强制开。
6. **D6 — 拆分时机**：现在拆 vs. 等再多一两个业务模块（如 reviewer / agent）再拆？倾向**现在拆**，趁工程小、测试覆盖足，迁移成本低于等业务厚了再动。
