# ARCH-REVIEW-20260507-007

## 需求基线（用于条目引用）
- 第1章 条目1.1：首阶段开工任务拆分（Day1~Day3）。
- 第1章 条目1.2：人天评估与方法签名冻结。
- 第2章 条目2.1：测试矩阵与验收标准。
- 第2章 条目2.2：并行度与依赖梳理。

## 一、可落地性结论
- 结论：可落地。
- 依据：
  - 任务清晰化与并行度高，后端/前端/运维可独立开展。
  - 关键路径短（ES 部署 → 后端 API → 前端集成），不超过 5 天。

## 二、关键问题与调整建议

1. 问题：后端与前端开工有依赖，无法完全并行。
   - 位置：第1章 条目1.1
   - 风险：前端被阻塞。
   - 建议：
     - Day1：后端先部署 mock API（返回固定 JSON）。
     - 前端基于 swagger/postman 文件并行开发。
     - Day2：后端 ES 集成完成，前端切换真实数据源。
   - 优先级：P0

2. 问题：未明确人天与工作量。
   - 位置：第1章 条目1.2
   - 风险：无法评估进度与风险。
   - 建议：
     - 后端 API 接口层：2 天（1 人）
     - 后端 ES 查询与脱敏：3 天（1 人）
     - 告警引擎：2 天（1 人）
     - 前端 SRE 总览页：2 天（1 人）
     - 前端排障/审计/告警页：3 天（1 人）
     - 总计：12 人·天（2 后端 + 2 前端 + 1 运维）
   - 优先级：P1

3. 问题：缺少测试矩阵与上线验收标准。
   - 位置：第2章 条目2.1
   - 风险：上线后有漏洞。
   - 建议：
     - 单元测试：查询 DSL 拼装、脱敏规则、聚合计算。
     - 集成测试：ES 写入、查询、聚合精度。
     - 端到端测试：从日志写入 → 看板展示完整流程。
     - 验收 KPI：查询误差 < 1%、P95 延迟 < 500ms、脱敏命中 100%。
   - 优先级：P1

4. 问题：告警规则的初期配置缺少建议。
   - 位置：第2章 条目2.2
   - 风险：上线后告警规则过多或过少。
   - 建议：
     - P0 规则（必配）：错误率、P95 延迟、首 token 延迟。
     - P1 规则（可选）：工具失败率、ES 写入失败率。
     - 初期从 P0 上线，P1 按需补充。
   - 优先级：P1

## 三、最小落地路径（MVP）
- Phase1（Day1）：ES 配置、后端 API mock、前端路由骨架。
- Phase2（Day2~Day3）：后端 ES 集成、脱敏与聚合、前端图表集成。
- Phase3（Day4~Day5）：告警规则、端到端测试、灰度上线。
