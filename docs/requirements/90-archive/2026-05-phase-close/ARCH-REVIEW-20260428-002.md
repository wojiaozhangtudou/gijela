# ARCH-REVIEW-20260428-002 gijela-core-chat / gijela-bloom-chat 模块脚手架与联调契约评审

### 一、可落地性结论
- 结论：可落地（按 MVP 边界执行）。
- 依据：
  - `gijela-core-llm` 已具备可复用 SDK 能力（同步/流式/Function Calling/工具调用）。
  - `gijela-core-pistil` 已具备统一响应与安全链路，可复用 `ApiResponse`、`ErrorCode`、全局异常处理模式。
  - 风险主要集中在模块边界与联调契约，不在底层能力缺失。

### 二、关键问题与调整建议
1. 问题：后端新模块边界若不冻结，容易与 `pistil` 职责重叠。
   - 位置：第二章（模块职责）
   - 风险：权限后台与聊天联调应用耦合，后续演进困难。
   - 建议：`gijela-core-chat` 定位为“对话联调 BFF + 会话编排层”，不承载 RBAC 主业务。
   - 优先级：P0

2. 问题：前端聊天模块若并入 `gijela-bloom-pistil` 主包会放大发版耦合。
   - 位置：第二章（前端交付形态）
   - 风险：联调频繁改动影响管理后台稳定性。
   - 建议：新建独立模块 `gijela-bloom-chat`，保持与 `pistil` 并行。
   - 优先级：P0

3. 问题：联调 API 契约未冻结。
   - 位置：第三章（协议与数据契约）
   - 风险：前后端联调反复改字段，影响周期。
   - 建议：冻结以下契约（MVP）：
     - 同步：`POST /api/v1/chat/completions`
     - 流式：`POST /api/v1/chat/stream`（SSE）
     - 工具调用事件：`tool_call`、`tool_result`
     - 流式事件集合：`start/delta/tool_call/tool_result/error/done`
   - 优先级：P0

4. 问题：会话存储方案未确定。
   - 位置：第四章（状态管理）
   - 风险：内存态导致多实例下会话不一致。
   - 建议：MVP 采用 Redis（TTL 7 天）存会话摘要；完整历史先不落库。
   - 优先级：P1

5. 问题：MCP/Skills 联调范围过宽。
   - 位置：第五章（扩展能力）
   - 风险：首期实现发散，导致延期。
   - 建议：MVP 仅接 2 类技能：
     - 内置 Skills：`time.now`、`echo`
     - 外部示例 MCP：`knowledge.search`（单一 mock provider）
   - 优先级：P0

6. 问题：错误码与异常映射在 chat 模块未给出统一策略。
   - 位置：第六章（错误处理）
   - 风险：前端无法稳定识别失败类型。
   - 建议：`LlmException -> ApiResponse.fail(ErrorCode.*, message)`；流式 `error` 事件带 `code/message`。
   - 优先级：P0

7. 问题：上线门槛未量化到 chat 模块。
   - 位置：第七章（测试与发布）
   - 风险：可运行但不可交付。
   - 建议：
     - 后端：契约测试 + 回放测试 + 基线压测（20 QPS / 80 并发）
     - 前端：同步/流式/工具调用/中断恢复 4 条冒烟
   - 优先级：P0

### 三、最小落地路径（MVP）
- 第一步：模块骨架
  - 新增 `gijela-core-chat`（Spring Boot）
  - 新增 `gijela-bloom-chat`（Vue3 + Vite）
- 第二步：主链路打通
  - `/completions` 同步 + `/stream` SSE
  - 技能路由（内置 skills + 1 个 MCP mock）
- 第三步：联调准入
  - 错误码映射、审计脱敏、回放测试、前端冒烟

### 四、待拍板决策
1. `gijela-core-chat` 是否独立端口（建议：独立端口，避免影响 `pistil`）。
2. 会话存储是否首期直接上 Redis（建议：是）。
3. MCP 示例是否允许外网调用（建议：否，先内网 mock）。
4. 前端鉴权是否复用 `pistil` token（建议：复用，减少登录体系重复）。
5. 首期是否要求历史会话持久化（建议：否，先摘要 + TTL）。
