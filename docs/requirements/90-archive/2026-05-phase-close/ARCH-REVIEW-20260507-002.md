# ARCH-REVIEW-20260507-002

## 需求基线（用于条目引用）
- 第1章 条目1.1：日志存储方案固定为 Elasticsearch（ES）。
- 第1章 条目1.2：需要统一的日志聚合看板（面向运维、研发、业务审计）。
- 第2章 条目2.1：沿用上版日志分层（access/runtime/audit）与脱敏原则。
- 第2章 条目2.2：支持检索、聚合、告警、留存与灰度观测。

## 一、可落地性结论
- 结论：可落地。
- 依据：
  - ES 天然支持时序检索、聚合分析、ILM 与索引模板，适配 LLM 日志场景。
  - 现有 chat 链路已有统一事件出口规划，可直接对接 ES 写入与 Kibana 看板。
  - 风险主要集中在索引治理与字段规范，属于工程可控项。

## 二、关键问题与调整建议
1. 问题：索引规划未冻结，后续扩展会产生 mapping 冲突。
   - 位置：第1章 条目1.1
   - 风险：字段类型漂移（keyword/text/long）导致聚合失败、查询性能退化。
   - 建议：固定 4 组 data stream：
     - `llm-access-*`
     - `llm-runtime-*`
     - `llm-audit-*`
     - `llm-metric-*`（聚合后指标）
     并冻结组件模板（字段类型、analyzer、dynamic=false）。
   - 优先级：P0

2. 问题：日志契约与 ES 字段未对齐。
   - 位置：第2章 条目2.1
   - 风险：同名字段不同类型，导致跨索引查询失败。
   - 建议：统一字段字典（必填）：
     - 标识：`@timestamp`、`traceId`、`sessionId`、`turnId`、`tenantId`、`appCode`
     - 路由：`provider`、`model`、`modelRoute`、`endpoint`
     - 结果：`status`、`errorCode`、`latencyMs`、`firstTokenMs`
     - 计量：`promptTokens`、`completionTokens`、`totalTokens`、`costMicros`
     字段命名采用 lowerCamelCase，枚举字段使用 keyword。
   - 优先级：P0

3. 问题：看板人群不同但未分视图，信息噪音大。
   - 位置：第1章 条目1.2
   - 风险：研发看不到慢点细节，运维看不到全局健康，审计看不到追责路径。
   - 建议：拆成 3 套看板（同源字段）：
     - 运维总览：QPS、错误率、P95 延迟、首 token 延迟、ES 写入失败率。
     - 研发排障：按 `traceId/sessionId/toolName/errorCode` 下钻，展示事件时间线。
     - 审计合规：按租户/操作者/模型路由查询，展示脱敏后变更轨迹。
   - 优先级：P0

4. 问题：容量与成本控制策略未落地到 ES。
   - 位置：第2章 条目2.2
   - 风险：分片过多、热节点爆盘、查询抖动。
   - 建议：
     - ILM：hot 7 天 → warm 23 天 → delete（runtime 30 天；audit 180 天）。
     - rollover 条件：`max_age=1d` 或 `max_primary_shard_size=30gb`。
     - 分片建议：按日索引初始 1~2 primary，副本 1（按集群容量再调）。
   - 优先级：P0

5. 问题：流式事件写入频率高，ES 写入与查询互相干扰。
   - 位置：第2章 条目2.2
   - 风险：高峰期 ingest backlog，主链路观测失真。
   - 建议：
     - 流式仅落关键事件（start/first_token/done/error）。
     - debug 事件采样（默认 1%，可按租户提升）。
     - 引入 ingest pipeline：脱敏、字段归一、异常字段丢弃计数。
   - 优先级：P1

6. 问题：告警规则未体系化。
   - 位置：第1章 条目1.2
   - 风险：出故障时只能被动查日志。
   - 建议：建立 5 条 P0 告警：
     - `errorRate > 5%`（5 分钟）
     - `P95 latencyMs > 基线*1.5`（10 分钟）
     - `firstTokenMs P95 > 3000ms`（10 分钟）
     - `esIngestFailureRate > 1%`（5 分钟）
     - `toolErrorRate(toolName) > 10%`（10 分钟）
   - 优先级：P0

7. 问题：上线门槛未绑定 ES 与看板验收。
   - 位置：第2章 条目2.2
   - 风险：上线后“有日志但不可用”。
   - 建议：增加 Go/No-Go 验收：
     - `traceId` 全链路串联成功率 >= 99%。
     - 核心看板 8 张图都有近 24h 数据。
     - 任一 `errorCode` 可在 3 次点击内下钻到原始事件。
     - 敏感字段抽检 100 条，脱敏命中率 100%。
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：冻结 ES 索引模板 + ILM + ingest pipeline（先 runtime）。
- 第二步：打通 8 个核心事件写入 ES，并落地运维总览看板（QPS/错误率/P95/首 token）。
- 第三步：补研发排障看板与审计看板，最后接入告警与值班通知。

## 四、待拍板决策
1. 看板载体：Kibana 原生还是 Grafana + ES（建议先 Kibana）。
2. 审计域是否允许按白名单查看“受控摘要原文”。
3. 多环境策略：dev/test/prod 同集群分 namespace，还是独立集群。
4. 成本上限：ES 热存储预算与月度日志量红线。
