# ARCH-REVIEW-20260428-001 新建 gijela-core-chat / gijela-bloom-chat 联调架构评审

### 一、可落地性结论
- 结论：有条件可落地。
- 依据：
  - 现有 `gijela-core-llm` 已具备 SDK 核心能力（同步/流式/Function Calling/工具调用/运行时选项），可作为 `gijela-core-chat` 的基础依赖。
  - 但当前需求文档对“新建业务联调模块”的边界、契约、容量与上线门槛未显式定义，直接实施存在架构漂移风险。

### 二、关键问题与调整建议
1. 问题：目标与范围未明确“SDK 与联调应用”的分层关系。
   - 位置：REQ-20260427-002 第二章 In Scope 第3条（仅定义 Java SDK 交付）
   - 风险：`gijela-core-chat` 可能与 `gijela-core-pistil` 职责重叠，导致后续维护边界不清。
   - 建议：补充一条范围声明：`gijela-core-chat` 为“联调/BFF 示例应用”，不承载 RBAC 主业务；`gijela-core-llm` 保持纯 SDK。
   - 优先级：P0

2. 问题：模块边界与职责尚未定稿。
   - 位置：REQ-20260427-002 第三章 P0（能力清单）
   - 风险：前后端容易把“对话编排、会话存储、MCP/Skills 路由、审计”混在 Controller 层。
   - 建议：明确分层：
     - `gijela-core-chat`：`controller`（协议）/`service`（编排）/`adapter`（SDK、MCP、Skills）/`domain`（会话与消息模型）
     - `gijela-bloom-chat`：`src/api`（请求封装）/`src/store`（会话状态）/`src/views`（聊天页）
   - 优先级：P0

3. 问题：协议与数据契约未统一到“联调场景”。
   - 位置：REQ-20260427-002 第五章 验收标准 第3/12条（流式事件集合）
   - 风险：前端与后端流式事件字段不一致，导致联调反复改协议。
   - 建议：先冻结 Chat API 契约：
     - `POST /api/v1/chat/completions`（同步）
     - `POST /api/v1/chat/stream`（SSE）
     - 事件类型固定：`start/delta/tool_call/tool_result/error/done`
     - 响应统一外层 `ApiResponse`（同步），流式用标准事件体（不再包二层业务 envelope）
   - 优先级：P0

4. 问题：性能与容量目标未落到新模块。
   - 位置：REQ-20260427-002 第四章（性能基线）
   - 风险：联调阶段若不设并发和超时门槛，容易把 SDK 问题与业务问题混淆。
   - 建议：给 `gijela-core-chat` 增加最小目标：
     - 同步 `P95 <= 3s`、流式 `TTFB <= 800ms`
     - 单实例联调基线 `20 QPS / 80 并发`
   - 优先级：P1

5. 问题：稳定性策略在“对话会话级别”未定义。
   - 位置：REQ-20260427-002 第三章 P0-3/P0-11（重试/隔离）
   - 风险：流式断连、工具调用超时、插件失败时用户态表现不一致。
   - 建议：补充会话级策略：
     - 流式可取消、断连可重试（仅重连，不重复执行已完成工具）
     - 工具调用超时统一映射 `TOOL_ERROR`
     - 插件失败时回退“纯模型回复”并记录审计
   - 优先级：P0

6. 问题：安全与合规在 chat 模块未落地到最小要求。
   - 位置：REQ-20260427-002 第四章（安全/合规）
   - 风险：日志泄露 Prompt/密钥、会话留存不受控。
   - 建议：
     - API Key 仅服务端配置，不透传前端
     - Prompt/Tool 参数日志默认脱敏
     - 会话留存默认 7 天可配置，提供审计 traceId
   - 优先级：P0

7. 问题：可测试性与上线门槛未定义。
   - 位置：REQ-20260427-002 第四章（可测试性）与第五章（验收）
   - 风险：模块虽然能跑，但缺少联调准入标准，难以稳定交付。
   - 建议：新增上线门槛：
     - 后端：契约测试 + 回放测试 + 基线压测通过
     - 前端：至少覆盖“同步、流式、工具调用、错误恢复”四条 E2E 冒烟
   - 优先级：P0

### 三、最小落地路径（MVP）
- 第一步：建立模块骨架与依赖
  - `gijela-core-chat`（Spring Boot + 依赖 `gijela-core-llm-sdk-*`）
  - `gijela-bloom-chat`（Vue3 + 会话页 + SSE 消费）
- 第二步：冻结最小联调协议并打通主链路
  - 同步 + 流式 + Function Calling（含 `tool_call/tool_result`）
- 第三步：补齐治理与准入
  - 错误码映射、审计脱敏、回放测试、联调脚本与验收清单

### 四、待拍板决策
1. `gijela-core-chat` 是否独立端口部署，还是并入 `gijela-core-pistil`（推荐独立，避免边界污染）。
2. `gijela-bloom-chat` 是独立前端项目还是并入 `gijela-bloom-pistil` 子应用（推荐独立，联调迭代更快）。
3. 会话存储策略：首期内存/Redis/DB（三选一，建议首期 Redis）。
4. MCP/Skills 首期范围：仅示例技能还是接入真实外部工具（建议先示例技能 + 1 个真实工具）。
5. 联调验收门槛是否采用“P0 必过 + P1 可延期”的发布策略。
