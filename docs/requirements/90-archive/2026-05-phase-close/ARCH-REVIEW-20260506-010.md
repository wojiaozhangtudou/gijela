# ARCH-REVIEW-20260506-010

## 一、可落地性结论
- 结论：**可落地**。
- 依据：功能方案（004~009）已完整，当前瓶颈从“怎么做”转为“如何按节奏做”；通过统一排期与闸门可控上线。

## 二、关键问题与调整建议

1. 问题：Day1~Day3 任务分散，缺少统一节奏。
   - 位置：第2章 2.1（目标与范围一致性）
   - 风险：并行开发造成返工与联调拥堵。
   - 建议：按“后端主链路优先、前端延后半天接入、发布控制面最后收口”执行三天排期。
   - 优先级：P0

2. 问题：人员分工未固定。
   - 位置：第2章 2.2（架构边界与模块职责）
   - 风险：多人改同文件导致冲突频发。
   - 建议：固定角色：BE-A（数据/服务）、BE-B（接口/权限/审计）、FE（页面/交互），每天只在约定窗口合并。
   - 优先级：P0

3. 问题：缺少“停线闸门”。
   - 位置：第5章 5.1（稳定性）
   - 风险：带隐患进入下一天，问题滚雪球。
   - 建议：设置 P0 Gate：单测不过、409 冲突不可复现、回滚不可用，任一命中即停线修复。
   - 优先级：P0

4. 问题：上线前缺少统一验收口径。
   - 位置：第7章 7.1（可测试性与上线门槛）
   - 风险：功能“看似可用”但生产不可控。
   - 建议：发布前必须完成“灰度 + 回滚演练 + 审计追溯”三项联验。
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：Day1 完成“数据层 + 接口层 + 前端壳子”闭环。
- 第二步：Day2 完成“冲突/diff/回滚/灰度”控制能力。
- 第三步：Day3 完成“审批发布流程 + 监控告警 + 演练验收”。

## 四、待拍板决策
1. 合并策略：是否要求每日仅 2 次合并窗口（建议：是）。
2. 生产首日灰度比例（建议：10%）。
3. 告警策略：先人工回滚还是自动回滚（建议：先人工）。

## 五、实施总排期（Day1~Day3）

### 5.1 甘特视图（简版）
- Day1 上午：BE-A 建表与 Mapper；BE-B 建 Controller/DTO；FE 建 `prompt.ts` API 壳。
- Day1 下午：BE-A 完成 `PromptConfigService` 基础实现；BE-B 联通四接口；FE 接入 `store/prompt.ts` 并展示读取。
- Day2 上午：BE-B 完成 409 冲突载荷；BE-A 完成审计 diff；FE 接冲突弹窗。
- Day2 下午：BE-A/BE-B 完成回滚与灰度；FE 接回滚入口；联调 `effectivePromptHash`。
- Day3 上午：BE-B 完成提交/审批/发布状态机；FE 接审批按钮与状态展示。
- Day3 下午：全员进行灰度验证 + 回滚演练 + 发布前评审。

### 5.2 人员分工
- BE-A（核心域）：Entity/Mapper/Service、版本与回滚逻辑。
- BE-B（接口与治理）：Controller、权限点、审计写入、状态机。
- FE（交互）：API/Store/页面改造、冲突处理、审批流交互。
- QA（可兼任）：回归清单执行、演练记录产出。

## 六、风险闸门（P0 Gate）
1. 单测/集成任一失败：停止合并。
2. `PROMPT_VERSION_CONFLICT` 无法稳定复现：停止进入 Day2。
3. 回滚接口不可用或耗时 > 10 分钟：禁止灰度。
4. 审计缺少 `effectivePromptHash`：禁止发布。

## 七、发布验收清单（Go/No-Go）
1. 功能：系统级/会话级提示词可编辑、生效范围正确。
2. 稳定性：冲突可处理、回滚可执行、灰度可控。
3. 安全：权限点生效，审批链路“提交人与审批人不同”。
4. 可观测：可按 `promptPublishedVersion` 追踪错误率与耗时。
