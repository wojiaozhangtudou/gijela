# ARCH-REVIEW-20260428-005 chat 模块附件存储选型补充评审（RustFS）

### 一、可落地性结论
- 结论：可落地。
- 依据：
  - `RustFS` 兼容 S3 协议，适合作为 `gijela-core-chat` / `gijela-bloom-chat` 的附件对象存储。
  - 该决策不会影响 `gijela-core-llm` SDK 主链路，只影响 chat 模块的附件上传、预签名访问与对象元数据管理。

### 二、关键问题与调整建议
1. 问题：附件存储选型此前未冻结。
   - 位置：ARCH-REVIEW-20260428-004 第四章待拍板项未覆盖附件对象存储。
   - 风险：开发可能在 MinIO / OSS / 本地文件之间摇摆，导致接口与配置返工。
   - 建议：明确首期附件对象存储统一采用 `RustFS`，通过 S3 协议接入。
   - 优先级：P0

2. 问题：附件访问协议与元数据边界未定义。
   - 位置：chat 模块实施级目录与接口清单中未覆盖附件能力。
   - 风险：前后端可能直接传本地文件路径或耦合具体存储实现。
   - 建议：冻结为三层边界：
     - 对象存储：`RustFS(S3)` 只存二进制对象
     - 业务库：保存附件元数据（`fileId/objectKey/fileName/contentType/size/uploader/sessionId`）
     - 前端：仅消费上传接口与预签名 URL，不感知底层 RustFS 细节
   - 优先级：P0

3. 问题：安全与合规策略未细化。
   - 位置：REQ-20260427-002 第四章（安全/合规）
   - 风险：若直接暴露长期 AK/SK 或公开 bucket，存在泄露风险。
   - 建议：
     - 服务端持有 S3 凭证
     - 前端通过后端申请预签名上传/下载 URL
     - bucket 默认私有
     - 对象 key 按 `tenant/session/date/uuid` 规范生成
   - 优先级：P0

4. 问题：模块接入方式未明确。
   - 位置：chat 模块实施级清单
   - 风险：附件能力可能散落在 Controller 或前端直接调对象存储。
   - 建议：在 `gijela-core-chat` 增加：
     - `adapter/storage/ObjectStorageGateway.java`
     - `adapter/storage/s3/RustfsS3StorageGateway.java`
     - `service/AttachmentService.java`
     - `domain/dto/AttachmentUploadInitRequest.java`
     - `domain/dto/AttachmentUploadInitResponse.java`
   - 优先级：P1

5. 问题：验收标准未补充附件联调场景。
   - 位置：chat 模块联调准入
   - 风险：聊天主链路能跑，但附件链路上线后出问题。
   - 建议：新增最小验收：
     - 获取上传凭证成功
     - 上传后回传对象 key / fileId
     - 聊天消息可引用附件元数据
     - 非授权用户无法下载他人私有附件
   - 优先级：P1

### 三、最小落地路径（MVP）
- 第一步：冻结选型
  - 附件对象存储统一采用 `RustFS(S3)`
- 第二步：冻结接入方式
  - 后端负责预签名 URL 与元数据落库
  - 前端直传对象存储，不直持凭证
- 第三步：补齐联调契约
  - 上传初始化接口
  - 上传完成回调/确认接口
  - 聊天消息附件引用结构

### 四、待拍板决策
1. RustFS bucket 是否按租户隔离（建议：逻辑隔离优先，bucket 可共享，key 前缀分租户）。
2. 附件元数据首期落 Redis 还是 MySQL（建议：MySQL）。
3. 是否首期支持图片预览与文本类附件解析（建议：图片预览支持，内容解析放 P1）。
