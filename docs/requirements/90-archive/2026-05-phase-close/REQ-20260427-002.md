# REQ-20260427-002 大模型调用框架封装

## 一、目标
- 封装一套可复用的大模型调用框架，预留多模型提供商扩展能力；首期基于单一 OpenAI 兼容配置落地，统一请求/响应协议并具备可观测与可治理能力，便于在业务中稳定复用。

## 二、范围
### In Scope
- 统一抽象层：模型客户端接口、请求参数模型、响应模型、错误模型。
- 提供商适配：首期仅支持单一 OpenAI 兼容接口（按配置固定 `baseUrl`/`apiKey`/`model` 使用，不做厂商切换）。
- 交付形态：以 **Java SDK** 方式交付，对标 LangChain4j 的模块化能力（模型接入、流式回调、工具调用、记忆/RAG 可扩展）。
- 技术约束：所有 HTTP 请求统一使用 **OkHttp**，不得与 Apache HttpClient、JDK HttpClient 或其他 HTTP 客户端混用。
- 关键治理能力：超时、重试、基础限流、幂等、降级（熔断作为 P1 增强项）。
- 可观测性：结构化日志、调用指标、链路追踪、成本统计（token/金额）。
- 安全能力：API Key 管理、敏感信息脱敏、审计日志。
- 基础能力：同步调用、流式输出（SSE）、函数调用/工具调用抽象。
- 扩展协议能力：支持 MCP、Skills、A2A，并采用可插拔扩展架构（插件式接入）。
- 扩展治理能力：插件清单（Manifest）、版本兼容校验、签名校验、权限模型与调用审计。

### Out of Scope
- 复杂 Agent 编排引擎（多智能体调度）。
- Prompt 可视化平台与运营后台。
- 模型训练/微调平台。
- 首期不实现非 OpenAI 兼容协议的原生适配（如 Anthropic 原生协议等）。
- 首期不实现多 OpenAI 兼容厂商动态切换或路由。
- 不建设独立网关形态（本项目仅 SDK 形态）。

## 三、功能清单
### P0（必须）
1. `LlmClient` 统一接口（chat、embedding 可分接口）。
2. Provider 适配器层（`OpenAiCompatibleProvider`）。
3. 统一重试与超时策略（含指数退避 + 抖动）。
4. 统一错误码与异常分层（网络错误/限流/鉴权/模型错误）。
5. 流式输出抽象（SSE chunk -> 统一事件）。
6. 基础指标与日志（延迟、成功率、token 消耗、错误分布）。
7. Function Calling（工具调用）能力：工具注册、参数校验、工具执行结果回传模型。
8. 可插拔扩展框架：`Plugin SPI`、插件生命周期（加载/启停/卸载）、统一配置模型。
9. MCP / Skills / A2A 统一扩展接口与最小可用实现（至少各 1 个示例插件）。
10. 运行时热插拔：支持插件在不停机条件下动态加载、启用、禁用、卸载。
11. 插件隔离与治理：插件级权限控制（允许调用的工具/资源）、健康检查、故障隔离与回滚。
12. 协议与版本治理：统一事件/错误码契约、插件 API 版本兼容策略（向后兼容规则）。
13. 成本与配额治理：按应用/租户配置预算上限、超额降级策略与告警。
14. 默认策略基线：
	- 流式事件契约固定为 `start/delta/tool_call/tool_result/error/done`。
	- 插件信任策略首期采用“内网白名单 + SHA-256 校验”，签名校验作为 P1 增强。
	- 预算超限默认策略为“限流 + 模型降级 + 告警”，不立即全量拒绝。
	- 成本统计粒度首期固定为“租户级”（应用级仅观测，用户级放 P1）。
	- 热插拔运行约束：新请求走新版本，在途请求保持旧版本直至完成；触发回滚时自动回切上一稳定版本。

### P1（应该）
1. 熔断增强（按租户/模型/接口粒度，含半开探测与恢复策略）。
2. Prompt 模板与变量注入机制。
3. 结果缓存（短期缓存 + 失效策略）。
4. 回退策略（主模型失败自动切备用模型）。

### P2（可选）
1. 语义路由（按任务自动选模型）。
2. 成本优化器（自动根据预算降级模型）。
3. A/B 实验与效果评估闭环。

## 四、非功能需求
- 性能（首期基线）：非流式 P95 <= 3s；流式 TTFB <= 800ms；最小目标 50 QPS、200 并发。
- 可用性：核心调用链路可用性目标（建议 >= 99.9%）。
- 质量：调用错误率 <= 1%（按 5 分钟滑窗统计）。
- 安全：密钥不落盘明文，日志默认脱敏，支持审计追踪。
- 可维护：新增 Provider 时变更范围限制在适配层。
- 一致性：HTTP 客户端实现必须复用统一 `OkHttpClient` 工厂与拦截器链。
- 稳定性：插件热插拔期间核心调用链路不中断，失败插件可隔离回滚。
- 合规：会话与日志保留策略可配置（保留时长、脱敏级别、可追溯审计）。
- 可测试性：提供契约测试、回放测试与压测基线，支持发布前自动验收。

## 五、验收标准（Given-When-Then）
1. Given 已配置固定 `baseUrl`、`apiKey` 与 `model`，When 发起模型调用，Then 框架按该配置稳定调用，不做厂商切换。
2. Given 上游模型接口偶发超时，When 触发重试策略，Then 在最大重试次数内返回成功或明确可识别错误。
3. Given 开启流式输出，When 模型返回分片数据，Then 业务层可按统一事件持续消费并可中断。
4. Given 线上调用发生失败，When 查看日志与指标，Then 能定位 provider、model、错误类型与耗时区间。
5. Given 模型返回 function/tool 调用请求，When 框架执行对应工具，Then 可完成参数校验、工具执行，并将结果按协议回传模型继续对话。
6. Given 业务侧主动取消流式会话，When 触发取消信号，Then 框架应及时关闭上游连接并释放资源，不产生连接泄漏。
7. Given 新增 MCP/Skills/A2A 插件，When 完成插件注册与配置，Then 无需改动核心调用链即可启用扩展能力。
8. Given 插件被禁用或卸载，When 业务继续调用核心 LLM 能力，Then 主链路仍可稳定运行且不受插件故障影响。
9. Given 线上运行中的实例，When 执行插件热加载/热卸载，Then 无需重启服务，且不影响正在进行的普通模型调用。
10. Given 插件尝试访问未授权工具或资源，When 触发调用，Then 框架应拒绝并记录审计日志。
11. Given 达到租户预算阈值，When 继续调用模型，Then 框架应按策略执行限流/降级并触发告警。
12. Given 流式输出开启，When 返回事件流，Then 事件类型必须严格落在 `start/delta/tool_call/tool_result/error/done` 集合内。
13. Given 系统处于最小压测目标（50 QPS、200 并发），When 连续压测 10 分钟，Then 非流式 P95 <= 3s 且错误率 <= 1%。
14. Given 执行插件热加载或回滚，When 有在途请求，Then 在途请求继续由旧版本处理，新请求切换到新版本，且主链路无中断。

## 七、风险与依赖
- 各厂商响应协议差异大，适配层设计不当会导致后续扩展成本高。
- 缺少统一超时/重试边界，容易造成请求风暴或重复扣费。
- 流式场景下取消与资源释放处理不当会导致连接泄漏。

## 八、实施计划（里程碑）

- M3（3~4天）：日志指标 + 限流熔断 + 成本统计。
- M4（2~3天）：接入示例、压测、文档与验收。

## 十五、业界通用定义参考（用于拍板）
1. 架构形态
	- `SDK`：嵌入业务服务内，延迟低、落地快、治理分散。
	- `Gateway`：统一入口，治理集中、观测统一、运维复杂度更高。
	- 常见路径：先 SDK 验证，稳定后演进到网关化。

2. 需求优先级
	- `P0`：不上线会阻断主流程或产生高风险。
	- `P1`：不阻断上线，但影响体验/效率，通常次迭代补齐。
	- `P2`：优化项或增强项。

3. 性能与可用性（SLO）
	- 常见定义：可用性（如 99.9%）、成功率、`P95/P99` 延迟、流式 `TTFB`。
	- 验收建议：按“正常/峰值/降级”三档给阈值。

4. 重试与超时
	- 常见定义：连接超时、读取超时、总超时分离；指数退避 + 抖动；只对幂等请求重试。
	- 常见上限：重试 2~3 次，避免放大流量风暴。

5. 限流与熔断
	- 限流：按租户/模型/接口维度限速与并发上限。
	- 熔断：基于错误率或超时率触发，进入半开后探测恢复。

6. 流式输出
	- 常见协议：SSE。
	- 常见事件：`start/delta/tool_call/tool_result/error/done`。
	- 必备语义：可取消、可回收、可审计。

7. Function Calling
	- 常见链路：工具注册 -> 参数校验 -> 执行 -> 结果回传 -> 模型继续推理。
	- 必备约束：权限校验、超时控制、幂等与审计。

8. 插件化与热插拔
	- 常见定义：`Manifest + SPI + 生命周期 + 隔离 + 回滚`。
	- 热插拔验收：无重启生效，主链路不中断，失败可回退。

9. 成本治理
	- 常见维度：应用/租户/用户。
	- 常见策略：预算阈值告警 -> 限流 -> 模型降级 -> 最后拒绝。

10. 流式协议选型（SSE vs WebSocket）
	- 现状：文本流式输出场景业界大量使用 SSE（实现简单、HTTP 友好）。
	- 局限：SSE 天然单向（服务端 -> 客户端），不适合高频双向交互；断线恢复与重放需要业务层补偿；对实时音频/低时延强交互场景不如 WebSocket/WebRTC。
	- 选型建议：
	  - 文本生成/增量回显：优先 SSE。
	  - 双向实时控制、语音流、事件双工：优先 WebSocket（或 WebRTC）。

## 十六、协议决策建议（本项目）
- 结论：不是“WebSocket 一定更好”，而是按场景选。
- 对当前需求（单一 OpenAI 兼容 + 文本流式 + Function Calling）：**MVP 推荐 SSE**，实现成本更低、兼容性更稳。
- 对后续场景（A2A 高频双向交互、语音实时、服务端主动控制）：新增 **WebSocket 通道**。
- 落地策略：
  1. P0：SSE 主链路上线（文本流式）。
  2. P1：补 WebSocket 双工通道（实时控制/语音）。
  3. 保持统一事件模型，避免上层业务感知协议差异。
