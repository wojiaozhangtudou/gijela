# ARCH-REVIEW-20260505-001：Neo4j 图数据库管理页（含文本/文件抽取入图）可落地性评审

- 日期：2026-05-05
- 状态：已评审
- 评审对象：新增 Neo4j 图数据库增删改查页面，交互参考“知识库管理”，支持“上传文件”和“直接文本”两种触发方式，并基于 LLM 提示词抽取实体关系后写入图谱。

## 一、可落地性结论

- 结论：**有条件可落地**。
- 依据：
  1. 仓库父 POM 已纳入 `neo4j-java-driver` 版本管理，可直接在后端落地 Neo4j 访问层。
  2. 现有仓库已有“文本写入 / 文件上传 / 后端统一 `ApiResponse` / 前端 Element Plus 管理页”成熟模式，可平移交互范式。
  3. 但当前需求仍缺少 4 个关键决策：**图模型约束、LLM 调用边界、文件处理策略、覆盖/合并语义**。不先冻结，后续很容易出现“能导入但不可维护”的问题。

---

## 二、关键问题与调整建议

### 1. 问题：目标范围过大，CRUD 与“抽取入图”混在一起
- 位置：**1.1 目标定义**
- 风险：
  - “图数据库 CRUD 页面”与“LLM 实体关系抽取”是两条链路：前者偏管理后台，后者偏 AI 入库流水线。
  - 若一次性一起做，前后端接口、状态机、异常处理都会膨胀，首版容易超 scope。
- 建议：
  - 将需求拆成两层：
    1. **图谱管理层**：节点/关系增删改查、搜索、详情、删除；
    2. **抽取入图层**：文本/文件 -> 抽取预览 -> 人工确认 -> 入图。
  - 首版页面仍可合并成一个入口，但实现上必须拆成两个 service 和两组 API。
- 优先级：**P0**

### 2. 问题：图模型未冻结，后续会直接影响 CRUD 语义
- 位置：**2.1 数据模型**
- 风险：
  - 只定义了输出 prompt，没有定义 Neo4j 中节点 label、关系 type、唯一键、租户隔离方式。
  - 若直接把 `relationship_description` 当 relationship type，会导致 type 爆炸，不可查询、不可索引。
- 建议：
  - 冻结首版图模型：
    - 节点统一 label：`Entity`
    - 节点主键：`tenantId + graphSpace + entityName`
    - 节点属性：
      - `entityName`
      - `entityType`
      - `entityDescription`
      - `sourceType`（TEXT / FILE / MANUAL）
      - `sourceId`
      - `createdAt`
      - `updatedAt`
    - 关系统一 type：`RELATED_TO`
    - 关系属性：
      - `description`
      - `strength`
      - `sourceType`
      - `sourceId`
      - `createdAt`
      - `updatedAt`
  - 不建议首版使用动态 relationship type。
- 优先级：**P0**

### 3. 问题：缺少“图谱空间 / 图谱名称”维度
- 位置：**2.2 图谱隔离**
- 风险：
  - 管理后台未来不可能只有一张总图；若没有 `graphSpace`，不同业务、不同批次、不同知识域会相互污染。
- 建议：
  - 首版至少增加 `graphSpace` 概念，类似知识库 collection。
  - 所有查询、写入、删除接口必须显式携带 `graphSpace`。
  - 页面左侧先展示“图谱空间列表”，右侧展示节点、关系、导入记录。
- 优先级：**P0**

### 4. 问题：上传文件链路未定义“是否落存储”
- 位置：**2.3 文件处理策略**
- 风险：
  - 直接上传后即时解析虽然快，但无法审计和重试。
  - 先存对象存储再异步处理虽然稳，但会多一层对象管理与清理策略。
- 建议：
  - 参考现有知识库链路，首版采用：
    1. 文件上传到对象存储；
    2. 后端读取文本（Tika）；
    3. 保存一条导入任务记录；
    4. 调用抽取；
    5. 生成预览；
    6. 用户确认后入图。
  - 这样既支持审计，也支持失败重试。
- 优先级：**P0**

### 5. 问题：LLM 抽取结果缺少“预览确认”环节
- 位置：**2.4 抽取流程**
- 风险：
  - 实体关系抽取天然不稳定，若直接入图，会把错误关系永久写进生产图谱。
- 建议：
  - 首版流程必须是：
    - 文本/文件提交
    - LLM 抽取
    - 解析为结构化结果
    - 前端预览（实体表 + 关系表）
    - 用户点击“确认入图”
    - 后端执行 Neo4j 写入
  - 不建议做“提交即入图”。
- 优先级：**P0**

### 6. 问题：缺少覆盖/合并语义
- 位置：**2.5 写入策略**
- 风险：
  - 同一实体多次导入时，描述、类型、关系强度如何处理若不明确，会导致数据抖动。
- 建议：
  - 首版增加 `importMode`：
    - `MERGE_APPEND`：实体 `MERGE`，关系去重后追加；
    - `REPLACE_SPACE`：清空当前 `graphSpace` 后重建；
    - `PREVIEW_ONLY`：只抽取不写入。
  - 默认 `MERGE_APPEND`。
- 优先级：**P0**

### 7. 问题：后端模块边界尚未明确
- 位置：**3.1 模块职责**
- 风险：
  - 现有“知识库管理”实际在 `gijela-core-chat / gijela-bloom-chat`，而用户现在要的是“管理后台页面”，应落在 `gijela-core-pistil / gijela-bloom-pistil`。
  - 若直接复用 chat 页面，会破坏模块边界。
- 建议：
  - 页面落在 **pistil 前端**；
  - API 落在 **pistil 后端**；
  - LLM 抽取客户端建议通过共享能力接入，避免 pistil 直接依赖 chat 业务实现。
  - 推荐后端分层：
    - `controller/GraphController`
    - `service/GraphImportService`
    - `service/GraphCrudService`
    - `support/neo4j/Neo4jGraphRepository`
    - `support/llm/EntityRelationExtractionClient`
- 优先级：**P0**

### 8. 问题：前端页面目标不应只做“表单提交”
- 位置：**3.2 前端交互**
- 风险：
  - 如果只做文本框+上传，会退化成调试页，不像“管理页面”。
- 建议：
  - 页面结构对齐“知识库管理”的双栏模型，但内容改为：
    - 左栏：图谱空间、导入入口、抽取预览；
    - 右栏：节点列表、关系列表、搜索结果、最近导入记录。
  - 首版不强求图可视化，先用表格和详情抽屉承载；图可视化放 P1。
- 优先级：**P1**

### 9. 问题：缺少错误码和任务状态定义
- 位置：**4.1 协议与数据契约**
- 风险：
  - 文件解析失败、LLM 输出不合法、Neo4j 连通失败，都需要前端可识别状态。
- 建议：
  - 接口统一复用 `ApiResponse`，但业务 data 中补充：
    - `taskId`
    - `status`（PENDING / EXTRACTING / PREVIEW_READY / IMPORTING / SUCCESS / FAILED）
    - `message`
    - `warnings`
  - 失败细分：
    - 文件解析失败
    - 抽取结果解析失败
    - 图写入失败
    - 空结果
- 优先级：**P1**

### 10. 问题：性能与容量未设上限
- 位置：**5.1 性能容量**
- 风险：
  - 大文件直接同步抽取会占用 Tomcat 线程并造成超时。
- 建议：
  - 首版限制：
    - 文件大小：10MB
    - 支持格式：txt / md / pdf / docx
    - 单次文本长度：20k~50k 字符
    - 单次预览实体上限：200
    - 单次预览关系上限：500
  - 超限时提示用户分批导入。
  - 文件抽取建议走异步任务，文本抽取可先同步。
- 优先级：**P1**

### 11. 问题：安全与审计要求未明确
- 位置：**6.1 安全合规**
- 风险：
  - 图谱数据可能含敏感人物和组织信息，若无审计，后续不可追溯。
- 建议：
  - 必须记录：
    - 谁导入
    - 导入来源（文本/文件）
    - 文件名/对象 key
    - 导入到哪个 `graphSpace`
    - 生成了多少实体/关系
    - 是否成功
  - 新增权限建议：
    - `graph:view`
    - `graph:import`
    - `graph:update`
    - `graph:delete`
- 优先级：**P1**

### 12. 问题：测试门槛需要前置
- 位置：**7.1 可测试性**
- 风险：
  - 若只做页面而不补协议测试，后续提示词调整会频繁打断功能。
- 建议：
  - 最少测试集：
    1. prompt 输出解析单测；
    2. Neo4j repository 写入/删除单测；
    3. `GraphController` 接口测试；
    4. 前端页面提交流程与预览状态测试。
- 优先级：**P1**

## 三、推荐落地设计（首版）

### 3.1 页面结构

单页面名称建议：**图谱管理**

页面分区：
1. **顶部操作区**
   - 图谱空间选择
   - 新建图谱空间
   - 刷新
   - 删除图谱空间
2. **左侧：抽取入图区**
   - Tab1：文本抽取
   - Tab2：文件抽取
   - Prompt 模板说明（只读）
   - 导入模式选择：`PREVIEW_ONLY / MERGE_APPEND / REPLACE_SPACE`
3. **中部：抽取预览区**
   - 实体表
   - 关系表
   - 校验提示（空实体、非法强度、重复关系）
   - “确认入图”按钮
4. **右侧：图谱数据管理区**
   - 节点列表
   - 关系列表
   - 关键字搜索
   - 节点详情抽屉
   - 关系详情抽屉
   - 最近导入记录

### 3.2 后端 API 设计（建议）

前缀：`/api/v1/graph`

1. 图谱空间
   - `GET /spaces`
   - `POST /spaces`
   - `DELETE /spaces/{space}`
2. 抽取任务
   - `POST /extract/text`
   - `POST /extract/file`
   - `GET /tasks/{taskId}`
   - `POST /tasks/{taskId}/confirm`
3. 图谱 CRUD
   - `POST /entities/page`
   - `GET /entities/{id}`
   - `POST /entities`
   - `POST /entities/delete`
   - `POST /relationships/page`
   - `GET /relationships/{id}`
   - `POST /relationships`
   - `POST /relationships/delete`
4. 搜索
   - `GET /search?space=...&keyword=...`
5. 统计
   - `GET /spaces/{space}/stats`

### 3.3 抽取结果标准化

虽然 prompt 输出是：
- `("entity"|实体名|类型|描述)`
- `("relationship"|源|目标|描述|强度)`

但后端落库前应统一转成结构化 DTO：

- `GraphExtractEntityDTO`
  - `entityName`
  - `entityType`
  - `entityDescription`
- `GraphExtractRelationshipDTO`
  - `sourceEntity`
  - `targetEntity`
  - `relationshipDescription`
  - `relationshipStrength`

并在服务端执行：
- 去重
- 大小写标准化（保留展示原值，主键建议 upper-case）
- 强度限定到 1~10
- 缺失字段剔除/告警

### 3.4 Neo4j 写入策略

推荐基于 Neo4j Java Driver 的 **managed transaction**：
- 读：`session.executeRead(...)`
- 写：`session.executeWrite(...)`

写入 Cypher 原则：
- 全部参数化，禁止字符串拼接 Cypher
- 使用 `MERGE` 保证实体幂等
- 关系统一 `MERGE (a)-[r:RELATED_TO {tenantId, graphSpace, sourceEntity, targetEntity, description}]->(b)`
- 再 `SET r.strength = $strength, r.updatedAt = datetime()`

### 3.5 页面首版不做的内容

以下建议明确延后：
- 真正的图谱可视化画布（如 G6 / Cytoscape）
- 多模型抽取对比
- 自动实体消歧
- 图谱版本回滚
- 审核流/多人协作

## 四、最小落地路径（MVP）

- 第一步：在 `gijela-core-pistil` 落 Neo4j 配置、Driver Bean、图谱空间/节点/关系 CRUD API，先不接 LLM。
- 第二步：在 `gijela-bloom-pistil` 新增“图谱管理”页面，完成图谱空间、节点、关系列表与基础 CRUD。
- 第三步：新增“文本抽取 -> 预览 -> 确认入图”链路，接入 LLM 抽取。
- 第四步：新增“文件上传 -> 文本提取 -> 抽取预览 -> 确认入图”链路，并补导入记录。
- 第五步：补权限、审计、异常提示和测试用例。

## 五、待拍板决策

1. 页面最终落在 **pistil 管理后台** 还是继续放在 `chat` 联调台？
2. `graphSpace` 是否作为必填维度？
3. 抽取结果是否必须“人工确认后入图”？
4. 文件是否先落对象存储再异步处理？
5. 首版关系类型是否固定为 `RELATED_TO`？
6. LLM 调用是否复用现有 OpenAI 兼容链路，还是单独配置图谱抽取模型？
7. 首版是否需要图可视化，还是列表/抽屉足够？
