### 一、可落地性结论
- 结论：**可落地**。
- 依据：
   1. “手动确认”与“同步执行”天然一致，流程更直观；
   2. 去除后台任务后，接口契约、前端交互、验收口径更统一；
   3. 在容量阈值受控前提下，同步链路可满足首版需求。

### 二、关键问题与调整建议
1. 问题：同步链路输入边界未冻结
   - 位置：`/extract/file` 与 `/import`
   - 风险：超大输入导致接口处理不稳定，触发重复提交。
   - 建议：首版先冻结文件/文本上限与超限错误码；同步超时阈值暂不设置。
   - 优先级：P0

2. 问题：同步返回结构未冻结
   - 位置：`/extract/*` 与 `/import` 响应
   - 风险：前后端字段口径漂移，联调反复修改。
   - 建议：统一返回 `previewId`、`warnings`、`stats`、`importedEntities`、`importedRelationships`。
   - 优先级：P0

3. 问题：幂等边界未覆盖同步重试
   - 位置：`/import`
   - 风险：网络抖动或前端重复点击导致重复入图。
   - 建议：强制 `Idempotency-Key`，同键返回上次导入结果快照。
   - 优先级：P0

4. 问题：失败回滚策略未定义
   - 位置：导入事务边界
   - 风险：部分写入后失败导致图谱不一致。
   - 建议：首版采用“分批写入 + 失败明细 + 可重放”，并记录 `sourceId/importBatchId` 支持按批次补偿删除。
   - 优先级：P1

5. 问题：手动确认审计粒度不足
   - 位置：审计字段
   - 风险：无法证明“谁在何时确认了哪一批预览”。
   - 建议：审计补充：`confirmedBy`、`confirmedAt`、`previewHash`、`previewId`、`resultSummary`。
   - 优先级：P1

### 三、最小落地路径（MVP）
- 第一步：保留“先预览、后确认”不变，`/extract/*` 与 `/import` 全同步返回。
- 第二步：冻结输入上限和分批上限，补超限错误码映射。
- 第三步：落幂等与审计，联调“重复点击确认”“失败重放”两类场景。

### 四、待拍板决策
1. 是否确认首版不建设任务查询接口。
2. `PARTIAL_SUCCESS` 是否允许自动重试，还是必须再次人工确认。
3. 失败补偿策略：按 `importBatchId` 全量回滚，还是只回滚失败批次。
