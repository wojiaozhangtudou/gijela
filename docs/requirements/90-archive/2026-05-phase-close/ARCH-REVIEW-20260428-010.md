# ARCH-REVIEW-20260428-010 同步 complete 失败场景消息持久化一致性评审

### 一、可落地性结论
- 结论：可落地。
- 依据：
  - 已将 `complete` 链路调整为“先写入用户消息，再调用 LLM”，并保留异常审计。
  - 已通过关键测试集回归，未引入链路回归。

### 二、关键问题与调整建议
1. 问题：同步 `complete` 与 `stream` 持久化顺序不一致。
   - 位置：`ChatOrchestratorServiceImpl#complete`（原实现）。
   - 风险：LLM 调用失败时用户消息丢失，导致会话轨迹不完整；与 `stream` 行为不一致。
   - 建议：统一为“先落用户消息，再调用上游”，成功后补写 assistant 消息。
   - 优先级：P0

2. 问题：失败路径应明确“只保留用户输入，不落 assistant”。
   - 位置：`ChatOrchestratorServiceImpl` 失败分支。
   - 风险：若误写 assistant 占位，会污染历史回放与摘要质量。
   - 建议：失败路径只做审计，不写 assistant 消息。
   - 优先级：P0

3. 问题：一致性修复缺少明确回归用例会导致后续回退。
   - 位置：`ChatOrchestratorServiceImplTest`。
   - 风险：后续重构可能再次引入“失败不落用户消息”问题。
   - 建议：补充成功/失败两类断言，分别校验持久化行为与审计输出。
   - 优先级：P1

### 三、最小落地路径（MVP）
- 第一步：调整 `complete` 调用顺序（先用户消息，后 LLM）。
- 第二步：补齐失败路径断言（不写 assistant）。
- 第三步：跑关键测试集验证无回归。
