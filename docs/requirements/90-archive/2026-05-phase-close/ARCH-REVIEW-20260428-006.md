# ARCH-REVIEW-20260428-006 chat 模块基础设施映射与待建清单评审

### 一、可落地性结论
- 结论：可落地。
- 依据：
  - 现有仓库已具备 Redis、MySQL、Qdrant 依赖/基础配置能力，其中 Redis 与 MySQL 已有实际使用基础。
  - chat 模块当前缺的不是基础设施选型，而是“chat 场景专用的数据模型、适配层和组件清单”。

### 二、关键问题与调整建议
1. 问题：基础设施有了，但 chat 模块的数据归属未冻结。
   - 位置：ARCH-REVIEW-20260428-004 第三章、ARCH-REVIEW-20260428-005 第二章
   - 风险：开发可能把会话态、历史消息、检索索引混存，造成职责混乱。
   - 建议：冻结基础设施映射：
     - Redis：会话态、最近消息、上下文摘要、SSE 会话状态
     - MySQL：会话元数据、历史消息、审计记录、附件元数据
     - Qdrant：知识检索
     - RustFS(S3)：附件对象存储
   - 优先级：P0

2. 问题：Redis 在仓库中已有安全模块用途，但 chat key 规范未定义。
   - 位置：现有 Redis 配置基础（security-common）
   - 风险：不同模块 key 冲突、TTL 不一致、难排查。
   - 建议：统一 chat Redis key 前缀：
     - `chat:session:{sessionId}:state`
     - `chat:session:{sessionId}:recent`
     - `chat:session:{sessionId}:summary`
     - `chat:sse:{sessionId}`
   - 优先级：P0

3. 问题：MySQL 已具备连接能力，但 chat 表清单未定义。
   - 位置：pistil 已有 MySQL 配置，chat 模块未扩展
   - 风险：开发先写代码后补表，导致 DTO 与表结构反复调整。
   - 建议：MVP 先冻结 4 张表：
     - `chat_session`
     - `chat_message`
     - `chat_audit_log`
     - `chat_attachment`
   - 优先级：P0

4. 问题：Qdrant 只有依赖，未形成接入层抽象。
   - 位置：顶层依赖管理存在 Qdrant 版本，但无业务适配层
   - 风险：后续 RAG/knowledge.search 开始时会直接把 client 侵入 service。
   - 建议：先定义 `KnowledgeSearchGateway` 抽象，MVP 提供 `QdrantKnowledgeSearchGateway` 骨架。
   - 优先级：P1

5. 问题：RustFS 作为附件存储已拍板，但元数据链路未并入总清单。
   - 位置：ARCH-REVIEW-20260428-005
   - 风险：只做对象上传，不做业务 fileId/objectKey 绑定，无法在会话中引用附件。
   - 建议：冻结附件链路：
     - RustFS 存对象
     - MySQL `chat_attachment` 存元数据
     - Chat 消息仅引用 `attachmentId` / `fileId`
   - 优先级：P0

6. 问题：待建组件尚未列表化，不能直接派给开发拆任务。
   - 位置：实施清单仍停留在目录级
   - 风险：多人并行时职责边界不清。
   - 建议：冻结待建组件：
     - `ConversationStore`
     - `ConversationRepository`
     - `MessageRepository`
     - `AttachmentService`
     - `ObjectStorageGateway`
     - `KnowledgeSearchGateway`
     - `ChatAuditService`
     - `SseSessionRegistry`
   - 优先级：P0

7. 问题：开发先后顺序未和基础设施映射绑定。
   - 位置：MVP 路径未细到组件交付顺序
   - 风险：先做 UI 或先接 Qdrant，主链路反而不闭环。
   - 建议：按顺序实施：
     1. Redis 会话态 + MySQL 会话/消息表
     2. 同步/流式主链路
     3. RustFS 附件链路
     4. Qdrant 检索链路
   - 优先级：P0

### 三、最小落地路径（MVP）
- 第一步：冻结基础设施映射与 key/table 规范
  - Redis key 前缀
  - MySQL 表清单
  - RustFS 对象 key 规范
- 第二步：先打通 chat 主链路
  - 同步会话
  - 流式输出
  - 会话态写 Redis、历史写 MySQL
- 第三步：补扩展链路
  - 附件上传/引用
  - Qdrant 检索
  - Skills / MCP mock

### 四、待拍板决策
1. `chat_message` 是否全量持久化到 MySQL（建议：是，便于审计与回放）。
2. Redis 最近消息保留轮数（建议：20 轮）。
3. 上下文摘要刷新策略（建议：每 10 轮或 token 超阈值触发）。
4. `chat_audit_log` 是否与现有审计体系复用表结构（建议：首期独立表，字段风格保持一致）。
5. Qdrant collection 是否按租户分集合还是共享集合加 tenant 过滤（建议：共享集合 + tenant filter）。
