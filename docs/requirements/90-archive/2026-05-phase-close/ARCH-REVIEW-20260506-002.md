# ARCH-REVIEW-20260506-002

## 一、可落地性结论
- 结论：**有条件可落地（坚持 D3 方案）**。
- 依据：D3 在力导布局、缩放、拖拽、数据绑定更新方面能力完整；当前仓库已有图谱 CRUD 接口，可直接承接 D3 渲染层。

## 二、关键问题与调整建议

1. 问题：D3 为低层绘图库，编辑器能力需自行封装。
   - 位置：第2章 2.1（前端选型）
   - 风险：交互一致性和维护成本高。
   - 建议：明确“先展示、后编辑”边界：
     - P0 仅实现：展示、查询、节点/关系高亮、详情弹窗、删除；
     - P1 再实现：画布内新增/连线编辑。
   - 优先级：P0

2. 问题：大图性能未设上限。
   - 位置：第4章 4.1（容量）
   - 风险：1920×921 非全屏出现卡顿、掉帧。
   - 建议：
     - 首屏限制：`nodes<=300`、`edges<=800`；
     - 超限进入“增量展开”（按节点点击扩展 1 跳邻居）。
   - 优先级：P0

3. 问题：渲染与业务状态耦合风险高。
   - 位置：第3章 3.2（前端架构）
   - 风险：D3 DOM 状态与 Vue 响应式状态不一致。
   - 建议：
     - 抽象 `GraphCanvasD3` 组件；
     - 组件输入仅收 `nodes/edges/selection`；
     - 对外仅暴露 `fit() / focusNode(id) / relayout()`。
   - 优先级：P0

4. 问题：删除与导入后的画布一致性未定义。
   - 位置：第5章 5.1（稳定性）
   - 风险：画布残留脏数据。
   - 建议：
     - 删除后局部更新（`selection.join`）；
     - 导入后按 `graphSpace` 全量重拉一次并 `fit`。
   - 优先级：P1

5. 问题：审计与权限尚未绑定图可视化操作。
   - 位置：第6章 6.1（安全合规）
   - 风险：无法追溯谁在画布执行删除。
   - 建议：
     - 画布触发删除统一走后端 API；
     - 继续复用 `X-Operator + ChatAuditService`。
   - 优先级：P0

## 三、最小落地路径（MVP）
- 第一步：新增 `GraphCanvasD3.vue`（只做展示 + 选中 + 缩放拖拽）。
- 第二步：接入现有查询接口（实体/关系分页 + 关键字）并映射为 `nodes/edges`。
- 第三步：打通“详情弹窗 + 删除动作 + 删除后局部刷新 + 导入后重拉”。

## 四、待拍板决策
1. D3 布局策略：`forceSimulation`（默认）还是 `dagre/elk`（有层级关系时启用）。
2. 首屏限制值是否固定为 `300/800`。
3. 是否允许画布内直接新增边（建议放到 P1）。
