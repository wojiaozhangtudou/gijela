# ARCH-REVIEW-20260507-008

## 一、可落地性结论
- 结论：有条件可落地。
- 依据：
  - Day1/Day2 已完成 `LLM 日志查询 API`、`ES 查询服务`、`前端看板骨架`，告警引擎具备复用基础。
  - 规则模型、事件模型、通知模型在 [SPEC-LLM-LOG-ALERT-ENGINE-20260507-001.md](./SPEC-LLM-LOG-ALERT-ENGINE-20260507-001.md) 已给出完整草案，但仍缺少“指标口径冻结、通知渠道落地方式、数据表初始化完成态”三个前置条件。

## 二、关键问题与调整建议
1. 问题：指标契约仍偏抽象，`metric_type` 与 Day2 查询口径未完全一一对应。
   - 位置：第 1.1 节、2.1 节。
   - 风险：`firstTokenMs`、`toolErrorRate`、`esIngestFailure` 在首版实现中容易退化为近似指标，触发结果不稳定。
   - 建议：在文档中补一张“告警指标 -> 聚合接口 -> 字段来源 -> 计算公式”映射表，未具备底层字段的指标先标记为 `P1 延后`。
   - 优先级：P0。

2. 问题：规则引擎假设数据库 DDL 已就绪，但当前执行策略是“迁移人工处理”。
   - 位置：第 1.1 节、4 节。
   - 风险：代码可编译但运行期直接失败，前端联调无法稳定开展。
   - 建议：在文档中增加“落地前检查项”，明确 `llm_alert_rule`、`llm_alert_event`、`llm_alert_notification_log` 三张表为上线前硬门槛。
   - 优先级：P0。

3. 问题：通知渠道示例以真实 webhook 为前提，但未定义降级策略。
   - 位置：第 3.1 节、3.2 节。
   - 风险：企业微信 / 钉钉 / 邮件任一未配置时，会阻塞规则联调。
   - 建议：文档改为“两阶段”：阶段 A 先落日志型通知适配器；阶段 B 再切换真实 webhook，并补充失败重试与限流策略。
   - 优先级：P1。

4. 问题：事件闭环只定义了 `open/ack/resolved`，但未定义重复告警合并策略。
   - 位置：第 2.2 节。
   - 风险：同一规则短时间内连续触发时，事件会膨胀，影响值班处置。
   - 建议：补充“冷却期内重复命中仅累计次数、不重复发通知”的规则，并为事件表预留 `repeat_count` 或在消息体中追加统计字段。
   - 优先级：P1。

5. 问题：前端告警页缺少与后端分页契约的明确约束。
   - 位置：第 4 节。
   - 风险：`Spring Page` 与页面字段命名不统一时，列表和分页器会出现兼容问题。
   - 建议：在文档补充事件分页响应示例，固定 `content/totalElements/number/size` 字段。
   - 优先级：P2。

## 三、最小落地路径（MVP）
- 第一步：冻结 P0 指标口径，只开放 `qps`、`errorRate`、`p95Latency` 三类规则。
- 第二步：完成三张告警表初始化，并上线规则 CRUD、事件分页、手动触发接口。
- 第三步：调度器按 5 分钟窗口跑通，通知先走日志型适配器，前端告警页先联通规则管理与事件处置。

## 四、待拍板决策
1. 首批上线的告警指标是否只保留 `qps/errorRate/p95Latency`。
2. 通知渠道首版是否允许仅记录发送日志，不直接接真实 webhook。
3. 重复告警是否采用“冷却期内合并事件”策略。
4. 告警规则是否按租户完全隔离，默认租户是否固定为 `default`。
