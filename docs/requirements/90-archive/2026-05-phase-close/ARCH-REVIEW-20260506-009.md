# ARCH-REVIEW-20260506-009

## 一、可落地性结论
- 结论：**可落地**。
- 依据：Day1/Day2 已覆盖功能与稳定性，Day3 只需补齐“生产发布控制面”即可上线：发布审批、双人复核、观测告警、回滚演练。

## 二、关键问题与调整建议

1. 问题：系统级提示词发布缺少流程化状态机。
   - 位置：第2章 2.1（架构边界与职责）
   - 风险：直接发布导致误操作。
   - 建议：引入发布状态：`DRAFT -> PENDING_REVIEW -> APPROVED -> PUBLISHED -> ROLLED_BACK`。
   - 优先级：P0

2. 问题：双人复核未落地到权限与接口。
   - 位置：第2章 2.2（安全与合规）
   - 风险：同一人可提交+发布，审计不可信。
   - 建议：新增角色点：`prompt.system.submit`、`prompt.system.approve`、`prompt.system.publish`，并强制“提交人与审批人不同”。
   - 优先级：P0

3. 问题：监控告警缺少版本维度指标。
   - 位置：第3章 3.1（性能与容量）
   - 风险：无法定位“某次发布导致错误率升高”。
   - 建议：增加指标标签：`promptPublishedVersion`、`grayHit`、`modelRoute`，并配置告警阈值。
   - 优先级：P1

4. 问题：回滚只有接口，没有演练标准。
   - 位置：第4章 4.1（稳定性）
   - 风险：真实事故时回滚步骤不熟。
   - 建议：固化回滚演练剧本（见第六章），要求每次大版本发布前演练一次。
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：补发布状态机与审批接口。
- 第二步：前端提示词页面增加“提交审批/审批通过/发布”流程按钮。
- 第三步：接入监控与一次完整回滚演练，达标后放量。

## 四、待拍板决策
1. 审批是否必须双人（建议：生产必须，测试可关闭）。
2. 告警触发后是否自动降级到上个版本（建议：先人工确认，P1 再自动化）。
3. 回滚是否允许跨租户批量执行（建议：不允许，按租户隔离）。

## 六、回滚演练剧本（最小版）
1. 发布一个带标识的测试提示词版本 `V_test`。
2. 发送 20 条标准问题，记录错误率、平均响应时延。
3. 执行回滚到 `V_prev`。
4. 再发送同样 20 条问题，确认指标恢复。
5. 产出演练记录：执行人、耗时、是否成功、差异指标。

## 七、验收门槛（Day3）
1. 审批链路可跑通，且“提交人=审批人”会被拒绝。
2. 发布只允许 `APPROVED` 状态版本。
3. 观测面板可按 `promptPublishedVersion` 过滤错误率。
4. 回滚演练全流程 ≤ 10 分钟。
