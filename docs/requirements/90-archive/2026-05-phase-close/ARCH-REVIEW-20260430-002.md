# ARCH-REVIEW-20260430-002 技能命中率评审（knowledge.search / attachment.context）

- 评审日期：2026-04-30
- 评审对象：chat 工具调用链（技能发现→选择→执行→续跑）

## 一、可落地性结论
- 结论：有条件可落地
- 依据：
  1. 工具注册与执行链已完整（`SkillRegistry` + `ToolExecutor` + `AUTO_TOOL_CONTINUE`）。
  2. 低命中核心不在“能力缺失”，而在“调用触发策略弱 + 协议兼容不完整 + 默认技能噪音”。
  3. 已完成第一轮修正（工具策略提示、文本 tool_code 兼容、默认技能收敛），可显著提升命中率。

## 二、关键问题与调整建议
1. 问题：工具触发策略只靠工具名/简短描述，缺少强约束指令
   - 位置：REQ-20260427-002 §三.P0-7（Function Calling），实现：`OpenAiChatAdapter.buildRequest()`
   - 风险：模型倾向“直接回答”而非先检索；`attachment.context`更易被忽略。
   - 建议：在请求前置 system 策略提示，明确“部署/参数类问题先调 `knowledge.search`；附件语义先调 `attachment.context`；禁止只输出工具文本”。
   - 优先级：P0

2. 问题：仅支持结构化 `tool_calls`，未覆盖部分模型的文本工具协议
   - 位置：REQ-20260427-002 §五.5（工具执行并回传模型继续对话），实现：`OpenAiCompatibleClient` / `OpenAiChatAdapter`
   - 风险：出现“卡在 knowledge.search『...』”现象，工具未真正执行，命中统计失真。
   - 建议：兼容 `<tool_code>{...}</tool_code>` 文本工具调用：提取→执行→follow-up 二次补全。
   - 优先级：P0

3. 问题：默认技能集合包含低价值噪音技能（`echo`/`time.now`）
   - 位置：实现：`gijela-bloom-chat/src/store/chat.ts`
   - 风险：模型在 auto 选择时分散概率，拉低核心技能命中率。
   - 建议：默认只启用 `knowledge.search` 与 `attachment.context`，把其余技能改为可选。
   - 优先级：P1

4. 问题：`attachment.context` 依赖 `process_status=2`，处理中附件不可见
   - 位置：实现：`SkillRegistry.loadAttachmentContext()`
   - 风险：模型调用后返回空，形成“调用了但没用”的负反馈，后续更少触发。
   - 建议：返回“处理中附件计数/提示”，并给出“稍后重试/缩小 query”建议文案。
   - 优先级：P1

5. 问题：缺少可观测指标（按技能维度的触发率/成功率/无结果率）
   - 位置：REQ-20260427-002 §四（可观测性）
   - 风险：无法区分“没触发”与“触发后无结果/失败”。
   - 建议：新增指标：`tool_call_rate`、`tool_success_rate`、`tool_empty_rate`（按 skill、模型、租户分桶）。
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：策略修正（已完成）
  - 后端注入 system 工具策略提示；技能描述增强为“场景触发型描述”。
- 第二步：协议兜底（已完成）
  - 增加文本 `<tool_code>` 兼容执行链，保证“看到工具文本=能执行工具”。
- 第三步：默认收敛（已完成）
  - 前端默认技能改为 `knowledge.search` + `attachment.context`。
- 第四步：可观测闭环（待完成）
  - 增加技能命中率与空结果率指标，并在日志中附 `skillName`、`query`、`hitCount`。
