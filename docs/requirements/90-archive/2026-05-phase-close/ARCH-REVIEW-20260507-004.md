# ARCH-REVIEW-20260507-004

## 需求基线（用于条目引用）
- 第1章 条目1.1：日志存储为 ES，不依赖 Kibana。
- 第1章 条目1.2：需要可直接开工的聚合 API 契约与看板信息架构。
- 第2章 条目2.1：必须满足租户隔离、脱敏、审计可追溯。
- 第2章 条目2.2：支持时序、TopN、分布、Trace 下钻与告警。

### 一、可落地性结论
- 结论：可落地。
- 依据：
  - 现有后端（Spring Boot）可快速承接“查询网关 + DSL 模板化”能力。
  - 现有前端（Vue3 + Element Plus）可承接三视图看板并复用已有权限体系。
  - 关键在于先冻结接口契约与字段字典，避免后续联调反复。

### 二、关键问题与调整建议
1. 问题：聚合 API 若按图表拆分过细，后续难维护。
   - 位置：第1章 条目1.2
   - 风险：接口爆炸、权限校验重复。
   - 建议：收敛为 6 个通用接口（P0）：
     - `POST /api/v1/llm-logs/query/timeseries`
     - `POST /api/v1/llm-logs/query/topn`
     - `POST /api/v1/llm-logs/query/distribution`
     - `POST /api/v1/llm-logs/query/records`
     - `GET /api/v1/llm-logs/query/trace/{traceId}`
     - `POST /api/v1/llm-logs/query/export`
   - 优先级：P0

2. 问题：查询条件缺少统一对象，前后端联调成本高。
   - 位置：第2章 条目2.2
   - 风险：每接口一套 filter，容易漏租户隔离条件。
   - 建议：统一 `LogQueryFilter`：
     - `timeRange`: `startAt/endAt`（必填）
     - `tenantId`（服务端二次覆盖，禁止前端越权）
     - `appCode`, `modelRoute`, `provider`, `model`
     - `status[]`, `errorCode[]`, `toolName[]`
     - `sessionId`, `traceId`, `userId`
     - `env`, `sampled`, `keyword`
   - 优先级：P0

3. 问题：缺少标准返回结构，前端图表适配复杂。
   - 位置：第1章 条目1.2
   - 风险：每图都写转换逻辑，易出错。
   - 建议：统一返回 VO：
     - `TimeSeriesResponse { buckets: [{ ts, value, group? }] }`
     - `TopNResponse { items: [{ key, value, ratio }] }`
     - `DistributionResponse { items: [{ key, count, p50?, p95?, p99? }] }`
     - `TraceDetailResponse { traceId, timeline[], summary }`
     - `RecordPageResponse { total, pageNo, pageSize, records[] }`
   - 优先级：P0

4. 问题：ES DSL 若由前端拼接会引入安全风险。
   - 位置：第2章 条目2.1
   - 风险：DSL 注入、越权字段查询、高成本查询攻击。
   - 建议：
     - 后端模板化 DSL（策略枚举驱动），前端只传业务参数。
     - 增加查询守卫：最大时间窗（默认 24h，最高 7d）、最大分页 200、聚合 bucket 上限 500。
     - 字段白名单与索引白名单固定在服务端配置。
   - 优先级：P0

5. 问题：看板 IA 未冻结，页面易反复。
   - 位置：第1章 条目1.2
   - 风险：模块职责混乱，用户学习成本高。
   - 建议：冻结页面信息架构（P0）：
     - 一级菜单：`LLM 可观测中心`
     - Tab1 `SRE 总览`：
       - 卡片：QPS、错误率、P95、首 token P95、ES ingest 失败率
       - 图表：请求趋势、错误趋势、慢请求分布、模型路由对比
     - Tab2 `研发排障`：
       - 查询区：traceId/sessionId/errorCode/toolName
       - 图表：错误码 TopN、工具失败 TopN、慢会话 TopN
       - 明细：事件表 + 右侧 trace 时间线抽屉
     - Tab3 `审计视图`：
       - 查询区：tenant/operator/modelRoute/action
       - 图表：操作量趋势、高风险操作 TopN
       - 明细：审计事件列表（脱敏字段）
     - Tab4 `告警中心`：
       - 规则、状态、最近触发、确认人、抑制窗口
   - 优先级：P0

6. 问题：告警与看板数据口径可能不一致。
   - 位置：第2章 条目2.2
   - 风险：同一时间窗看板正常但告警触发，可信度下降。
   - 建议：
     - 告警规则复用同一聚合查询服务（同 filter、同时间窗对齐）。
     - 规则版本化：`ruleId + version`，触发记录保留计算快照。
   - 优先级：P1

7. 问题：缺少可直接执行的开工顺序。
   - 位置：第1章 条目1.2
   - 风险：多人并行开发互相阻塞。
   - 建议：按以下实施拆分（P1）：
     - 后端先行：字段字典、DTO/VO、6 个查询接口、ES 查询模板。
     - 前端并行：SRE 总览页 + 排障页骨架，先接 mock。
     - 联调收口：trace 下钻、租户隔离、导出与告警规则。
   - 优先级：P1

### 三、最小落地路径（MVP）
- 第一步：冻结 API 契约（DTO/VO）与查询边界（时间窗、分页、bucket 上限）。
- 第二步：上线 `timeseries/topn/records/trace` 4 个核心接口 + 前端 `SRE 总览`。
- 第三步：补 `distribution/export`、`研发排障` 与 `告警中心`，完成灰度验证。

### 四、待拍板决策
1. 导出能力是否首期上线（CSV 异步导出 vs 二期）。
2. Trace 明细展示是否支持“跨服务拼接”（chat + skill + mcp）。
3. 告警通知优先渠道与升级策略（短信是否纳入）。
4. 审计视图是否开放给租户管理员（多租户权限边界）。
