# ARCH-REVIEW-20260506-003

## 一、可落地性结论
- 结论：**可落地**。
- 依据：现有图谱页面与 API 已具备查询/导入/删除基础能力，仅需新增 D3 画布组件与映射层即可形成可视化闭环。

## 二、关键问题与调整建议

1. 问题：缺少“文件级实施清单”，开发容易走偏。
   - 位置：第2章 2.1（实施路径）
   - 风险：组件边界模糊，后期难维护。
   - 建议：按以下文件级拆分实施（P0）：
     - 新增：`gijela-bloom/gijela-bloom-chat/src/components/graph/GraphCanvasD3.vue`
     - 新增：`gijela-bloom/gijela-bloom-chat/src/components/graph/types.ts`
     - 新增：`gijela-bloom/gijela-bloom-chat/src/components/graph/useGraphD3.ts`
     - 新增：`gijela-bloom/gijela-bloom-chat/src/components/graph/mapper.ts`
     - 修改：`gijela-bloom/gijela-bloom-chat/src/views/GraphPage.vue`
     - 修改：`gijela-bloom/gijela-bloom-chat/src/types/graph.ts`
     - 修改：`gijela-bloom/gijela-bloom-chat/src/api/graph.ts`
   - 优先级：P0

2. 问题：后端缺少“图视图查询接口”，前端无法一次性取 nodes/edges。
   - 位置：第3章 3.1（协议契约）
   - 风险：前端拼装成本高，数据不一致。
   - 建议：新增接口（P0）：
     - `POST /api/v1/chat/graph/view/query`
     - 入参：`graphSpace, keyword, centerNode, depth, limitNodes, limitEdges`
     - 出参：`nodes[], edges[], truncated`
   - 优先级：P0

3. 问题：渲染性能保护策略未落地。
   - 位置：第4章 4.1（性能容量）
   - 风险：1920×921 非全屏卡顿。
   - 建议：
     - 默认阈值：`limitNodes=300, limitEdges=800`
     - 超限展示告警条 + “继续扩展”按钮
     - D3 `tick` 节流：每 16ms 刷新一次
   - 优先级：P0

4. 问题：交互与数据变更联动未定义。
   - 位置：第5章 5.1（稳定性）
   - 风险：删除后画布与列表不同步。
   - 建议：
     - 删除节点/关系后：调用删除 API → 局部移除画布元素 → 刷新右侧列表
     - 导入后：重新查询视图并 `fit` 全图
   - 优先级：P1

5. 问题：详情页触发链路未统一。
   - 位置：第3章 3.2（前端交互）
   - 风险：列表和画布详情行为不一致。
   - 建议：统一事件：
     - 画布点击节点触发 `onNodeClick(node)`
     - 画布点击关系触发 `onEdgeClick(edge)`
     - 复用现有详情 Dialog，避免重复 UI
   - 优先级：P0

## 三、最小落地路径（MVP）
- 第一步：完成后端 `view/query` 接口与前端类型定义。
- 第二步：落地 `GraphCanvasD3.vue`（展示、缩放、拖拽、选中）。
- 第三步：完成“查询/删除/导入后刷新/详情弹窗”联动。

## 四、待拍板决策
1. `view/query` 是否支持 `centerNode + depth`（建议默认支持）。
2. 画布内是否允许直接删除（建议允许，新增放 P1）。
3. 是否增加“保存布局”能力（建议放 P1）。
