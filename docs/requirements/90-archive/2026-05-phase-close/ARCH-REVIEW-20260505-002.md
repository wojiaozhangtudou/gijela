# ARCH-REVIEW-20260505-002：Neo4j 图谱能力改为落在 chat 模块时的隔离方案说明

- 日期：2026-05-05
- 状态：已评审
- 关联：[ARCH-REVIEW-20260505-001.md](./ARCH-REVIEW-20260505-001.md)

## 一、可落地性结论

- 结论：**可落地**。
- 依据：
  1. 你已明确页面和能力应落在 `gijela-core-chat / gijela-bloom-chat` 这一条线上，而不是 `pistil` 管理后台；
  2. 当前仓库已有知识库管理页、文件上传、文本入库、LLM 调用链路，最适合在 chat 模块上继续扩展；
  3. 你使用的是 **Neo4j 开源版 / Community Edition**，因此隔离方案不应设计成“多数据库隔离”，而应采用**单库内逻辑隔离**。

## 二、关键问题与调整建议

### 1. 问题：模块落点需要调整
- 位置：**1.1 模块归属**
- 风险：若仍按前一版放到 `pistil`，会和你当前“知识库管理页同风格、同链路”的诉求不一致。
- 建议：
  - 后端落在 `gijela-core-chat`
  - 前端落在 `gijela-bloom-chat`
  - 直接复用现有：
    - 文件上传/对象存储链路
    - Tika 文本提取链路
    - LLM OpenAI 兼容调用链路
    - 知识库管理页的 UI 模式
- 优先级：**P0**

### 2. 问题：开源版 Neo4j 不适合用“多数据库隔离”
- 位置：**2.1 隔离方案**
- 风险：如果设计成“每个租户一个 database / 每个图谱一个 database”，Community Edition 下基本不可取，后续运维也会复杂。
- 建议：
  - 对开源版 Neo4j，采用**单库 + 逻辑隔离**。
  - 隔离字段最少包含：
    - `tenantId`
    - `graphSpace`
  - 也就是说，所有节点和关系都带这两个属性。
- 优先级：**P0**

### 3. 问题：需要解释“隔离”到底隔离什么
- 位置：**2.2 隔离语义**
- 风险：若只说“隔离”，实现时容易误解成只靠 label 区分，后续删除/查询容易串数据。
- 建议：
  - 这里的隔离不是物理隔离，而是**逻辑隔离**，主要隔离三件事：
    1. **租户隔离**：不同 tenant 之间不能互相查到图数据；
    2. **图谱空间隔离**：同一 tenant 下可以有多个图谱，如 `default`、`neo4j-demo`、`project-a`；
    3. **导入批次隔离**：可选增加 `sourceId/importBatchId`，便于按批次回滚。
- 优先级：**P0**

### 4. 问题：只靠 Label 隔离不够
- 位置：**2.3 图模型**
- 风险：若用 `:Person`、`:Org`、`:Event` 直接承载业务隔离，Cypher 很容易漏条件，导致跨图谱查询。
- 建议：
  - 首版节点统一主 label：`Entity`
  - 业务类型放属性：`entityType`
  - 查询条件必须带：`tenantId` + `graphSpace`
  - 例如：
    - 节点：`(n:Entity {tenantId: $tenantId, graphSpace: $graphSpace})`
    - 关系：`[r:RELATED_TO {tenantId: $tenantId, graphSpace: $graphSpace}]`
- 优先级：**P0**

### 5. 问题：唯一键必须体现隔离字段
- 位置：**2.4 唯一约束**
- 风险：如果只用 `entityName` 唯一，不同图谱里同名实体会冲突。
- 建议：
  - 节点唯一键建议：`(tenantId, graphSpace, normalizedName)`
  - `normalizedName` 建议统一大写，对齐你 prompt 里“实体名大写”的输出约束。
  - 可建唯一约束：
    - `FOR (n:Entity) REQUIRE (n.tenantId, n.graphSpace, n.normalizedName) IS UNIQUE`
- 优先级：**P0**

### 6. 问题：关系去重也要带隔离维度
- 位置：**2.5 关系模型**
- 风险：不同图谱中相同实体对的关系会互相覆盖。
- 建议：
  - 首版关系类型固定为 `RELATED_TO`
  - 去重键建议：
    - `tenantId`
    - `graphSpace`
    - `sourceName`
    - `targetName`
    - `description`
  - `strength` 用于更新，不作为关系类型。
- 优先级：**P0**

### 7. 问题：删除操作要明确是“删空间”还是“删批次”
- 位置：**3.1 删除语义**
- 风险：图数据删除比知识库危险，若没有边界，容易误删整张图。
- 建议：
  - 首版只开放三类删除：
    1. 删除单节点（同时删关联关系）
    2. 删除单关系
    3. 删除整个 `graphSpace`
  - “按导入批次删除”放 P1。
- 优先级：**P1**

### 8. 问题：chat 模块首版页面不必做图可视化
- 位置：**3.2 页面能力**
- 风险：如果一开始就上画布，周期会被拉长。
- 建议：
  - 先完全复用知识库管理页的模式：
    - 左侧：文本导入 / 文件导入 / 预览
    - 右侧：实体表 / 关系表 / 搜索 / 最近导入记录
  - 图可视化（G6 / Cytoscape）放 P1。
- 优先级：**P1**

## 三、“隔离”到底怎么做

### 3.1 不是物理隔离
在你这个场景里，“隔离”**不是**：
- 不是每个租户一个 Neo4j 实例；
- 不是每个图谱一个独立数据库；
- 不是每种实体一个单独 schema。

因为你用的是 **Neo4j 开源版**，更适合：
- **一个 Neo4j 库**
- **所有数据进同一个 database**
- 靠属性字段做逻辑边界

### 3.2 是逻辑隔离
建议每个节点、每条关系都带：
- `tenantId`
- `graphSpace`
- `sourceId`（可选，导入任务或文件 ID）

示例：

```cypher
MERGE (n:Entity {
  tenantId: $tenantId,
  graphSpace: $graphSpace,
  normalizedName: $normalizedName
})
SET n.entityName = $entityName,
    n.entityType = $entityType,
    n.entityDescription = $entityDescription,
    n.updatedAt = datetime()
```

关系同理：

```cypher
MATCH (a:Entity {tenantId: $tenantId, graphSpace: $graphSpace, normalizedName: $source})
MATCH (b:Entity {tenantId: $tenantId, graphSpace: $graphSpace, normalizedName: $target})
MERGE (a)-[r:RELATED_TO {
  tenantId: $tenantId,
  graphSpace: $graphSpace,
  description: $description
}]->(b)
SET r.strength = $strength,
    r.updatedAt = datetime()
```

### 3.3 查询时必须强制带条件
所有查询都必须自动补：
- `tenantId`
- `graphSpace`

不能把它交给前端“自觉传”。
应由后端基于 `ChatContext` 自动注入 `tenantId`，前端只选择 `graphSpace`。

### 3.4 这样做的结果
这样就能实现：
- tenant A 看不到 tenant B 的图；
- tenant A 下的 `project-x` 不会污染 `project-y`；
- 同名实体在不同图谱空间可以共存；
- 删除某个 `graphSpace` 时不会影响别的空间。

## 八、复核结果（按当前代码仓实际情况）

本次按 `chat` 模块现状重新核对后，结论从“理论可落地”收敛为：**可以落地，且改动路径清晰，没有结构性阻断**。

### 8.1 已具备的落地条件

1. **前端页面承载位已存在**  
  `gijela-bloom-chat` 已有 [KnowledgePage.vue](../../gijela-bloom/gijela-bloom-chat/src/views/KnowledgePage.vue) 与独立路由 [router/index.ts](../../gijela-bloom/gijela-bloom-chat/src/router/index.ts)，新增 `GraphPage.vue` 属于同层扩展，不需要改管理后台主框架。

2. **后端接口风格已现成**  
  [ChatController.java](../../gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/controller/ChatController.java) 已承载 `/api/v1/chat/knowledge/**`、`/storage/**`、`/mcp/**` 等 BFF 风格接口，继续加 `/api/v1/chat/graph/**` 是顺路的。

3. **文件提取链路已现成**  
  [DefaultKnowledgeIngestionService.java](../../gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/service/impl/DefaultKnowledgeIngestionService.java) 已经在用 Tika 做文件提取，文件入图不需要从零造轮子。

4. **LLM 调用链路已现成**  
  [ChatModuleConfig.java](../../gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/config/ChatModuleConfig.java) 已装配 `OpenAiCompatibleClient`，而 [OpenAiChatAdapter.java](../../gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/adapter/llm/OpenAiChatAdapter.java) 已证明 chat 模块能稳定复用该客户端。

5. **租户上下文已现成**  
  [ChatModuleProperties.java](../../gijela-core/gijela-core-chat/src/main/java/com/gijela/morpheus/chat/config/ChatModuleProperties.java) 已定义 `tenantHeader`，`ChatController` 也在统一构造 `ChatContext`，因此 `tenantId` 自动注入图谱查询/写入条件是顺路能力。

### 8.2 当前仍需补上的落地项

1. **`gijela-core-chat` 还没有显式引入 Neo4j Driver**  
  父 POM 已管理 `neo4j-java-driver` 版本，但 [gijela-core-chat/pom.xml](../../gijela-core/gijela-core-chat/pom.xml) 当前没有这个依赖；落地前需显式加一条 dependency。

2. **`ChatModuleProperties` 还没有 graph 配置段**  
  当前只有 `retrieval / storage / openAi / embedding / mcp` 等配置，没有 `graph` 配置。需要新增例如：
  - `gijela.chat.graph.enabled`
  - `gijela.chat.graph.uri`
  - `gijela.chat.graph.username`
  - `gijela.chat.graph.password`
  - `gijela.chat.graph.database`
  - `gijela.chat.graph.default-space`

3. **还没有抽取结果解析器**  
  你的 prompt 输出格式是行文本：
  - `("entity"|实体名|类型|描述)`
  - `("relationship"|源|目标|描述|强度)`
  这要求后端新增一个稳定的 parser，而不能直接把原始文本给前端。

4. **还没有导入预览 DTO / VO**  
  首版如果要“先预览再确认”，需要补：
  - 抽取请求 DTO
  - 抽取结果 VO
  - 导入确认 DTO
  - 节点/关系分页 VO

### 8.3 最终复核判断

- **没有结构性阻断**：现有 `chat` 模块已经具备页面、路由、BFF API、文件提取、LLM 调用、租户上下文这 6 个核心基础。
- **真正新增的只有 4 类东西**：
  1. Neo4j 配置与 repository；
  2. 实体关系抽取 parser；
  3. 图谱 CRUD service/controller；
  4. 一个仿知识库管理页的新页面。
- 因此结论维持：**可以落地，建议直接按 chat 模块方案推进**。

### 9.1 图谱空间

1. `GET /spaces`
  - 说明：列出当前租户下图谱空间
  - 响应：`{ spaces: string[], count: number }`

2. `POST /spaces`
  - 入参：`CreateGraphSpaceRequest`
  - 响应：`{ graphSpace: string, status: "created"|"exists" }`

3. `DELETE /spaces/{graphSpace}`
  - 说明：删除整个图谱空间（含节点和关系）
  - 响应：`{ graphSpace: string, deletedNodes: number, deletedRelationships: number }`

### 9.2 抽取预览

4. `POST /extract/text`
  - 入参：`GraphExtractTextRequest`
  - 响应：`GraphExtractPreviewResponse`

5. `POST /extract/file`（`multipart/form-data`）
  - 字段：`file`, `graphSpace?`, `title?`, `importMode?`
  - 响应：`GraphExtractPreviewResponse`

### 9.3 确认入图

6. `POST /import`
  - 入参：`GraphImportRequest`
  - 响应：`GraphImportResultResponse`

### 9.4 CRUD + 检索

7. `POST /entities/page`
  - 入参：`GraphEntityPageRequest`
  - 响应：`GraphEntityPageResponse`

8. `POST /relationships/page`
  - 入参：`GraphRelationshipPageRequest`
  - 响应：`GraphRelationshipPageResponse`

9. `POST /entities/delete`
  - 入参：`GraphDeleteEntitiesRequest`
  - 响应：`{ deletedEntities: number, deletedRelationships: number }`

10. `POST /relationships/delete`
   - 入参：`GraphDeleteRelationshipsRequest`
   - 响应：`{ deletedRelationships: number }`

11. `GET /search`
   - 参数：`graphSpace`, `keyword`, `limit?`
   - 响应：`GraphSearchResponse`

  1. 要求首版必须做图可视化画布
  2. 要求首版支持按任务回滚 + 审批流
  3. 要求去掉 `tenantId + graphSpace` 强制过滤

当前判断：**满足 Go，建议进入实现阶段。**

## 十四、模式切换设计（仅 LLM 场景下支持 4/5/6）

你当前仅依赖 LLM 做图谱抽取时，建议提供统一模式开关：`extractMode`。

### 14.1 模式定义

1. `LLM_ONLY`（方式 4）
   - 行为：仅执行一次 LLM 抽取，直接返回预览。
   - 用途：调试模型原始能力、快速试验。

2. `LLM_RULES`（方式 5）
   - 行为：LLM 抽取后走后端规则校验。
   - 规则最小集：
     - 实体名统一大写并去重；
     - `entity_type` 非枚举值置为 `其他`；
     - 关系两端实体不存在则删除；
     - `relationship_strength` 裁剪到 1~10；
     - 去除重复关系与自环。
   - 用途：生产默认模式。

3. `LLM_HUMAN`（方式 6）
   - 行为：LLM 抽取 + 规则校验 + 人工确认后再入图。
   - 用途：高风险、核心图谱数据。

### 14.2 入图控制

取消 `autoImport` 开关，统一为“先预览、后确认入图”：

- 抽取接口一律只返回预览结果；
- 入图仅允许调用 `/import` 显式确认；
- 三种 `extractMode` 都不允许绕过确认流程。
