# ARCH-REVIEW-20260506-001

## 一、可落地性结论
- 结论：**有条件可落地**。
- 依据：现有 chat 图谱链路（抽取/导入/实体关系 CRUD）已具备，缺口主要在“可视化渲染层 + 交互契约 + 性能分层策略”。只要先收敛图库与数据契约，即可快速落地。

## 二、关键问题与调整建议

1. 问题：目标与范围未分层，容易一次性做成“重图编辑器”。
   - 位置：第1章 1.1（目标定义）
   - 风险：交付周期失控，前端性能与交互复杂度显著上升。
   - 建议：拆为两阶段：
     - 阶段A：可视化浏览 + 查询 + 单点增删改；
     - 阶段B：批量编辑、布局保存、路径分析。
   - 优先级：P0

2. 问题：前端图库选型未拍板。
   - 位置：第2章 2.1（技术栈）
   - 风险：后续二次迁移成本高（事件模型、样式体系、布局算法差异大）。
   - 建议：
     - 默认选型：**Cytoscape.js + elkjs（或 dagre）**；
     - Vue3 集成方式：页面内封装 `GraphCanvas` 组件，接口收敛为 `setData()/fit()/highlight()`。
   - 优先级：P0

3. 问题：协议与数据契约未覆盖“图展示专用字段”。
   - 位置：第3章 3.1（接口契约）
   - 风险：前端需要二次拼装，导致查询抖动、节点闪烁。
   - 建议：新增图查询接口（建议）：
     - `POST /api/v1/chat/graph/view/query`
     - 入参：`graphSpace, keyword, depth, limitNodes, limitEdges, centerNode`
     - 出参：`nodes[], edges[], stats`（节点含 `id,label,type,degree,updatedAt`；边含 `id,source,target,label,strength`）。
   - 优先级：P0

4. 问题：性能与容量策略未定义。
   - 位置：第4章 4.1（性能容量）
   - 风险：大图一次性加载导致浏览器卡顿、白屏。
   - 建议：
     - 首屏限制：`nodes <= 300`、`edges <= 800`；
     - 超限采用“中心扩展”模式（按节点点击分批拉取）；
     - 前端启用 `requestAnimationFrame` 节流高频交互。
   - 优先级：P0

5. 问题：稳定性策略未覆盖“并发编辑冲突”。
   - 位置：第5章 5.1（稳定性）
   - 风险：多人编辑时出现覆盖写或误删。
   - 建议：
     - 删除/修改接口增加 `ifMatchUpdatedAt`（乐观锁字段）；
     - 删除后前端执行局部重拉，不做全图重建。
   - 优先级：P1

6. 问题：安全与合规未覆盖图操作审计维度。
   - 位置：第6章 6.1（安全合规）
   - 风险：无法追踪“谁删除了哪个节点/关系”。
   - 建议：
     - 复用 `ChatAuditService`，动作统一：`GRAPH_VIEW_QUERY/GRAPH_NODE_UPSERT/GRAPH_EDGE_DELETE`；
     - 透传 `X-Operator`，后端统一鉴权。
   - 优先级：P0

7. 问题：可测试性与上线门槛未明确。
   - 位置：第7章 7.1（测试上线）
   - 风险：上线后才暴露浏览器渲染兼容问题。
   - 建议：
     - 前端：补 3 类用例（大图渲染、增删后局部刷新、详情弹窗）；
     - 后端：补接口契约测试（分页/过滤/深度限制）；
     - 验收门槛：1920×921 非全屏可稳定操作。
   - 优先级：P1

## 三、最小落地路径（MVP）
- 第一步：拍板可视化栈（Cytoscape.js + elkjs），冻结图查询接口契约。
- 第二步：实现“查询展示 + 节点/关系详情 + 单条增删改 + 审计”。
- 第三步：实现“分批扩展加载 + 性能阈值保护 + 回归测试”。

## 四、待拍板决策
1. 图可视化库是否采用 Cytoscape.js（默认）还是 AntV G6（备选）。
2. 图查询接口是否引入 `depth`（推荐默认 1，最大 3）。
3. 首屏上限是否采用 `300/800`（节点/边）。
4. 编辑权限是否与 `promptOverride` 同级做白名单控制。
