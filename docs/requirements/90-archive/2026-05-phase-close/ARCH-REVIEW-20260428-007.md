# ARCH-REVIEW-20260428-007 chat 模块基础设施默认值收敛评审

### 一、可落地性结论
- 结论：可落地。
- 依据：
  - 当前剩余未拍板项已缩小到基础设施默认值层面，不再影响总体架构方向。
  - 这些项可直接按默认值实施，后续如有压测/联调反馈再局部调整。

### 二、关键问题与调整建议
1. 问题：`chat_message` 是否全量落 MySQL 未定。
   - 位置：ARCH-REVIEW-20260428-006 第四章条目1
   - 风险：若只存摘要，不利于审计、回放与问题排查。
   - 建议：**默认全量持久化到 MySQL**；Redis 仅保留热数据与摘要。
   - 优先级：P0

2. 问题：Redis 最近消息保留轮数未定。
   - 位置：ARCH-REVIEW-20260428-006 第四章条目2
   - 风险：过小影响上下文，过大增加热数据成本。
   - 建议：**默认保留最近 20 轮**。
   - 优先级：P0

3. 问题：上下文摘要刷新策略未定。
   - 位置：ARCH-REVIEW-20260428-006 第四章条目3
   - 风险：刷新过频影响性能，过稀影响上下文质量。
   - 建议：**默认每 10 轮或累计 token 超阈值时刷新一次摘要**。
   - 优先级：P0

4. 问题：`chat_audit_log` 是否复用现有审计表未定。
   - 位置：ARCH-REVIEW-20260428-006 第四章条目4
   - 风险：复用现有后台审计表会引入语义污染。
   - 建议：**首期独立表 `chat_audit_log`**，字段风格与现有审计体系保持一致。
   - 优先级：P0

5. 问题：Qdrant collection 隔离策略未定。
   - 位置：ARCH-REVIEW-20260428-006 第四章条目5
   - 风险：按租户分 collection 会增加运维复杂度；共享集合若无隔离规则会有越权风险。
   - 建议：**默认共享 collection + tenant filter**。
   - 优先级：P0

6. 问题：附件对象 key 规范虽有建议，但未纳入默认值决策。
   - 位置：ARCH-REVIEW-20260428-005 第二章条目3
   - 风险：开发各自生成 key，影响追踪与归档。
   - 建议：**默认 `tenant/session/yyyyMMdd/uuid.ext`**。
   - 优先级：P1

7. 问题：开发是否可直接开始仍需最终判定。
   - 位置：ARCH-REVIEW-20260428-004
   - 风险：若默认值不冻结，开发仍会反复确认。
   - 建议：以上默认值全部作为 **开发基线**；除非明确提出变更，否则按此实施。
   - 优先级：P0

### 三、最小落地路径（MVP）
- 第一步：冻结默认值
  - MySQL 全量历史消息
  - Redis 最近 20 轮 + 摘要缓存
  - 摘要每 10 轮或 token 超阈值刷新
  - 独立 `chat_audit_log`
  - Qdrant 共享 collection + tenant filter
- 第二步：按默认值建模与实现
  - 表结构、Redis key、Qdrant filter、RustFS key 规范
- 第三步：联调验证
  - 历史回放、上下文压缩、检索过滤、附件引用

### 四、待拍板决策
1. 是否接受以上默认值作为开发基线（建议：接受）。
2. token 阈值具体数值首期是否固定为 `6000`（建议：是，后续配置化）。
