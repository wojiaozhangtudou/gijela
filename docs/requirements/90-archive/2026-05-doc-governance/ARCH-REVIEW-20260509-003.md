# ARCH-REVIEW-20260509-003 Bug 修复分区与跟踪方式评审

### 一、可落地性结论
- 结论：可落地。
- 依据：当前索引已明确仓库进入 Bug 修复阶段，但目录结构中缺少专门的缺陷跟踪分区，容易导致 `01-active` 承担需求与缺陷双重职责。新增 `04-bugs` 后，职责更清晰，且不影响现有归档结构。

### 二、关键问题与调整建议
1. 问题：当前阶段已进入 Bug 修复，但目录结构未显式承接。
   - 位置：index.md / “当前状态、目录规划”
   - 风险：用户知道进入修复期，但不知道问题记录应该放哪里，容易继续把缺陷文档写进 `01-active`。
   - 建议：新增 `04-bugs` 目录，并在索引中标明当前阶段的挂载位置。
   - 优先级：P0

2. 问题：缺陷缺少统一聚合视图。
   - 位置：04-bugs / 缺失聚合页
   - 风险：问题数一多后，只靠分散的 `BUG-*.md` 文件难以快速查看优先级、状态与责任分工。
   - 建议：新增 `BUG-LIST.md` 作为当前问题总表，只维护进行中的问题。
   - 优先级：P1

3. 问题：Active 与 Bug 阶段的切换规则未写清。
   - 位置：01-active / README；00-governance / README
   - 风险：已完成需求会长期残留在 `01-active`，目录持续膨胀，削弱“当前活跃事项”语义。
   - 建议：补充“主体完成后进入 04-bugs”的迁移规则。
   - 优先级：P1

### 三、最小落地路径（MVP）
- 第一步：新增 `04-bugs/README.md`，明确适用场景与使用规则。
- 第二步：新增 `04-bugs/BUG-LIST.md`，作为进行中问题总表。
- 第三步：更新治理文档、Active 文档与索引页，明确阶段切换规则。
