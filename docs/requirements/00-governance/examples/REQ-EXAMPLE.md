# REQ-20260509-EXAMPLE 日志看板新增“导出筛选结果”能力

## 1. 背景
- 当前问题：日志看板支持筛选与分页，但运营排查时无法直接导出当前筛选结果。
- 触发原因：Bug 修复和联调阶段需要把指定时间段、指定模型、指定状态的日志快速导出给研发和测试分析。
- 业务价值：减少人工二次整理，提高排障效率，统一导出链路。

## 2. 目标
- 目标 1：支持导出日志看板当前筛选结果。
- 目标 2：保持与现有查询条件、权限和响应结构一致。

## 3. 范围
### 3.1 In Scope
- 日志看板导出按钮。
- 后端新增导出接口。
- 导出结果沿用当前筛选条件。

### 3.2 Out of Scope
- 不新增新的日志字段。
- 不改单条日志详情页结构。
- 不引入异步导出任务系统。

## 4. 影响模块
- 后端：`gijela-core-chat` 日志查询 Controller / Service。
- 前端：日志看板页面、`src/api` 请求封装。
- 安全/权限：沿用现有日志查看权限，不新增并行权限体系。
- 数据/缓存/任务：复用现有 ES 查询，不新增缓存。

## 5. 方案约束
- 保持与现有模块边界一致：Controller 只收参与返回，业务逻辑放在 Service。
- 优先复用现有接口/Service/Store：前端请求放到 `src/api`，页面层不散写请求细节。
- 不做的改动：不改 ES 索引结构，不改统一响应协议。

## 6. 数据与接口契约
### 6.1 请求
- 路径：`POST /api/v1/llm-logs/records/export`
- 方法：`POST`
- 参数：沿用当前筛选对象，如时间范围、模型、traceId、状态。

### 6.2 响应
- 成功返回：文件流或导出地址。
- 错误码：沿用统一 `ApiResponse` / `ErrorCode`。

### 6.3 事件/日志（如有）
- 记录一次导出审计日志，便于后续追踪导出行为。

## 7. 权限与安全
- 鉴权方式：沿用现有 JWT 鉴权链路。
- 权限点：复用日志查看权限或导出子权限。
- 审计要求：记录操作者、筛选条件、导出时间。
- 敏感数据处理：导出结果不得额外暴露脱敏规则外的信息。

## 8. 前端交互
- 页面入口：日志看板列表页工具栏。
- 页面状态：导出中、成功、失败三态。
- 交互流程：用户选择筛选条件 → 点击导出 → 前端调用导出接口 → 下载文件。
- 空态/异常态：无数据时提示“当前筛选条件下无可导出数据”。

## 9. 性能与稳定性
- 预估 QPS / 并发：低频功能，峰值并发低。
- 时延目标：普通导出 $< 5s$。
- 重试 / 降级 / 回滚：导出失败可重试；若实现风险高，先降级为只导出当前页。

## 10. 验收标准
- [ ] 能导出当前筛选条件对应的数据
- [ ] 前后端仍沿用现有统一协议与权限链路
- [ ] 导出失败时有清晰提示
- [ ] 文档已同步

## 11. 测试与上线检查
- 单测：后端 Service 增加筛选条件映射测试。
- 联调：验证不同筛选组合的导出结果。
- 回归范围：日志看板查询、筛选、详情查看不受影响。
- 上线前置条件：确认导出字段不包含敏感信息。
