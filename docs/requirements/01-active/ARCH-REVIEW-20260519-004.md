## 一、问题背景

在 Phase 1 代码实现中发现，`POST /api/v1/chat-flow/chat/completions` 接口对 `workflowId` 字段的处理存在设计歧义：

- **设计文档**（初版）：未明确说明 `workflowId` 是否应在请求中传入
- **实现策略**（后端）：从 Session 自动关联工作流 ID，请求中不需要传入
- **前端实现**：正确地没有在请求中传入 `workflowId`
- **结果**：前后端实现一致，但设计文档需澄清

---

## 二、改进的设计决策

### 2.1 核心原则

**一个会话（Session）对应一个工作流（Workflow）** → `workflowId` 是 Session 属性，不是每次消息的参数

### 2.2 API 请求契约（澄清后）

#### POST /api/v1/chat-flow/chat/completions
**功能**：用户发送消息，触发工作流执行并获得助手回复

**请求体**
```json
{
  "sessionId": "string",      // 必需，会话ID（格式：cfs_<uuid>，8-64字符）
  "content": "string",        // 必需，用户消息内容（1-8000字符）
  "requestId": "string"       // 可选，幂等性键值（1-64字符）
}
```

**说明**：
- ❌ **不** 包含 `workflowId`：工作流 ID 由 Session 自动关联（在创建 Session 时指定）
- ✅ 消息的工作流始终是 Session 对应的工作流

**响应体**
```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "sessionId": "cfs_...",          // 会话ID
    "messageId": "cmsg_...",         // 本轮用户消息ID
    "answer": "string",              // 工作流执行结果（AI回复）
    "workflowId": "cfwf_...",        // 执行的工作流ID（信息性返回）
    "runId": "cwrun_...",            // 工作流运行ID（用于查询详情）
    "createdAt": "2026-05-19..."     // 消息创建时间
  }
}
```

### 2.3 对比：Session 创建时指定工作流

#### POST /api/v1/chat-flow/chat/sessions
**请求体**
```json
{
  "title": "string",                  // 必需，会话标题
  "workflowId": "string",             // 必需，关联的工作流ID
  "workflowInputs": {}                // 可选，工作流初始化参数
}
```

**说明**：
- ✅ 会话创建时必须指定 `workflowId`
- ✅ 之后所有 completion 调用都会使用这个工作流

## 三、设计核心要点

### 3.1 为什么 Completion 不需要 workflowId？

| 理由 | 说明 |
|------|------|
| **一对一绑定** | 一个 Session 绑定一个工作流，不需要每次重复指定 |
| **一致性** | 同一对话中所有消息处理流程一致 |
| **简化前端** | 前端无需维护工作流选择状态，只需跟踪 sessionId |
| **避免冲突** | 防止用户误传不同的 workflowId 导致逻辑混乱 |

### 3.2 场景支持

**场景 1：单工作流多轮对话**（✅ 支持）
```
1. 创建会话 → workflowId = wf_001
2. 发送消息 1（会话ID = cfs_001）→ 调用 wf_001
3. 发送消息 2（会话ID = cfs_001）→ 调用 wf_001
4. 发送消息 3（会话ID = cfs_001）→ 调用 wf_001
```

**场景 2：多工作流独立对话**（✅ 支持）
```
1. 创建会话 A → workflowId = wf_001 → sessionId = cfs_001
   发送消息 → 调用 wf_001

2. 创建会话 B → workflowId = wf_002 → sessionId = cfs_002
   发送消息 → 调用 wf_002
```

**场景 3：运行时切换工作流**（❌ Phase 1 不支持）
- 若需要支持，应：
  1. 创建新会话（使用新的工作流 ID）
  2. 或在 `PUT /sessions/{sessionId}` 时更新工作流 ID

### 4.2 后端 Service 逻辑（确认）

```java
// ChatflowConversationServiceImpl.completion()
public ChatflowCompletionVO completion(ChatflowCompletionDTO dto) {
    // 1. 加载并验证 session
    ChatflowSessionEntity session = loadSession(dto.getSessionId());
    if (!session.getStatus().equals("active")) {
        throw new IllegalStateException("会话已禁用");
    }

    // 2. 从 session 读取工作流 ID（不从请求读取）
    String workflowId = session.getWorkflowId();  // ✅ 核心设计点
    
    // 3. 验证工作流
    WorkflowEntity workflow = workflowService.getWorkflow(workflowId);
    if (!workflow.getStatus().equals("published")) {
        throw new IllegalStateException("工作流未发布");
    }

    // ... 后续逻辑
}
```

## 八、向后兼容性

### 当前设计的兼容性评估

| 场景 | 兼容性 | 说明 |
|------|--------|------|
| 客户端无意中传入 workflowId | 安全 | DTO 验证忽略多余字段，不会报错 |

## 九、改进决策总结

### 9.1 设计决策（已定）

| 决策项 | 值 | 理由 |
|--------|-----|------|
| Completion 需要 workflowId 参数 | ❌ 否 | Session 已绑定工作流，无需重复传入 |
| 工作流切换支持 | Phase 1 不支持 | 创建新会话以切换工作流 |
| 初始化参数传入时机 | 创建 Session 时 | workflowInputs 作为 Session 属性存储 |
| 工作流版本跟踪 | 使用 published_version | 自动追踪工作流最新发布版本 |

### 9.2 实现状态

- ✅ 后端代码：已正确实现（无 workflowId 参数）
- ✅ 前端代码：已正确实现（API 调用不传 workflowId）
